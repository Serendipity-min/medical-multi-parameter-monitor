## 4. 工具失败的实证位置与纠正

原工具复用QueryLink时继承6000次SDK API上限。31槽/559B计划实际完成前26槽共432B（包含一次启用、配置及全部15次时间查询），随后第一条DNS命令只写出14B头部、**没有CRLF**，累计UART446B。原API日志重建与冻结计划前缀一致，SDK调用恰好6000，没有负DLL返回；失败为主机ESP_API_BUDGET，不是服务器超时或ESP拒绝DNS。DNS查询完成0、SNTP关闭尝试0。

此前仅按预期指令边界理解会漏掉这14B，现已按原生AP写记录逐字节复核，明确记录部分命令。原源码、授权、使用标记、字节流和返回码不覆盖。

预算异常发生在读取/发送轮询路径，原读取包装器将保护失败锁存read_failed并取消verified_running_flash，实际close_resume=false；未完成健康续跑收尾。下一会话实测HALT与这条退出链一致，但缺乏DLL Close内部全部子操作轨迹，不能借此宣布历史ROM唯一根因已解决。没有依据责怪负责人改线或输入信号。

修正版SDK上限12000，每条普通命令之前在调用原生读取前检查3200次收尾余量；余量不足只跳向预定关闭命令，仍受原生总上限与外部硬停限制。这样避免先耗尽budget触发read_failed再尝试收尾。不放宽任何设备读写地址、UART命令、时间判据或算法阈值。原11项新定向离线检查通过；增加预算保留/关闭及只补剩余工作检查后14项通过。旧矩阵未重跑。**完整31槽修正版尚未实板验证**，不能用离线通过冒充它已通过。
