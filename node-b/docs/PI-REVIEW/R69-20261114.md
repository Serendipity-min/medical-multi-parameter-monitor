## 3. 排查推理
1. **红灯只出现在 C 一侧。** S2（A–E）和 S4（B–D）上各有两块从板，它们互相应答，CAN2/CAN4 不报错；打开 ECG 后 CAN4 绿灯闪烁，说明 B 在发数据。S1、S3 上除 GT 外只有 C。GT 把 A/E 和 B/D 的报文转发到 CAN1/CAN3 后，如果 C 不应答（ACK），GT 会不停重发并累计错误，最后红灯常亮。两路同时红灯，最简单的解释是 C 两个 CAN 控制器都没有应答。
2. **以前为什么没暴露。** 以前每段 3 块板挂在同一条总线上，C 不在线时两块从板仍然互相应答，现象只是“节点不上云”，不会有红灯。拆段以后，C 所在子段只剩 C 一个应答方，C 不工作就直接表现为总线错误。
3. **C 的启动顺序（WP-AZ `2c97094`，`gateway/b5/network_main.c`）。** 统一构建跳过 776–778 行的早期 CAN 初始化，先在 800 行执行 `pass_startup()`（复位标志检查和 ESP AT 启动），成功后才在 826 行执行 `b4_hw_init()` 打开两个 bxCAN。
   - `pass_startup()` 失败时，C 打印 `GW PASS_BOOT_RESET_LOCKED` 或 `GW FAIL LINK` 后停在 `platform_poll()`，CAN 永远不初始化。
   - `CAN_Init` 退出初始化模式超时（`b4_bxcan.c` 返回 -2）时，C 进入 `for(;;){}`，同样不应答。
   - 反过来，如果 CAN 已初始化，之后无论走哪条停止路径，`b4_hw_stop()` 都按注释“控制器仍可 ACK 对端”，不会造成 GT 无应答。因此**红灯说明 C 停在 CAN 初始化之前，或者 C 本身没有正常上电或运行**。
4. **云端旁证。** 两份记录 15 分钟以上全程网关 OFFLINE。负责人补充：热点已打开，但 C 没有连上。注意：`pass_startup()` 只做 MCU 与 ESP 之间的 UART AT 握手（`gateway/mqtt/src/platform.c:846`：`+++` 退出透传后收到 `AT`→`OK`），**不包括加入 Wi-Fi**。所以只是热点连不上时，C 仍会打开 CAN 并应答，网关只是 OFFLINE。只有 ESP 本身不响应（没上电、没启动、UART 不通），才会同时造成“热点连不上”和“CAN 不打开”。两条现象合在一起，最符合 ESP 没有响应 AT 握手。
5. **采样点与故障帧选项。** 采样点和独立故障帧隔离选项为 UNKNOWN。点对点 30 cm 线上，采样点差几个百分点不会导致两路一起持续错误；而且这无法解释网关 OFFLINE。暂列为次要嫌疑。
6. **阻值合格不代表收发器已上电。** 60 Ω 只证明 C 板载 120 Ω 在线上，不能证明 C 的收发器有电，也不能证明 MCU 在运行。
