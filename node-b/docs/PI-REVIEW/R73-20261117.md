## 3. 启动溢出（R71 §3.3 的跟进）
- **本轮读数**：
  - CAN 初始化前两路 `overflow` 都是 0；
  - 初始化后首个样本分别为 352（A/E 段）和 369（B/D 段），此后 30 分钟不再增加。
  - R70 为 352/370，与本轮几乎相同。
- **直连基线**：R20、R32 首个值都是 0/0，但那两轮用的是 WP-AZ 之前的固件。同版本固件的启动原件没有找到，所以这组对照只能参考。
- **PI 推断（未证实）：溢出主要来自 GT 在 C 不应答期间积压的报文，C 一开始应答就集中补发。** 依据有三条：
  1. A/E 段报文少，B/D 段有连续 ECG 报文。如果原因是 C 的主循环来不及取走，B/D 段的丢弃数应明显更多，实际两段几乎相等；
  2. R70 和 R72 中 C 上电前从板已运行的时长不同，丢弃数却几乎不变，像是固定容量的缓存溢出；
  3. 直连时 A/E 互相应答，不会积压，读数为 0。
- **影响**：只发生在 C 启动时，持续约 2 s，此后不再增加，不影响稳态。
  - 补发的旧报文会以接收时刻打上时间戳（`b4_bxcan.c:51-52`），理论上 C 在启动后的极短时间内可能处理到 C 上电前的数据。
  - C 联网约需 35 s，这段时间内这些数据早已被新数据覆盖，不会上云。
  - 记为观察项，不改 GT 配置，也不改固件。
