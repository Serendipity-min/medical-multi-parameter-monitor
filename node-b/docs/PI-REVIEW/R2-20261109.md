## 3. 新发现

### N-01（P2）WP-B 的夹具未接入任何回归入口；清单有路径错误
- `gateway/mqtt/tests/test_field01_wifi_failure.c` 不被任何 Python 运行器、CI 或脚本引用，只存在于清单里的一条手动命令。以后改动 `gateway_transport.c` 时没有东西会再跑它。
- 清单 `PI-R1-EVIDENCE-MANIFEST.json` 第 793 行 path 为 `gateway/mqtt/tests/.c`，第 898 行的 `producer` 命令里文件名也丢了（原应为 `test_field01_wifi_failure.c`）。这条证据按清单原文无法复现。PI 是用补全文件名后的命令复现的。
- 同类的文件名被吞掉问题可能还有，请全表自查。

### N-02（P2）VPS 与 Windows 的 5.6 KB 差值：已有一条线索
- PI 对 VPS 的 `gateway.map` 做了归档汇总（数值是按 map 条目累加，与 `.bin` 大小对不上，仅用于看相对量级）：项目 LTO 对象约 57.5 KB，`libc_nano.a` 约 10 KB，`libgcc.a` 约 0.75 KB。
- Windows 总共 57,776 B，数值上约等于 VPS 的“项目对象”部分。**线索（不是结论）**：两个工具链链入的 libc 内容量可能不同（是否多拉了 printf 族、`strtod`、`malloc` 等）。
- 现 VPS 余量：FIELD01 2,148 B，非 FIELD01 2,016 B；Windows FIELD01 余 7,760 B。

### N-03（P1，影响 PI-01 方案）USART3 接收中断优先级最高，且 8 MHz 下 CPU 余量很紧
- Codex U-04 推定 USART3 抢占优先级为复位默认 0（高于 CAN 的 3）。`platform.c` 的 `USART3_IRQHandler` 体内有两处 `%` 取模（含 `MP_B5_EGRESS_FINAL` 下的高水位计算）。
- 8 MHz 内核每字节周期数（10 位/字节）：115200 约 694；230400 约 347；500000 约 160；921600 约 87。若中断体含入口出口约 100 个周期（**PI 估算，待 Codex 用反汇编给出实数**），则突发接收时 500000 约占 60% CPU，且因优先级高于 CAN，会延迟 CAN RX 处理；bxCAN 接收 FIFO 仅 3 帧。
- 这就是 R1 里 U-03/U-04 的真实风险点，必须在提高波特率之前量化。

### N-04（P1，PI-02 的证据）sector3 与 RAM 注入的热点配置**两个字段都不同**
- Codex U-06：SSID 15 B（`00fbf133`）对 11 B（`f39d82da`）；密码 8 B（`f07910aa`）对 10 B（`c775e7b7`）。FIELD01 使用的是 sector3 的那套。
- 假设（均未验证，不得当结论）：
  - H1：sector3 里是旧/错的热点凭据。此时 `+CWJAP` 子码预计为 2（密码错误）或 3（找不到 AP）。
  - H2：凭据对但关联超时（子码 1），失败耗时 15.125 s 与手册默认 15 s 吻合，指向热点休眠或兼容模式。
  - 两者靠 WP-B 新增的子码输出才能区分，**需要一次获批的现场窗口**。
- U-08 显示历史成功窗信号很强（channel 11，rssi −26/−31 dBm），信号强度不是已知问题。

### N-05（P3）ESP-AT 是 `2.3.0.0-dev` 开发构建
`AT+GMR` 报 `2.3.0.0-dev(s-bcd64d2 …)`、1 MB 镜像。官方手册与此构建的行为可能不一致，所以对 `AT+UART_CUR` 的范围、切换时序，都应以运行时发现为准，不能只信手册。

### N-06（P1，更正 PI 自己在 R1 的错误）过采样 8 对 8 MHz 内核没有精度收益
R1 §PI-01 第 4 点写“用过采样 8 改善 BRR 精度”，这在 8 MHz 下不成立。PI 重新计算（STM32 按 BRR 的整数+小数舍入；ESP 侧**假设** UART 时钟 80 MHz 整数分频，待 Codex 核对）：

| 目标波特率 | STM32 实际（OS16 与 OS8 相同） | STM32 误差 | ESP 误差（假设） | 双方相对误差 |
|---:|---:|---:|---:|---:|
| 115200 | 115,942 | +0.64% | +0.06% | +0.58% |
| 230400 | 228,571 | −0.79% | +0.06% | −0.86% |
| **460800** | 470,588 | **+2.12%** | −0.22% | **+2.35%（偏高）** |
| **500000** | 500,000 | **0.00%** | 0.00% | **0.00%** |
| 921600 | 888,889 | −3.55% | −0.22% | −3.33%（不可用） |

**修正候选档位：230400 与 500000**，取代 R1 的 230400 与 460800。500000 在两端都是整数分频，误差为零。按 P3 同样的缩放估算，500000 约 13 批/s，230400 约 10.8 批/s；仍是估算，不得入结论表。

### WP-C1：PI-01 的离线实现（取代 R1 的 WP-C）
前提不变：只用 `AT+UART_CUR`，禁止 `AT+UART_DEF`。

1. **参数化**：`ESP_UART_BAUD` 单一常量，`platform.c:373`、`:457` 的公式、`USART_InitTypeDef`、超时预算全部引用它。默认构建仍是 115200，**行为与现有 Host 输出一致**。
2. **协商状态机（运行时发现）**：
   - 115200 `AT` 同步 → `AT+UART_CUR?` → 解析实际五元组（只取数字，报告 `GW UART_CUR baud=… data=… stop=… parity=… flow=…`）→ 若已是目标速率则不改。
   - 否则发 `AT+UART_CUR=<baud>,8,1,0,0`，收到 `OK` 后按**可配置的保护间隔**（手册没给，默认值由 Codex 提议并说明依据）切 STM32 → `AT` 重同步。
   - 失败有界回退：STM32 先退回 115200 试一次；再失败则上报 `GW FAIL UART_NEGOTIATE` 并停止联网，不循环、不写持久配置。
   - 若 ESP 实际返回的速率与请求不同（手册称可能因分频有差异），按实际值设置 STM32，并上报差值。
3. **Host 夹具**：扩展 `mock_esp`，可配置：保护间隔长短、切换后旧速率字节的丢失/乱码、收到 `OK` 后不切换、回复缺失、参数被改写。逐一证明回退与停止路径。
4. **BRR**：实现一个纯函数计算实际波特率与误差，Host 测试复现 §3 N-06 的表；若 |双方相对误差| > 2%，构建期拒绝该档位。
5. **两个候选构建**：`230400`、`500000`。不做 460800/921600。
6. **阶段计时与分因计数**（R1 PI-01 第 6 点原样保留），并加入 USART3 中断每字节的周期数实测路径说明（见 WP-I）。
7. **预算**：以 Windows 工具链报告每个候选的 Flash/SRAM 增量与 sector4 余量；P3 设计预算为 Flash 6,144 B，如实际超出，说明超出原因，不删既有检查。

**验收（离线）**：P3 同一输入在 115200 / 230400 / 500000 下 Host 重跑，报告批/s、实时波形交付/输入、CRC 不一致、倒序/重复；缺口为 0 才可称“Host 容量改善”，不是实板 PASS。

### WP-I（分析，纯离线）：USART3 中断与 CAN 的余量
1. 用 Windows 工具链的反汇编，给出 `USART3_IRQHandler` 在正常路径与溢出路径的**指令数与最坏周期数**（说明估算方法和假设，如除法指令周期）。
2. 以 8 MHz、230400 与 500000，算出突发接收（单个 MQTT 包长度的 CIPRECVDATA）时 USART 中断的 CPU 占比，以及 CAN RX0 在最坏情况下的延迟上界；对照 bxCAN 3 帧 FIFO 与 500 kbit/s 最小帧时间，给出是否存在 CAN 溢出风险的算术结论。
3. 若结论为风险存在，提出最小缓解选项（如去掉中断体里的 `%` 取模、环形缓冲取 2 的幂并用掩码、去掉 `MP_B5_EGRESS_FINAL` 下热路径里的高水位取模、调整 USART3 与 CAN 的相对优先级——**优先级改动要列出对 CAN 的影响，PI 审后再动**），并给出每项的字节与周期收益。
4. 只给分析与建议，**本包不改中断优先级**。

### WP-F（设计 + 离线实现，需负责人先批准概念）：START 前的 PREFLIGHT
动机：现有固件只在接受 START 之后才入网，任何 Wi-Fi 排查都要烧掉唯一的 START（R1 PI-03、WP-E 结论）。

建议的最小设计，供负责人决策，**未获批准前只出设计文档，不改固件**：
- C 在 `DISARMED` 状态下接受一条一次性命令（暂名 `PREFLIGHT`），顺序执行：`AT` 同步 → `AT+GMR`（数字版本）→ `AT+UART_CUR?`（只报五个数字）→ `AT+CWJAP` 加入热点（只报子码与成功/失败）→ 查询 IPv4 是否就绪（只报是/否）。完成后停止，不 TLS、不 MQTT、不启 T0、**不消耗 START**。
- 回执绑定本次启动代次与单调时间；不输出 SSID/口令/IP/原始回复；有总时限与单次 AT 时限；失败即停，不重试。
- 这一条命令同时回答 U-02（五元组）、N-04（子码），并让后续窗口在 START 前就能判定 `PRECONDITION_BLOCKED`。
- 需 Codex 回答：新增命令面对 Flash 的字节估算（Windows 工具链）、与现有 START 状态机的互斥与回退、是否改变 FIELD01 既有安全边界（sector0/4、sector3 只读）。
