## 2. 代码审读结论（`router.c`、`egress.h`、`b4_gateway.c`、`network_main.c`）
**接受，没有阻断问题。** 要点：
1. **默认关闭：** 全部改动在 `MP_OUTAGE_RETENTION` 内。
2. **TIME 与锚：** C 在两段 CAN 上持续发 TIME，B 不改；锚外推 + 每 100 ms 最多 1 ms 的收敛 + `last_utc` 非递减钳位；过期用 `utc_floor` 防止新锚回退。符合 R24 §2。
3. **保留环：** 标量 1,472 项、状态 736 项，各 28 B，在 CCM `NOLOAD`，不占常规 SRAM（余 20,696 B）；满时只覆盖超过 240 s 的最旧项，否则保护旧数据、拒收新数据并计 `pressure`。NIBP 为 2 个值，正好装得下 `values[2]`。
4. **回放：** 仅在实时队列为空且槽位不满时取标量，保留一个槽给下一条实时 QoS1；标量全部确认后才补波形；队首在 PUBACK 前不出队。实时优先、标量优先均成立。
5. **一个低概率风险（要求补测，不阻断）：** `b5_prepare_publish` 对 `timestamp > now+1000 ms` 或 0 的帧返回失败，此时 `mp_router_retain_unsent` 解除在途标记但**不出队**，下个循环会重取同一项。若校时使时钟回退 >1 s，或锚在回放中过期，队首会被卡到时间追上为止。正常重连时的校正远小于 1 s（SNTP 实测差 334 ms），不会触发，但缺 Host 用例。

## 3. 状态补传裁定（回答 Codex 的 BLOCKED 项）
**裁定：本阶段云端不补传历史状态，状态只在 C 保留。**
- 理由：现有 Backend 把 `source=REPLAY` 的节点/网关状态判为非法，且 MQTT 适配器拒绝其进入历史主题；旧状态直接发到当前状态主题会让旧 ONLINE/OFFLINE 覆盖当前状态。要支持补传，需要新的历史状态通道和去重语义，属于云端改动，是另一个授权对象，也不是方案 A 的"标量优先"核心。
- 后果：断网期间云端看不到节点状态时间线（只有 LWT 与恢复后的当前状态）。**这是对 R24 "标量与节点状态无损"的收窄，需要负责人确认（§6）。**
- C 侧 736 项状态环（约 20.6 KB CCM）暂时用不上云端，保留不动；若负责人不需要历史状态，后续可回收这块 CCM。
