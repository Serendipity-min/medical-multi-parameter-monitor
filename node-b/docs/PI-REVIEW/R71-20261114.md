## 3. 新发现
1. **C 在主窗口前已经在运行（19:09:05）。** R68 收尾时记为全部断电，但 R70 准入时 COM15 读到了 C 的运行日志。当时 J-Link 仍然连着。Codex 已立即通知负责人关 C、拔 J-Link，该记录单独保存，没有混入主窗口，处置正确。
   - 这说明 C 的供电状态（USB_UART 加板上开关）没有被现场流程完全掌握。
   - R68 时 C 的上电方式、是否连着 J-Link、是否比 ESP 或其他部分先上电，现在都无法回溯。这是 R68 根因的**一个候选**，未经证实。
2. **COM15 跟着 C 一起上电才枚举，所以录不到前约 9 秒。** 首次打开报 Windows 错误 433，19:15:10.898 才打开成功。启动握手的几行正好落在这段缺口里。只要还用 C 板载的 USB 串口，这个缺口就会一直存在。
3. **C 的 CAN 接收溢出计数在启动时就不为零。** `overflow` 首个样本分别为 352 和 370，之后一直不增加，说明稳态没有丢帧。可能的原因有两种：
   - C 刚打开 CAN 时，主循环还在做联网和 SNTP（期间出现两次 `GW FAIL SNTP_FRESH_SAMPLE`），96 槽环形缓冲来不及取走；
   - GT 在 C 不应答期间积压了报文，C 一应答就集中补发。
   仓库里没有直连接法下的启动溢出基线，所以目前无法区分是哪种。
4. **指示灯。** C 上电后 CAN1/CAN3 由红转绿闪；CAN3/CAN4 近似绿灯常亮，与 ECG 波形连续高频收发相符，不算异常。逐点灯态表和 GCAN Box 截图没有取得。

## 4. 附带条件与未决项
1. R68 失败根因为 UNKNOWN。同样的现象（C 一侧两路红灯）再出现时，按 R70 方法被动录控制台定位。
2. 启动溢出 352/370 没有基线。请 Codex 在受限 EFS 中查找以往直连现场（W-AZ、R65 等）`FIVE STATE` 或 `ABC A_CAN` 的首个 `overflow` 值，只回报数值。若直连时也有同量级的值，就是启动阶段的固有现象，与网桥无关。
3. 逐点灯态、GCAN Box 错误计数、现场照片、精确断电秒数均为 UNKNOWN，留到正式验收补齐。

## 5. 正式验收（双绞线）卡的前置要求
- C 只用一条明确的供电路径。J-Link 物理拔除。上电前确认 C 确实断电（例如 COM15 不存在）。
- 控制台改用独立的 USB-TTL 适配器，只接 C 的 USART1 TX 和 GND，由主机供电，在 C 上电前打开，以便录到启动握手行。如果做不到，至少用每 100 ms 重试一次的打开循环。
- 上电顺序沿用 R70：GT → A/B/D/E → C。记录 C 上电的精确秒、CAN1/CAN3 由红转绿的时刻、30 min 稳态、每 5 min 灯态和 GCAN Box 错误计数，以及启动溢出计数。
- 断电后量四个子段的阻值，与 R68 的 60.8–61.0 Ω 对照。
