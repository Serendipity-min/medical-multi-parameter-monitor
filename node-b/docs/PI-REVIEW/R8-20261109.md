## 2. 纠正：“最高 10.390 批/s，低于 10.45 门槛”不是容量结论

Codex 的结论表述会误导读者。PI 读了 `R7-P3-TRANSPARENT-HOST` 的逐格数据：

| 对比（115200，0 µs，对端应答 370 ms） | 普通模式（校准点 55 ms） | 透传 |
|---|---:|---:|
| 批/s | 8.047 | 10.380 |
| 波形 交付/输入 | **392 / 495** | **492 / 495** |
| 丢弃 / 顶替 / 迟到 | **168 / 153 / 0** | **0 / 0 / 0** |
| 窗口末队列 | 24（顶满） | 12 |

- 透传的 `10.38x` 在 115200、230400、0–60 µs 几乎所有格都**一样**，说明它等于**夹具的到达速率减去窗口末尚在途的批次**，不是处理能力的上限。用 `10.45` 去比一个被输入速率封顶的数字没有意义。
- 正确的读法：**透传下 115200 与 230400 都能“跟上”输入，零丢弃、零顶替**；普通模式则丢 168、顶替 153、队列顶满。这与我在 R7 的结构性判断一致，并且**比我预期的更好**：我原以为透传需要 230400 才够，夹具显示 115200 在 CPU 开销 ≤60 µs/字节时也跟得上。
- **需要警惕的两个点**：
  1. **CPU 开销**：120 µs/字节时，115200 透传崩溃（丢 220、迟到 14，6.25 批/s），230400 也出现 84 次顶替。所以真实的每字节开销必须量出来（WP-Q 的 DWT 计数）。
  2. **QoS1 窗口**：三个在途槽位被占满的采样比例：250 ms 档约 40%，370 ms 档约 65%，`slot_peak=3`。QoS1 约 5.9 条/s，三槽在 370 ms 往返下上限约 8.1 条/s，利用率约 73%；对端往返再变慢（例如 >500 ms）就会成为新瓶颈。现场测得的 250–370 ms 含 AT 轮询等待，透传下的真实往返未知。

**结论的写法**（请 Codex 以后沿用）：容量判据用“逐流交付/输入、丢弃、顶替、迟到、窗口末队列趋势”，不要拿单个批/s 数字对门槛。

## 3. 透传实现的审查发现

**符合预期的部分**
- 严格的下行帧检查：无订阅时只接受 CONNACK(0x20)、PUBACK(0x40)、PINGRESP(0xD0) 及其固定长度；`CLOSED`、`WIFI DISCONNECT`、`ready` 混入会被当作非法头立即终止会话。
- `+++` 防护：任何业务写入出现三连 `+`（含跨写）整段拒绝。PI 核对了载荷格式：`mp_json` 只输出数字、`-`、`.`、`,` 和固定文本，**业务数据里没有 `+`**，所以这个保护不会误伤；二进制的 MQTT 头出现 `2B 2B 2B` 的概率约 6e-8/位置，可忽略。
- 进入顺序：先 `CIPRECVMODE=0`、`CIPRECONNINTV=36000`（ESP 自动重连间隔 3600 s，避免旧 MQTT 会话悄悄接到新 SSL 连接上）、`CIPSTART="SSL"`、`CIPMODE=1`、裸 `AT+CIPSEND`，2 s 内要 `OK` 与 `>` 才交给 coreMQTT。
- 退出：冻结发送→TC→静默 ≥25 ms→`+++`（无 CRLF）→TC→静默 ≥1001 ms→`AT+CIPMODE?` 回读 1→`CIPMODE=0`→`CIPCLOSE`；任何未知则封住普通 AT，需人工恢复。
- 透传构建强制 `--no-audio`，只用于隔离 TLS 端口 28895。

**非阻塞的风险与建议**
- **R-1 `pass_recv` 只接受三种应答**：将来若恢复音频订阅（SUBACK、下行 PUBLISH），必须扩展，否则会被当作故障。这是正确的当前取舍，请在设计里写明。
- **R-2 断链感知依赖 keepalive/PUBACK 期限**：没有 `SEND FAIL`。需要在台架里**实测**检测时间（见 §5 的 F1）。
- **R-3 重连代价**：退出透传至少 ≈1.0 s + 恢复步骤，重连时间需要实测。
- **R-4 MCU→ESP 的大块写入在 230400 下尚无实板证据**（R5 只测了 ESP→STM32 方向）。这是台架必须验的项目（带校验）。
- **R-5 台架里 CAN 空闲，`service()` 开销被低估**；真实带 CAN 的开销要等五板阶段。

## 4. 下一轮离线任务

### WP-X：C 单板传输台架镜像（`--transport-bench`，是 §5 批次卡的前提）
目的：在**不需要五板、不涉及 CAN** 的情况下，用真实 ESP/Wi-Fi/TLS 测量普通与透传两种传输。
1. 新构建目标 `--transport-bench`（只能与 `--unified --five-appliance --no-audio` 组合；**不得**与 `--field01` 的 START 路径混用）。
2. **合成源**：把 P3 夹具里的生产者（同样的流、速率、批大小、`MOCK/synthetic=true` 标记、确定性内容）搬进固件，通过**真实的** Router、`mp_json`、coreMQTT、传输适配层发布。每帧内容可由 `seq` 确定性复算，便于对端校验。**必须标注 MOCK，不得冒充 LIVE。**
3. 控制台命令（单次、`DISARMED` 阶段上电 45 s 内受理，缓冲 ≤15 字符）：`BENCH N115`、`BENCH N230`、`BENCH P115`、`BENCH P230`（N=普通模式，P=透传；115/230=波特率）。一个镜像、一次启动一个命令；与 PRE 一样有一次性与脏锁。
4. 窗口：入网/授时/TLS（沿用 FIELD01 的流程与门禁）→ 以合成源持续发布 **120 s** → 排空 → 停止；每秒输出 `B5 DIAG`（含 DWT 计数、队列、QoS1 槽位、drop/replace/late）。
5. 对端校验器（Python，放在 Broker 侧或 VPS）：按 `seq` 检查连续性、逐帧重算内容、记录到达时间、QoS1 的 PUBACK 往返；输出每流 交付/输入、最大间隔、校验错误数。
6. **不动**：START/KEY 现有语义、sector3、Options、ESP 固件、`AT+UART_DEF`。
7. Host 测试：生产者确定性、命令状态机、一次性与脏锁、与现有 17 组回归不冲突；报告 Windows 构建 Flash/SRAM（预计 <55 KB）与 VPS 位级一致回执。

### 5.4 PI 预先约定的判据（不得事后改）
| 观测 | 含义 |
|---|---|
| B1 的 交付/输入 ≈ 现场（波形约 79%，丢弃/顶替明显） | P3 的 42 ms 档标定成立 |
| B1 明显更好 | P3 标定偏悲观，需要重标定，容量缺口比想象的小 |
| B2 校验错误 > 0 | 230400 的 MCU→ESP 大块写入不安全；生产不得启用 230400 |
| B3/B4：每流 交付/输入 ≥ 99%，丢弃=0、顶替=0、迟到=0，窗口末队列不增长 | 透传在 C 单板上**跟得上** |
| B3/B4 出现 `PASS_FAULT/UNKNOWN` 或非法帧 | 记录原因；停止透传路线的生产化 |
| F1 的断链检测时间 > MQTT 期限若干倍，或无法自动恢复 | 透传需要补一个主动探活机制 |
| DWT：`await_cyc/await_b`、`tx_cyc/tx_b`、`irq_cyc/irq_n` | 得到**真实**每字节开销，与 P3 的 0/30/60/120 µs 对照 |
