# R15 WP-AJ 离线余量扫点

在校准的 300 秒 Host 夹具中，115200 透传的最后一个稳定点为 **14.00 批/s**，**14.25 批/s** 开始持续顶替并有丢弃。以 10.5 批/s 为分母，稳定点相对输入的余量为 **33.3%**。以 14.00 批/s 为分母，未用份额为 **25.0%**。230400 的最后一个无顶替点为 **15.75 批/s**，16.00 出现顶替，16.25 出现持续积压和丢弃。以上是这组输入相位与 ACK 模型下的离线结果。

## 主扫点

稳定的定义为输入段内无实时顶替或丢弃，且快照不出现持续积压。完成速率按 C Host 的实时发送完成/PUBACK 计，扣除补传。槽满比例为按虚拟时间加权的近似值。最后在途及队列残留分别计入，300 秒模拟不包含现场收尾排空。

最先限制主模型的是 **三槽 QoS1 窗口**。115200 到 14.00 时满槽约 91%，TX 占约 78%。保留相同字节耗时，改为较快 ACK，16.00 档仍有 15.987 批/s，顶替和丢弃均为零。反过来，只把 TX 改为线速而保留校准 ACK，16.00 档仍有 266 次顶替、71 次丢弃。发送与服务竞争会降低余量，在主模型中它没有先于 QoS1 窗口形成限制。

若按 CAN 负载比例同时放大服务时间和每字节额外开销，115200 在 12.00 档仍无顶替或丢弃，14.00 档已出现 275 次顶替和 81 次丢弃，16.00 档实时队列满 24/24、满槽时间只剩约 2%。因此 33.3% 取决于固定服务开销模型。CAN 比例假设下只确认至少测试到 12.00，所对应的模型余量为 14.3%。实板的服务开销随帧率增长幅度尚未知。

## 复跑与待实板问题

运行 `python -X utf8 node-b/tools/five_appliance_p3.py --r15-scan --cc gcc --out <新目录>`。46 个 Host 场景覆盖主扫点、加速 ACK、线速 TX 与 CAN 比例三组对照。每个场景输出逐 30 秒队列快照、槽占用、分桶延迟和完整结果。

需要实板确认更高输入时的实际 CAN 与服务成本曲线、逐笔 PUBACK 和槽位高水位、负载相位、持续丢弃点及长窗口完整性。C 台架扫点和五板实板扫点均为 **NOT_RUN**。
