## 2. 对你的问题：DMA 可行，**不需要**暂停麦克风

- USART3_TX 的 DMA 请求在 DMA1 **Stream3 / Channel4**；INMP441 走 SPI3/I2S3 RX，用的是 DMA1 **Stream0 / Channel0**。两者是不同的流，**不冲突**。这与 Codex 的 WP-R 分配表一致，也与我对 RM0090 请求映射的理解一致（Codex 需在文档里补上 RM0090 表号，见 §5 WP-U 的 1）。
- 冲突只会出现在**将来把音频改到 SPI2/I2S2**（它们也映射到 Stream3）时。所以现在不需要为 DMA 关掉麦克风。
- 语音功能本身：PI 的建议是**保留代码、降级为可选**：
  - 容量验收和后续测量的构建**默认关闭音频**（P3 数据里 125 块音频会拖累约 0.5 批/s）；
  - 不删除麦克风驱动，因为 P2 的语音规则可能写进了合同验收，删除前请先确认合同条款；
  - 你决定“这个功能不要了”的话，删除也很简单，但那是一个**产品决定**，不是技术必须。
- 另外要说明：**DMA 对容量缺口的帮助有限**（见 §3）。

## 3. 本轮最重要的结论：在 AT 普通模式下，容量缺口无解

P3 的 22 组扫描（Codex 回执）：

| 额外 µs/字节 | 115200 · 42 ms | 230400 · 42 ms |
|---:|---:|---:|
| 0 | 8.047 | **9.884** |
| 30 | 7.124 | 8.464 |
| 60 | 6.323 | 7.609 |
| 120 | 5.230 | 6.010 |

要求 **≥10.45 批/s**。

1. **42 ms 这一档才是现场标定的**：它在 115200 下得出 8.047，而现场实测是 8.07。22 ms 档在 115200 下是 9.338，**偏乐观**，不能用来做决策。
2. 即使 CPU 额外开销为 0，**230400 也只到 9.884，仍低于 10.45**；Codex 在已扫描范围内也没有找到达标的 CPU 阈值。
3. 所以：**波特率 + 降 CPU + DMA 的组合，在 AT 普通模式下都够不到目标。** 缺口来自每个包固定要付的 AT 往返，不是线速，也不是 CPU：
   P3 对 110 s 的分解（115200，22 ms 档）：CIPSEND 命令 1.9 s + 提示符 3.7 s + SEND OK 等待 24.6 s + 接收长度查询 15.8 s + 有效数据读 8.3 s = **约 54.5 s，占一半**；二进制写入本身 54.1 s。波特率只能缩短后一项。
4. 这也回答了你最初的问题：**换 RTOS 不会改善这件事，DMA 也只能改善“写二进制”那一项**。

## 4. 结构性方案：ESP-AT 透传模式（`AT+CIPMODE=1`）

### 4.1 依据（来自仓库内手册 `ESP-AT-ESP8266-v2.3.0.0.pdf`，PI 已读）
- `AT+CIPMODE=1`：“Wi-Fi Passthrough Receiving Mode … can only be enabled in TCP single connection mode, UDP …, or **SSL single connection mode**”（PDF 第 102 页，印刷页 98）。本项目已是单连接。
- 进入：`AT+CIPSEND`（无参数）→ 回 `OK` 和 `>` → 此后 UART 收到的数据**直接透传给服务器**；服务器发来的数据**直接出现在 UART 上**，没有 `+IPD`、没有 `CIPRECVLEN` 查询。
- ESP8266 一次最多接收 2048 B、发送 1460 B；收到的数据若不足一次发送上限，**20 ms 内**发出（PDF 第 95 页）。
- 退出：只含 `+++` 的数据包；退出后**至少等 1 秒**才能发下一条 AT 命令；`AT+CIPSEND` 可再次进入。

### 4.2 为什么它能解掉缺口
透传模式下每个 MQTT 包**不再有**：CIPSEND 命令、`>` 提示符、`SEND OK` 等待、`CIPRECVLEN` 查询、`CIPRECVDATA` 读取。按 P3 的 110 s 分解，只剩二进制写入（54.1 s）和少量空闲（1.5 s）：

| 速率 | 上界估算（**未验证**） |
|---|---|
| 115200 | 约 18 批/s |
| 230400 | 约 36 批/s |

这是**上界**：假设原始流的成本只有字节写入加少量空闲、MQTT/ACK 处理可忽略，也没有计入逐字节 CPU 开销。即使上界打对折，230400 下仍有约 18 批/s，远高于 10.45；115200 下对折后约 9，不够。**因此透传方案要和 230400 合用。**

### 4.3 风险与待验证项（PI 的清单，不是结论）
1. **链路断开的感知变弱**：没有 `SEND FAIL`/`SEND OK`；`CLOSED`、`WIFI DISCONNECT` 这类提示在透传里**可能直接混进数据流**，把 MQTT 帧结构搞坏。需要：以 MQTT 的 keepalive、PUBACK 超时作为主要健康判据（符合项目规则“SEND OK≠服务器接收，PUBACK 才是证据”）；帧错误即判链路故障。
2. **重连变慢**：退出透传要 `+++` 加 ≥1 s 静默才能发 AT；需要给出重连时间上限。
3. **AT 级诊断在流传输期间不可用**（不能查 `CWJAP?`）；`B5 DIAG` 的 AT 阶段计数要重新定义。
4. **MCU→ESP 方向的大块写入在 230400 下没有实测过**。R5 的 PRE 压测只覆盖了 **ESP→STM32** 方向（`GMR` 回复）。ESP8266 的 UART 没有硬件流控引出，一次 564 B 的 MQTT 包在 230400 下约 24 ms 灌进去，而 ESP 做 TLS 加密也要时间；**有丢字节风险**，必须带完整性校验地实测。
5. **ESP-AT 是 `2.3.0.0-dev` 开发构建**，手册行为需要实测确认（尤其 SSL 与透传同时使用、`+++` 的时序）。
6. `AT+CIPMODE` 不保存到 Flash，符合“只用易失配置”的边界。

### 4.4 若透传不可行的备选（按收益排序，均在 AT 普通模式下）
被动模式 `+IPD` 提示替代空查询（约省 7 s/110 s）、机会式两包合发、DMA 发送与逐字节瘦身。**P3 显示它们叠加后也很难稳定越过 10.45**，所以只作为透传失败后的退路。

## 5. 下一轮任务（全部离线，不上板）

### WP-T0：透传传输的设计与 Host 验证（核心）
1. **设计文档**：状态机（进入/稳定/退出/重连）、与现有单 AT/coreMQTT 所有者的关系、MQTT 适配层改动点（`esp_mqtt_send`/`esp_mqtt_recv` 在透传下的语义）、`CLOSED`/`WIFI DISCONNECT` 混入数据流的检测与处置、`+++` 的时序、重连时间预算、与音频上行（同一 MQTT 流）的关系、PUBACK 与 `SEND OK` 语义的重新表述。
2. **Host 模拟 ESP 的透传行为**：进入 `OK`+`>`；20 ms 合并发送；2048/1460 B 分片；服务器数据直出；`CLOSED` 混入；`+++` 退出与 1 s 静默；断链后的各种表现。
3. **扩展 P3 夹具**加入“透传”模式，参数化：线速（115200/230400）、每字节额外 CPU µs（0/30/60/120）、PUBACK 往返（250/370 ms，现场值）、QoS1 在途上限 3，输出批/s、波形完整性、PUBACK 窗口是否成为新瓶颈。**用 42 ms 档标定普通模式，作为同一夹具里的对照。**
4. 报告 Windows 构建的 Flash/SRAM 预算（当前默认 58,048 B，余 7,488 B；生产协商 +1,076 B；插桩 +616 B）。
5. 默认构建行为不变，新模式在编译开关之下。

### WP-U：DMA 与逐字节优化的补充
1. WP-R 的 DMA 分配表补上 RM0090 的表号/页码引用，并加上 USART3_RX 的 Stream1/Channel4 备选。
2. 逐字节优化清单里按“收益/风险”排序，给出一份**不依赖 DMA 的最小改动**（锁存 `+CIPRECVDATA:` 行类型、减少每字节的 `platform_poll`），并说明它们在**透传**下是否仍然有价值（透传下接收是裸字节流，`reply_byte` 不再逐字节解析）。
3. **只出文档**，不实施 DMA。
