## 3. 发现

### N-07（事实，也是 U-02 的首个实测）`AT+UART_CUR?` = `115273,8,1,0,1`，冷启动复现
- 两次（含一次全新上电）读数相同，说明这是模块**自带的存储配置**，不是我们设置的；`flow=1` 在 ESP-AT 里表示**只开 RTS**。
- 115273 与 PI 在 R2 N-06 的假设吻合：ESP 的 UART 时钟 80 MHz、整数分频，`80e6/round(80e6/115200)=115273.8`。**V-03 因此由实测关闭**；230400 与 500000 的 ESP 侧估算（230548、500000）沿用。
- 本批 `RESTORE`、`STRESS` 没有数据不是 ESP 的问题。

### N-08（固件缺陷，需修）判定条件过严，并且把“门控不符”误报成“恢复失败”
依据 `gateway/mqtt/src/field01_preflight.inc`：
1. `pre_uart_matches()` 要求 `parity==0` **且 `flow==0`**。模块实际 `flow=1`，所以 S1 的 `initial_valid` 为假，直接 `NEGOTIATE=MISMATCH`。
2. 没有改过速率的路径上，`PRE RESTORE` 也走同一个谓词（`pre_confirm()`→`pre_uart_matches()`），因此**什么都没改**也报 `RESTORE=FAIL`、`END reason=NEED_POWER_CYCLE`。这把一次只读查询判成“必须断电”，是误导。
3. 结果：R3 §5.3 要求的“S1 115200 下 50 次 GMR 基线”没有取得。
4. **PI 的责任**：R3 §5.3 的门控“`UART_CUR` 为 115200/8/1/0/0”是我基于“默认无流控”的假设写的，现实不符。该门控作废，用 §4 WP-J 的新规则替换。

### N-09（回执缺口）三处未对上，需要解释
1. **“逐字节一致”与回执矛盾**：Codex 对话里说 sector0/4 与归档逐字节一致；回执里 `stock_overlay_tail_bytes_differed_from_archive: 1519`，且 `verified_against_archived_full_except_authorized_sector3: true`。请给出这 1,519 B 的地址范围、实际值（是否为 0xFF）、归档里对应字节的值，以及为什么不同。若只是 sector4 在原应用长度（56,072 B）之后的残留被擦成 0xFF，请明说；若落在应用本体、sector3 或 Options 内，则是新问题。
2. **上电次数**：S0 回执写 `ledger_recorded_power_sessions: 2`，最终回执写 `recorded_power_sessions: 6` 与 `power_sessions_including_unexpected_supply: EXACT_TOTAL_UNKNOWN`。PI 按时间线数得 POWER_SESSION 6 次，外加 S0 期间 J-Link 反向供电（LED 亮）的异常一次，共 7 次，未超镜像 1 的 8 次上限，但“精确总数未知”不能是最终口径。请列出每一次上电：时间、供电路径（J5 / USB_UART / J-Link）、用途。
3. **原应用启动未验证**（`original_app_boot: NOT_RUN`）：回退目标是否真的能启动，目前没有证据。

### N-10 Wi-Fi 历史失败的根因仍然未知
- 新配置下入网 2.6 s、一次成功；Codex 说原热点已不可用，历史 `GW FAIL WIFI` 无法复现。
- PI 的判断：**最可能**是“sector3 里存的热点与现场实际热点不一致”（U-06 已证实两套配置字段不同；R3 的 S1 预检也发现操作员热点与 sector3 不一致），但这是**推断，不是证据**；超时（H2）无法排除。PI-02 的“工具部分”（子码输出、PRE 诊断）已完成，“根因”保持 UNKNOWN，不得写成已定位。
- sector3 的这次写入是负责人单独授权的对象，**不在 R3 批次内**，PI 只记录；它把此前的配置覆盖了，回退也保留了这份新配置（`wifi_sector3_preserved: true`）。

### N-11 供电路径与 R3 的设想不同
- R3 假设“USB_UART 给 C 供电”。实际 S0 起：**J5 供电**，USB_UART 仅作日志，J-Link 只用于编程；J-Link 在 USB_UART 断开后仍能给 C 反向供电（LED 亮），Codex 为此中止了目标操作，处置正确。
- 此后的“已断电”口径：负责人确认 J5 关、USB_UART/J-Link 断开、C 的电源 LED 熄灭。

## 4. 下一轮任务

### WP-J：镜像 2（固件，R3 §5.5 第 3 条已预授权，无需另批）

规则变化（均针对 `field01_preflight.inc`，并同步 Host 夹具与主机脚本）：
1. **门控谓词**：`data==8`、`stop==1`、`parity==0`、波特率在 2% 内；`flow` 接受 **0 或 1**（只开 RTS，不会拖住 STM32 的发送）；`flow==2` 或 `3`（开了 CTS）判 `MISMATCH`，因为该模块 C 侧没有 CTS 引出，可能卡死发送。
2. **只改一个变量**：切速的 setter 使用**回读到的 flow 值**（`AT+UART_CUR=<baud>,8,1,0,<flow>`），恢复也用同一个 flow；确认条件是“baud 在 2% 内且 flow 与初始读数相同”。这样候选速率下的差异只来自波特率。
3. **无改动路径**：目标为 115200 且 `AT` 同步、初始读数通过上述门控时，`NEGOTIATE=OK`，直接做 **115200 下 50 次 GMR 基线**，`RESTORE=OK`，**不发任何 setter**。
4. **区分“门控不符”与“恢复失败”**：门控不符时 `END` 的 `reason` 用新枚举 `UART_GATE`，不得用 `NEED_POWER_CYCLE`；只有“改过速率且确实恢复失败”才是 `NEED_POWER_CYCLE`。`PRE_DIRTY` 也只在后者置位。
5. **切速诊断**（R3 §5.5 第 2 条）：切速尝试之前输出 `PRE RETIME reason=<OK|TC|RX_NOT_QUIET|BRR|STOP|DEADLINE>`，让 `NO_SWITCH` 的原因可分。`ESP_UART_SWITCH_GUARD_MS` 保持 20 ms，不在本镜像里调。
6. **主机脚本** `field01_preflight.py` 同步：`reason` 增加 `UART_GATE`，增加 `RETIME` 行的完整行匹配，并更新 `complete()` 里与 `RESTORE`/`END` 的一致性检查。
7. **Host 夹具**至少新增：初始 `flow=1`（S1 通过且有 STRESS 基线）；`flow=1` 下的 230400 流程与 flow 保持；`flow=2/3`、`parity!=0` 被拒；无改动路径下不得出现 setter；门控不符不置 `PRE_DIRTY`；`RETIME` 各 reason。原有 14 个 C 用例与 34 个 Python 用例保持通过。
8. **预算与复现**：Windows 报告 sector4 占用与余量（当前候选 61,616 B、余 3,920 B）；VPS 用 Arm GNU 14.2 做位级交叉复现并给出三项 SHA。超过 sector4 或需要裁剪既有检查就先停下来提方案。
