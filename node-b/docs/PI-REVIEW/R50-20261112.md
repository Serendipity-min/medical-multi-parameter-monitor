## 2. 根因（PI 复核遗漏，承认）
- 时间：每次 1 MiB 整片读约 26 s。旧路径在写入前只读 2 遍整片，Halt 后只读 4 字节 RAM 状态；F2 正式路径（`b5_sector3_write.py` 中的 `S3_FORMAL_SOURCE_CHANGED_AFTER_HALT`）把 Halt 后的核验改成了第 3 遍整片读，写入前耗时因此到 78.6 s。
- 引擎在 `STAGE_VERIFY` 之后要求剩余时间 ≥110 s（提交 + 引擎最终整片读 + 调用方第二遍整片读 ≈ 53 s，另加余量），也就是说必须在 70 s 内到达这里，结果超出 8.6 s。
- **设计缺陷**：时间是否够用，在擦除和写入这些不可逆操作**之后**才判定，本应在擦除之前判定。合成测试的 IO 没有耗时模型，所以测试没有暴露这个问题。R47 复核 F2 时，PI 把"Halt 后整片复核"记为优点，没有核算时间预算，是 PI 的遗漏。
- 现场弹窗写的是"达到 180 s"，与原生日志不符，属于监督器提示文案的问题。以原生记录为准。

## 3. 恢复方案（推荐：只补写提交字）
目标状态不变（正式 sector3 已提交）。现有工具和授权都不能从未提交态继续，需要离线补一条最小恢复路径，**只写 1 个字**：

**Codex 任务卡 F2c（离线；不上电、不连 J-Link）**
1. 写入器新增 `--formal-cloud --commit-resume` 模式，scope 为 `WP_AY0_FORMAL_SECTOR3_COMMIT_RESUME`，绑定同一正式包（manifest `3489afc1…`）、R49 停止回执的 SHA，以及新的批次卡与现场记录。
2. 准入：连接后双读整片，两次都必须等于 `expected-full-uncommitted`；Options 与 UID 等于备份；sector3 未提交记录的 CRC 正确，提交字为 `FFFFFFFF`。Halt 后**只复读 sector3（16 KiB）**，须与 Halt 前一致。理由：B5 应用在构建时由门禁保证不含 SPL 的 Flash 擦写入口（`build_arm.py:284` 检查 `FLASH_EraseSector`/`FLASH_ProgramWord` 符号），配置也只存放在 sector3；Halt 前已双读整片，Halt 后复读 sector3 足以排除这段时间内的漂移。
3. 写入：不擦除，不写数据字；解锁后只编程 `0x0800C014 = 0x54494D43` 这一个字，等待就绪，再锁回 CR、恢复 ACR。
4. 写后双读整片，两次都必须等于 `expected-full-committed`（`1808eebf…`）；Options 与身份不变；保持 Halt，不执行 Reset 或 Go。
5. **时间预算前置**：在任何 NVM 写入之前，按实测速率（26.5 s/MiB，加 20% 余量）计算剩余的全部步骤，不够就在写入前停止。主写入路径同样改为在擦除之前判定，并把 Halt 后的整片读改为只读 sector3；这一改动用于以后的批次，本次恢复不使用主路径。
6. 测试：IO 夹具带耗时模型（按回执的 26 s/MiB）。① 恢复路径在 180 s 内完成，并留有余量；② 用 R49 实测的时间序列重放主路径，必须**在擦除前**停止；③ 起始状态不是未提交态（已提交、被擦空、数据被改动）时，都必须零写入停止。定向 pytest 全部通过，并给出新的工具 SHA。
7. 修正监督器的提示文案，按实际停止原因显示。

**备选（不推荐）**：在未提交态的基础上重新擦除，再走完整写入。这需要新的打包输入，写入量也大得多。另一个选项是恢复隔离配置，但我们本来就没有 sector3 回退工具（R47 §6），而且隔离账号已经删除，恢复了也没有意义。
