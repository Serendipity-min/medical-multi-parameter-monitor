## 3. 次要分析（非预注册，不改判定；`results/r128_l1_secondary.txt`）

### 3.1 15:14:52 断链：PUBACK 停滞，触发既定的恢复流程

C 串口时间线：
1. 最后一个 PUBACK 的延迟为 1,599 ms；此后 `q1_puback` 停在 18,700，不再增加。
2. QoS1 事务 5 s 超时，C 执行 `TXEXIT`，退出透传。
3. 依次重新联网：`PASS_ESCAPE_SENT` → `PASS_REENTRY_BACKOFF` → Wi-Fi（RSSI −50，信号良好）→ SNTP 新鲜样本（RTT 121 ms）→ CA/主机名校验 → TLS → `MQTT_CONNECTED` → `PASS_REENTRY_OK`。
4. 约 13 s 恢复。

这段时间里，本地链路的各项计数都正常：
- UART 错误停在冷启动基线 223；
- 短写 0，TXE 超时 0；
- CAN 发送失败 0、溢出 0。

**结论**：断链的触发点是 PUBACK 停滞，也就是 Broker 在 5 s 内没有回确认。C 的本地串口和 CAN 都正常，恢复流程按设计完成。PUBACK 为什么停滞（ESP、无线、公网或 Broker 侧）仍为 UNKNOWN。R125 那两次掉线没有串口日志，不能断定是同一原因。

### 3.2 G3 体温覆盖不足：CAN 段二上，D 的标量帧少收约 19%

C 串口里的 `FIVE RX` 计数，取窗口首末相减：

| 节点 | PDO3 标量 | PDO4 时间锚 | PDO5 标志 | PDO3/PDO5 | PDO4/PDO5 |
|---|---|---|---|---|---|
| A（段一） | 3,583 | 3,583 | 3,655 | 0.980 | 0.980 |
| E（段一） | 3,579 | 3,579 | 3,583 | 0.999 | 0.999 |
| B（段二） | 3,403 | 3,516 | 3,581 | 0.950 | 0.982 |
| **D（段二）** | **2,892** | **3,130** | 3,583 | **0.807** | **0.874** |

- 三类 PDO 的发送周期都是 1 s。D 的标志帧（PDO5）一个不少，标量帧（PDO3）却少了约 19%，时间锚帧（PDO4）少了约 13%，所以 C 能发出的 TEMP 帧随之减少。B 的 HR/RR 覆盖率 98%、L-17 中 B 的“2 s 空洞”，都对应 B 的 PDO3 少收约 5%。
- 段一的 A、E 基本没有这种情况。
- **推测（未证实）**：段二上，B 每秒发出 250 帧 ECG 和 50 帧 RESP，COB-ID 0x182、0x282，仲裁优先级高于 D 和 B 自己的标量帧（0x384、0x382）。B/D 共用 `node-b/canopen/CO_driver.c`，事件定时到期时发送缓冲可能还被占着，这一帧就被跳过了。要证实，需要在节点侧读取 CANopenNode 的发送溢出计数。冻结后不改固件，列为已知限制。
