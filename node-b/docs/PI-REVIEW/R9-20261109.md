## 2. 本轮最重要的发现

### N-12：C 单板上，**普通模式 115200 也跟得上输入**
- 输入 **10.51 批/s**（1,261 批 / 120 s，由 P3 的流定义生成，与现场“可证输入下界” 10.45 同量级）。
- 普通模式 115200：**1,261/1,261，丢弃 0、顶替 0、迟到 0**，C 侧实际 `SEND OK` 1,263 次（≈10.5/s），PUBACK p50 189 ms / p95 299 ms / 最大 439 ms。
- P3 夹具在同一输入下预测普通模式 115200 只交付约 79% 波形并丢 168 批。**实板否定了这个预测**：ESP、Wi-Fi、TLS 与 AT 往返本身**不是**现场 8.08 批/s 的瓶颈。
- 因此“必须换透传/230400 才能满足容量”这个前提**不成立**；R7 的透传方案不是必要条件，至少在 C 单板、CAN 空闲的条件下不是。

### N-13：DWT 实测的每字节开销（8 MHz）

| 模式 | 接收解析（周期/字节） | 发送（周期/字节） | PUBACK p50 / p95 / 最大 |
|---|---:|---:|---:|
| N115 | 504（≈63 µs） | 689（≈86 µs） | 189 / 299 / 439 ms |
| N230 | 505（≈63 µs） | 349（≈44 µs） | 137 / 281 / 375 ms |
| P115 | 67（≈8 µs，裸流） | 688 | 206 / 393 / 495 ms |
| P230 | 69（≈8.6 µs，裸流） | 349 | 241 / 368 / 575 ms |

- 发送周期/字节 = 字节线上时间（115200：86.8 µs；230400：43.4 µs）：**C 单板上发送是线速受限，CPU 在等 TXE**。
- 普通模式接收解析 **约 63 µs/字节**，**这与我在 R6 里从 GMR 数据反推的约 500 周期/字节吻合**，高于 230400 的字节时间（43 µs）；但接收量小（ACK、长度查询），不构成瓶颈。
- 裸流接收只需约 8 µs/字节，比解析路径便宜约 7.5 倍。
- 透传的 PUBACK 往返比普通模式**略慢**（p50 206/241 vs 189/137 ms；20 ms 的合并发送加 TLS 处理），这在 3 槽 QoS1 下要留意（R8 的 28 组扫点：3 槽在 500 ms 往返下开始丢）。

### N-14：现场 8.08 批/s 缺口现在**没有解释**，最可能在 C 的“业务服务”开销
台架与现场的差别只有这些：CAN 与采集、`service()`（每次 `platform_poll()` 都会调它）、五板节点流量、FIELD01 的诊断、音频代码（现场构建里存在但空闲）。台架里这些**都不存在或空闲**。

PI 的**推断（待验证）**：现场里 `platform_poll()` 在发送的每个字节前、接收的每次循环里都会调 `service()`，若每次要多花约 50–70 µs（处理 CAN 帧、采集、入队），发送路径每字节就会变成约 87+60 µs，吞吐掉到现场观察值附近。这与 P3 夹具“每字节额外 60 µs 时 115200 约 6–7 批/s”的扫点**量级一致**。如果成立：
- DMA 发送（不再每字节调 `service()`）、透传（接收裸流更便宜）、降低 `service()` 单次开销，都是**对症**的；
- 单纯提高波特率则**无益**（线时间缩短，但每字节的 `service()` 开销不变）。

**这个推断必须由五板窗口里的 `svc_cyc/svc_n` 来验证**，在那之前，不再推进任何“基于假设的优化”。

### N-15（需要修）230400 模式结束时 DIRTY，且可能影响生产的断线恢复
- 现象：N230、P230 结束时 `RESTORE=DIRTY`，需要冷断电；N115、P115 都 OK。230400 窗口内 UART 错误为 0。
- 现状没有恢复子码，Codex 也无法定位步骤。
- PI 读了 `production_restore()` 与台架的 `gateway_bench_restore()`，提出**假设 H-JUNK**：ESP 当前在 230400 时，`production_restore` 的第一支先把 STM32 切到 115200 去 `AT` 探测——这会向 ESP 发出**用错波特率的字节**，在 ESP 的 AT 解析缓冲里留下垃圾；随后切回 230400 再发 `AT`，回复可能是 `ERROR`（垃圾+`AT`），探测判失败，恢复链断掉。R5 的 PRE 没有这个问题，因为它的恢复是从**已知速率**直接发 setter，没有先探测错误速率。
- **为什么要紧**：生产里 ESP 常驻 230400，**只要 MCU 单独复位（看门狗、J-Link 复位、断电抖动）而 ESP 没断电**，`production_uart_setup()` 就是“先在 115200 上 `AT`（会对 230400 的 ESP 发垃圾）→失败→切 230400 再 `AT`”，和上面同一条路径。若同样被 `ERROR` 绊住，就会 `GW FAIL UART_NEGOTIATE` 并整个启动周期不联网（现在 WP-V 的降级只在“已证明恢复到 115200”时才联网）。这是**可用性问题**，需要在 230400 成为生产默认前解决。
- 这只是假设；需要先做 §4 的 WP-AA。

### N-16：回执的两点说明
- B2/B4 的 `empty`（空长度查询）计数是 4,447 / 24，B1/B3 是 953 / 3：N230 空查询变多只是主循环轮询更快，不表示更差。
- 现场主机墙钟与会话时间基准不一致，回执用固件 tick 与相对时钟，这个处理正确。

## 3. 对方案的重新排序

| 方案 | 现在的判断 |
|---|---|
| 230400 | 在 C 单板上**没有必要**；且有 N-15 的恢复风险。**暂不进入生产**，等 WP-AA 修完并有实证。 |
| 透传 | 在 C 单板上**没有必要**。仍可能有价值：接收裸流便宜 7.5 倍；但往返略慢、断链感知弱、实现复杂。**降为备选**，等五板数据再定。 |
| DMA 发送 | 取决于 N-14 的验证：若 `service()` 单次开销确实大，DMA 是**对症**方案。**先量，不先做。** |
| 降低 `service()` 单次开销 | 同样取决于 N-14；可能比 DMA 更便宜（例如按固定节拍处理 CAN，而不是每个字节都调一次）。 |
| 168 MHz | 一次性把所有 CPU 开销缩小 21 倍，但牵动 CAN/串口/音频；**只在 N-14 证明是 CPU 问题且软件办法不够时再启动**。 |
| FreeRTOS | 与之前结论一致，**不需要**。 |

## 4. 下一轮离线任务

### WP-AA：230400 恢复缺陷（对应 N-15）
1. 给恢复路径增加**步骤子码**（例如 `BENCH RESTORE step=<STATUS|CIPMODE|UART_CUR|RETIME115|PROBE115|RETIME230|PROBE230|SETTER|RETIME_BACK|PROBE_BACK>` 与 `GW UART_RESTORE step=…`），失败时输出，不泄露内容。
2. **在 Host 夹具里复现垃圾字节效应**：虚拟 ESP 在“错误波特率下收到的字节”之后，对随后的第一个 `AT` 回复 `ERROR`（并按 ESP 收到乱码字节的情形建模）。证明现状在该模型下失败，并覆盖“MCU 单独复位而 ESP 在 230400”的启动同步。
3. **修复**（最小）：
   - 恢复时**速率已知**（`platform_esp_uart_baud()==230400` 且同步良好）就**不要**先到 115200 探测，直接在 230400 发 setter 再切回；
   - 同步探测时，先发一个单独的空行 `\r\n`，**吸收一次 `ERROR`**，再发 `AT`；或把“收到 `ERROR`”当作“该速率下链路是活的，需要一次冲刷”的信号，最多重试一次；
   - 启动同步（MCU 单独复位）同理。
4. 默认 115200 构建的行为与 SHA 不得变化。

### WP-AB：五板窗口用的 FIELD01 兼容构建（对应 N-14 的验证）
现有的透传/230400/台架目标都没有走 FIELD01 的 START 路径。请提供：
1. **F-N115**：`--field01 --no-audio --transport-profile`（普通模式 115200，**基线复现**）。
2. **F-P230**：`--field01 --no-audio --esp-passthrough --esp-230400 --transport-profile`（透传 230400，候选）。若 `--field01` 与 `--esp-passthrough` 不能组合，请说明原因并给方案。
3. 在 `B5 DIAG` 里**增加 `svc_max_cyc`**（单次 `service()` 的最大周期）和 CAN 收帧计数，因为峰值比均值更能说明问题；保持与现有 DWT 计数同一输出格式。
4. 每个构建给出 Windows 的 sector4/SRAM 余量、与 VPS（Arm GNU 14.2）的位级一致回执；默认目标 SHA 不得变化。

### WP-AC：夹具的校准
把 P3 夹具里的“额外 CPU µs/字节”重新表达为“每次 `platform_poll()` 的 `service()` 开销”，并**拟合**：多大的 `service()` 单次开销能让**普通模式 115200**复现现场的 **8.07 批/s**（P1 的窗口数据）？再用这个值预测：230400、透传、DMA 发送各自的容量。**这个拟合值就是 N-14 要由 DWT 验证的预测。**
