## 2. 这批数据说明了什么

### 2.1 五板 W1 的实测（150 s，F-N115）

| 项 | 数值 | 对照 |
|---|---:|---|
| `service()` 调用 | 3,127,237 次（**约 20,850 次/s**） | 台架 `produce()` 在 CAN 空闲下约 74 周期/次 |
| `service()` CPU 占比 | **约 53%**（635 M / 1,200 M 周期） | — |
| 均值 / 单次最大 | **203 周期（25.4 µs）/ 53,340 周期（6.7 ms）** | |
| 发送 `tx_cyc/tx_b` | **937 周期/字节 = 117 µs/字节** | 台架 689 周期/字节 = **86 µs（= 线速）** |
| 平均包长 | 479 B（586,793 B / 1,225 包） | |
| CAN 收帧 | 约 **370 帧/s**（A 9,057 + B 46,577） | 台架 0 |

### 2.2 机理（PI 的推导，**非直接测量**，假设标注在内）

`service()` 里已经有一个 5 ms 节流（`B5_SERVICE_MS`）：每 5 ms 才做一次重活（`b4_gateway_tick`、`b4_hw_poll` 等），其余调用很快返回。设“快速返回”的调用约 70 周期（假设 40–100），则：

- 重活每次约 **14,000 周期 ≈ 1.7 ms**（范围 1.4–2.1 ms），占每 5 ms 的约 **35%**（27–43%）；峰值 6.7 ms；
- 发送是**轮询单字节**（F4 的 USART 只有一个数据寄存器，没有 FIFO），115200 下每字节 87 µs。每次重活阻塞 1.7 ms，串口就空转约 1.6 ms；
- 所以发送的有效速率只有线速的 **约 74%**（87 µs ÷ 117 µs），与实测一致。

这解释了 **TX 变慢**，但**不是全部缺口**。把发送补到线速，每包 TX 从 56 ms 降到 42 ms，每包总时间 122.7 → 108.4 ms，约 **9.2 批/s**，仍低于 10.44。**只靠 DMA 发送补不齐。** 另一半在普通模式每包固定要付的 AT 往返（命令、提示符、SEND OK、长度查询、数据读，P3 分解约 53 ms/包）。

**透传把这 53 ms 去掉**：每包只剩 TX（仍按 74% 线速约 56 ms）→ 约 **14 批/s（115200）**，高于 10.44；230400 下更高。这与 R8 的夹具结论方向一致，现在有了实测的 TX 速率支撑。

### 2.3 一个必须坦白的判读问题
R10 的判读表规定：W1 缺口复现且 `svc` 均值 **≥ 约 30 µs** → N-14 成立；“均值很小（≈台架水平）” → N-14 不成立。实测均值 **25.4 µs**，既低于我写的 30 µs 线，又是台架（约 9 µs）的近 3 倍，**落在我表里没写规则的区间**。我不改线，也不假装表里有规则。

PI 的裁定：**N-14 的机理成立，但我写的“均值”这个指标选错了**——真正说明问题的是**占空比与峰值**（服务占 CPU 约 53%，重活峰值 6.7 ms）以及 **TX 每字节 117 µs 对线速 87 µs**，不是均值。均值被 20,850 次/s 的快速返回稀释了。以后判读改用：①`svc` 占 CPU 比例；②`svc_max`；③`tx_cyc/tx_b` 对线速的比值。

### 3.1 PI 预先登记的预测（不得事后改）

| 指标 | 预测 | 若不符 |
|---|---|---|
| Broker 实收 / C 入队 | **≥ 99%**，实收速率 **≥ 10.0 批/s** | 若 <95% 且队列顶满：透传没有解决，重新规划 |
| 实时队列高水位 | **≤ 16/24**，无持续上升 | 顶满则容量仍不足 |
| 丢弃 / 顶替 | **0 / 0** | 出现即记录来源 |
| `tx_cyc/tx_b` | 约 **430–560 周期/字节**（≈54–70 µs；线速 43 µs ÷ 约 0.74 的有效率） | 若仍接近线速 ×1.3 以上，说明服务阻塞更严重 |
| `rxstep_cyc/rxstep_b` | 约 **60–120 周期/字节**（裸流；台架 69） | 远高于此说明接收路径仍被服务拖慢 |
| `svc` 占 CPU 比例 | 约 **35–55%**，`svc_max` 仍可达数 ms | 这是**服务没变**的预期；本窗不改服务 |
| QoS1 PUBACK | p50 约 200–300 ms（台架透传 206/241），最大 <600 ms | 若 >500 ms 常见，3 槽 QoS1 窗口会成为瓶颈（R8 扫点：500 ms 开始丢） |
| UART/CAN 错误 | **0** | 任何非零单独列为缺陷 |
| 非法帧 / `PASS_UNKNOWN` | **0** | 出现则透传路线停止生产化 |

**判读**
- 全部落在预测内：**透传是对症方案**。随后 W3 用 **F-P115**（透传、不改波特率）确认是否需要 230400；若 F-P115 也通过，**生产首选 115200 透传**（避开 230400 的恢复风险）。
- 达不到：先看 `tx_cyc/tx_b` 与 `svc` 占比，再决定转向 DMA 发送或缩短重活（见 §4）。
- 本窗只有 150 s，**不能**签“五板 300 s 完整性”或“容量 PASS”。

### 3.2 现场提醒（来自 W1 的教训）
1. **A 的 PPG 工装在 START 前确认连续有效，START 之后不要碰 A 的电源或复位。**（W1-A/B 都栽在这里。）
2. SNTP 取得有效 UTC 需要 12–24 s，不稳定；START 在新启动后 45 s 内发出，TLS 修复已给建链留出预算。
3. 其余沿用 R10 §6。
