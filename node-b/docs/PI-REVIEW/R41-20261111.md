## 2. 裁定
**窗口 3：STOP_TARGET（C 应用主动停机），预登记全部 NOT_RUN。** 未进入 ROM，无安全事件。

**根因（源码已证，Host 已复现；现场具体回包仍 UNKNOWN）**：两个缺陷叠加。
1. **触发器（取决于条件）**：冷启动建链在 `AT+CWMODE=1` 之后、加入热点之前核对旧 socket（`gateway_transport.c:1123–1127`）。`AT+CIPCLOSE` 无连接时返回 ERROR，转而查 `AT+CIPSTATUS`；`gateway_socket_absent()`（`:797`）只接受 `STATUS:2/4/5`。按 ESP-AT v2.3.0.0，`0/1` 表示 station 未初始化或尚未发起 Wi-Fi 连接，本来就不可能有 socket，却被判为"未确认"→ `gateway_network_close()` → `platform_passthrough_recover()` 硬复位 ESP（`platform.c:757`）。ESP 此时报哪个状态，取决于它上电后是否已自动开始连接热点，所以 R36 等以往冷启动能通过，本窗没有通过。
2. **锁停（几乎必然）**：ESP 复位后 ROM 用 74880 baud 输出启动日志，C 以 115200 接收，必然产生帧错误；`platform.c:741` 的注释也承认这一点。恢复函数只清活动错误，累计计数保留；随后 `pass_reconnect()`（`network_main.c:196–201`，WP-AW 加入）发现累计值偏离启动基线 → `GW PASS_LOCAL_FAULT` → 停止。**也就是说，只要发生一次 ESP 硬复位（包括运行中网络异常后的硬复位），WP-AW 镜像就会锁停。**

**是否偶发**：触发器 1 取决于条件（ESP 自动连接的状态与时序），所以出现频率不稳定，重新上电很可能会过；但缺陷 2 是确定性缺陷，只是以前没有走到硬复位分支。这不是随机故障，而是冻结清单里"PF6 硬复位路径未经硬件验证"这一项第一次在实板上暴露出来。

**PI 责任**：R35 §2 要求在重连路径保留"UART 错误增量即停止"，当时没有核对它与硬复位路径的交互。这是我的复核遗漏。

**附带收获（推断）**：冷启动基线约 220–222 个 UART 错误，与 ESP 上电时 ROM 在 74880 baud 输出启动日志的机理一致，可以把已知限制"冷启动 UART 约 220 错误的电气来源"从 UNKNOWN 改为"最可能是 ESP ROM 启动日志的波特率不匹配（推断，未经示波器验证）"。

## 3. WP-AX 修复合同（需负责人放行；放行前不生效）
基线 `2a8ee47`，最小改动，不做无关重构：
1. **复位后重设基线**：只在 `platform_passthrough_recover()` 确认 `ready` 且 `AT OK` 成功时，把 UART 错误基线重设为当时的累计值，并输出 `GW PASS_RESET_UART_REBASE before=<n> after=<n>`。复位未确认时不重设；其余路径上的 UART 增量仍然停止。
2. **socket 判定**：`gateway_socket_absent()` 接受 `STATUS:0/1/2/4/5` 且无 `+CIPSTATUS:` 行；`3` 及有连接行仍判为"存在"。
3. **补诊断**（不含敏感信息）：`PASS_BOOT_SOCKET_UNCONFIRMED`/`PASS_SOCKET_UNCONFIRMED` 时输出状态数字或"查询失败"；`PASS_LOCAL_FAULT` 时输出基线、累计值，以及 ORE/NE/FE/环溢出分项。
4. **测试**：把 Codex 的两个 Host 夹具转为 `test_unified.py` 回归，覆盖：`STATUS:0/1` 冷启动不触发硬复位；`STATUS:3` 仍触发；硬复位期间 1 次帧错误加 `ready`/`AT OK` 后不锁停；未确认复位不重设基线；稳态新增 UART 错误仍锁停。全量 `test_unified.py`、定向 pytest 通过；关闭新改动后仍与 WP-AW 冻结镜像逐位一致（如用编译开关），或在回执中说明差异。
5. **交付**：源码提交、boot/code/HEX 及 SHA-256、Flash 余量（sector4 当前余 7,444 B）、测试输出。我用 `/mmpm-rebuild-verify` 复核。

**之后**：新镜像需要实板验证，建议并入重做的窗口 3：安装 1（C sector0/4，`unified_install.py` 冷启动路径），其余按 R40 执行。硬复位重设基线这一项，只有现场自然触发时才有实板证据，否则仍为 Host 证据，回执如实写。冻结对象改为 WP-AX 镜像，重新冻结。

## 4. 备选（不推荐）
不改代码，按 R40 原卡直接重新冷启动。大概率能通过，但缺陷 2 会被带进冻结镜像：真人采集中途一旦发生硬复位，C 就会停止出口（不影响血压泵安全，泵由 E 控制）。另外，后续 AI 播报本来就要出新镜像，冻结迟早要重开。
