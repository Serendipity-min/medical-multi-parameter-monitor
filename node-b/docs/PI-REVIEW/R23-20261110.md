- 600 s 内 `enqueued`/本地发布/Broker 三列几乎相等（6,313/6,313/6,314），**这是第一次拿到固件侧的入队比**，结论为"稳态入口无损"。差的 1 条温度未闭合到单条身份，不影响判定。

- 把 PUBACK 预测线定在 800 是因为前一窗最大 763 ms，实际单窗最大值有 ±10% 的波动。811 ms 位于 p99 桶 1,000 ms 内，不构成问题，但我不改线。

## 3. 断网无损目标：差距的真正位置

Codex 的离线分析和实板对账给出三层缺口，**Router 缓存只是最内层**：

| 层 | 位置 | 实测（S1b-2 / WP-AR） | 机理 |
|---|---|---|---|
| ① B 未把波形送到 C | B 节点 | ECG/RESP 只收到名义波形约 45 s / 约 52.6 s；少约 673 / 约 740 批 | B 在 TIME 失效后从本地发送队列移除样本（`node-b/canopen/b_canopen_app.c`、`node_policy.h`） |
| ② C 拒收无时标批 | Router 之前 | `unstamped` 增 1,513 / 1,648 | UTC 锚断网后 30 s 失效，`emit()` 对零时间戳直接返回 |
| ③ Router 历史环 | Router | 补传 56–58 条，容量约 56 槽 | 56 槽历史环满则覆盖；状态批离线不进历史 |

- **时间锚的 30 s 保持期是主因。** 它同时造成①和②，量级为数百到上千批，比③大一个数量级。**只把 56 槽加大不会让断网 3 分钟无损。**
- 我复核了 Codex 的"近似核算"：S1b 跨断网快照 70 s，名义约 739 批，分层合并后约 721 批，余约 18；S1b-2 约 2,495 批→约 2,437 批，余约 58。余数小于 3%，与"网关状态未产生、边界"相容。**我接受这个主要差额的归因，不接受逐批闭合**（回执也未声称闭合）。
- 我在 R22 §1.3 里"补传+丢弃+顶替只覆盖 11–48%"的比较，**应作废**：顶替与补传、丢弃有重叠（顶替是转入历史），不能当互斥项相加。Codex 已指出，我承认这是我的算法错误。
- **PPG 缺口已定位：** 两窗各 12/15 个空档，≈2.08 s 周期网格，空档后第一批 1 点 INVALID，CAN 历史窗口显示 A 的质量位在波形点后 11–20 ms 先掉。结论：**源端质量门控及恢复边沿**，不是传输。27 个空档的证据一致；UNO 算法窗口和工装耦合仍 UNKNOWN。按点计缺口 6.3–6.8%，比我按批算的 2.2–2.7% 更大，我采用按点口径。

### 3.1 3 分钟无损在资源上是否可能（PI 估算，需 Codex 实测校正）
- 名义波形：ECG 250 Hz、RESP 50 Hz、PPG 50 Hz，约 350 点/s。若每点 2–3 B，180 s 约 126–190 KB。STM32F407 的 SRAM 共 192 KB，还要容纳现有缓冲，**全部波形无损 3 分钟在 RAM 里放不下**（需要 Codex 给出实际空闲 RAM 和每批字节数）。
- **Flash 边界不可动**（仅 C 的 sector0/4，不得用 sector3/Options），不能把 Flash 当缓存。
- 标量（SpO₂、PR、HR、RR、温度）加状态，约 6 条/s，180 s 约 1,100 条，每条几字节到数十字节，RAM 内可行。

因此无损目标必须**拆分**，这是负责人的需求决策，不是代码问题（§5）。

## 4. 恢复和第二次掉线（程序行为，不是人为因素）

| 现象 | 证据 | 状态 |
|---|---|---|
| 恢复慢：热点开启回执后 161.8 s 才有实时遥测 | 前 4 次 Wi-Fi 失败；Wi-Fi 恢复后 5 次新鲜 SNTP 拒绝（1 次收到 48 B 因模块时间与样本不一致，`reason=10`；4 次零回复，`reason=2`）；全部发生在 TLS/MQTT 之前 | **未达 ≤90 s。** 慢在 SNTP 重试，不在接入或透传；SNTP 零回复的外部原因 UNKNOWN |
| 第二次非人工掉线 | 第一次恢复后约 191 s，C 自己 `PASS_ESCAPE_SENT` 后重入，间隔 9.1 s；步骤码未给触发原因 | **UNKNOWN，需要原件追查**（见 §6.1） |
| RESP 载荷数组数值带前导零，JSON 解析失败 | 观察器一条 RESP 样本；来源 UNKNOWN | **潜在缺陷**（云端解析会失败），需追查 |
| 补传期间 PUBACK 最大升到 1,732 ms | 第一轮恢复段补传 56 条 | 记录；补传与实时同槽竞争 |

- **SNTP 问题与"时间锚保持"同源：** 若 C 保持时间锚（用本地单调钟外推），断网重连时可以不必等新鲜 SNTP 才进入 TLS/MQTT。但 TLS 证书校验是否需要新鲜时间要核对，我不假设。
- **第二次掉线是程序侧事件**，不是人为操作。它没有触发 LINK 停止、PF6 或软复位，R17 的退避逻辑在两次恢复里工作正常。

## 5. 需要负责人决定（无损目标的范围）

> 你在 Codex 回执里写的"约 3 分钟无损"是产品目标。我估算全部波形无损在 RAM 里放不下（§3.1），Flash 不能用。请选择：

1. **A. 标量与状态 3 分钟无损，波形尽力而为**（我推荐）：5 个标量加节点状态在 RAM 内保留 3 分钟；波形只保留尽可能多的最近数据，断网后超出部分允许缺口。
2. **B. 全部无损**：需要新增外部存储（硬件）或降低波形精度/抽取，需另议；Flash 边界不放宽。
3. **C. 云端允许缺口**：只修时间锚（把 30 s 保持期延长），不扩缓存，缺口仍然存在但缩小。

无论选哪个，**时间锚保持期**都值得先做：它是当前最大缺口（量级数百到上千批）的主因，也不依赖存储方案。
