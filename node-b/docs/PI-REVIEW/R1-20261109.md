## 2. 问题清单

### PI-01（P1）出口容量缺口：优先提高 ESP-AT 串口速率

**事实**
- 实测约 8.08 批/s，输入下界约 10.45 批/s，须提升 ≥29.3%（`CAPACITY-DECISION.md`）。
- Host 夹具（P3，22 ms SEND OK 档，约 110 s 虚拟时间）：二进制写入 54.1 s（49%），SEND OK 等待 24.6 s，接收长度查询 15.8 s（其中空查询 7.2 s），CIPSEND 命令 1.9 s，提示符 3.7 s，AT 未占用仅 1.5 s。
- 串口速率写死：`gateway/mqtt/src/platform.c:659`（USART3 `115200`）、`:373`（超时下界公式）、`:457`（`platform_send_reserve`）。
- C 内核实际运行在 HSE **8 MHz**、无 PLL（`gateway/dual_can/system_hse.c`，启动日志 `core_hz=8000000`）。USART3 接收为 RXNE 中断逐字节，无 DMA；仓库内未见硬件流控（CTS/RTS）使用。

**判断**
- 串口写入与命令线上时间约占一半，这部分与波特率成反比；SEND OK 的 24.6 s 主要是 ESP 内部时延，**不随波特率缩短**。
- PI 的算术估算（仅把“二进制写入+CIPSEND 命令”两项按波特率缩放，其余不变）：230400 ≈ 10.8 批/s（余量约 3%），460800 ≈ 13 批/s。**这是基于 P3 模型校准假设的估算，不是验收数据，不得写入结论表。**

**修复方案（离线候选，Windows 构建）**
1. 把 115200 参数化为单一常量（如 `ESP_UART_BAUD`），`:373`、`:457` 的公式都用它，不再各自写字面量。
2. 启动顺序：115200 同步 `AT` → 查询 `AT+UART_CUR?` 并按数字解析 → 发 `AT+UART_CUR=<baud>,8,1,0,0`（**只用 `_CUR`，断电不保留；禁止 `AT+UART_DEF`**）→ 收到 `OK` 后按手册要求的间隔切换 STM32 USART3 → 用 `AT` 重新同步。
3. 重同步失败的有界回退：STM32 退回 115200 再试一次 `AT`；仍失败则报告并停止联网，不循环重试，不触及持久配置。ESP 复位后 `_CUR` 自动回到默认速率，须在恢复分析里写明。
4. BRR 精度：8 MHz 下用过采样 8（SPL V1.4.0 有 `USART_OverSampling8Cmd`）并在 Host 中计算各目标速率的实际误差，写入回执。
5. 候选档位 230400 与 460800 各出一个构建；921600 不进入本轮（8 MHz 下 RXNE 中断间隔约 10.8 µs ≈ 87 个周期，PI 判断余量不足，不作为候选）。
6. 增加阶段累计计时与分因计数（P3 已预算：Flash 2,048 B、SRAM 512 B），至少区分：CIPSEND 命令字节、提示符、二进制写入、SEND OK、接收长度查询（空/非空）、有效读、票据等待、AT 未占用；并导出 `platform_uart_errors_total` 的分项（帧/噪声/溢出）。

**验收（离线）**
- Host 夹具在参数化波特率下重跑 P3 同一输入，报告批/s、实时波形交付/输入、CRC 不一致、倒序/重复，波形缺口为 0 才可称“Host 容量改善”，仍不是实板 PASS。
- ARM 构建的 sector4 余量以**权威工具链**的结果为准（见 U-01）；超预算不得靠裁剪既有安全检查换取。

**不确定项**
- U-01 工具链口径：Windows 产物 sector4 57,596 B，VPS 重编 63,204 B（余 2,332 B），差 5.6 KB，原因未解释。预算以谁为准？
- U-02 `AT+UART_CUR?` 的实际返回值未归档（历史只有 OK）。ESP8266 1MB dev 构建对 230400/460800 的支持、手册给出的合法范围与切换后的最小间隔，PI 未能从已有资料确认。
- U-03 无硬件流控下 ESP→STM32 方向在 460800 的丢字节风险未知。
- U-04 USART3 与 CAN1/CAN2 RX、SysTick 的 NVIC 优先级及最大中断延迟未归档。
- U-05 SEND OK 的 24.6 s 在真实 TLS 链路中的占比未知（Host 为替身，参数 22/42 ms 是假设）。

### PI-02（P1）Wi-Fi 入网失败：失败子码未导出

**事实**
- `gateway/mqtt/src/gateway_transport.c:834-840` 用 `step("WIFI", ..., 30000)` 发 `AT+CWJAP`；失败只输出 `GW FAIL WIFI`，子码丢弃。
- 现场失败耗时约 15.1 s，与手册 `AT+CWJAP` 默认关联超时 15 s 吻合，但交接文档已明确**不能据此倒推子码**（1 超时 / 2 密码错误 / 3 找不到 AP / 4 连接失败）。
- `gateway/microphone/network_transport.c:21` 的 `report_open_failure` 已有解析 `+CWJAP:` 的写法，可参考。
- sector3 与历史成功窗（RAM 注入）的热点配置字段不同；实际手机热点当时使用哪套参数 UNKNOWN。

**修复方案**
1. 在失败路径、`secure_memzero(command)` 之后，从 `at_response()` 只提取 `+CWJAP:<n>` 的单个数字，输出 `GW FAIL WIFI code=<n>`（未找到则 `code=NONE`）。**绝不输出原始回复**：若模块回显开启，回复里可能含 SSID/口令。
2. 同时输出已有的 UART 错误计数，确认失败时线路是否健康。
3. 不改 sector3，不改热点凭据。

**验收（离线）**：Host 用 `+CWJAP:1/2/3/4`、无子码、超长回复、含回显的回复各一个夹具，证明只输出数字、不泄露字段、不越界。

**不确定项**
- U-06 sector3 配置与 RAM 注入配置的差异落在哪些字段？只需“字段名 + 是否相同 + 长度 + SHA-256 前 8 位”，不要明文。
- U-07 手机热点是否为 2.4 GHz（ESP8266 仅支持 2.4 GHz）、是否隐藏、是否设了兼容模式、手机是否会在无流量时休眠热点：只需 是/否/未知。
- U-08 历史成功窗的 `GW WIFI_SIGNAL channel=… rssi=…` 日志行。

### PI-04（P2）整 90 秒边界：Backend 与 AI 不一致

### PI-05（P3）2500 ms 让路阈值重复且比较符不一致

**事实（PI 纠正上次表述）**：2500 ms 是实时 5 s 期限的一半，作用是**让路阈值**（音频准入与补传准入），不是过期判断。
- `gateway/b5/egress.h:27`：`utc>f->timestamp && … > 2500u`
- `gateway/b5/egress.h:54`：`utc>=… && … >= 2500u`
- `gateway/storage/router.c:127`：`utc>=… && … >= 2500u`
- 另有字面量 `5000`：`router.c:163`。

三处语义相同，仅比较符差 1 ms，**不影响安全**，是重复常量与风格不一致。

**方案**：一个具名常量（如 `MP_REALTIME_YIELD_MS`，值 2500，注释说明“实时期限的一半”）和一个共享谓词，三处共用；同时把 `5000` 具名。不改变阈值与行为。

**不确定项**：U-11 Codex 需确认 `egress.h:27` 用 `>` 是否有意（例如 `utc==timestamp` 的时钟回拨处理）。若有意，在谓词里保留并注释。

### PI-09 FreeRTOS 决策：本轮不引入

理由（均来自已有证据或仓库代码）：
1. AT 未占用时间仅 1.5 s/110 s，调度间隙不是损失主体。
2. 主要损失是线上时间与 ESP 内部时延，RTOS 不能缩短。
3. sector4 余量 2,332 B（VPS 口径）/ 以 Windows 口径也只有数 KB，内核+任务栈难以进入；Flash 写入边界仅允许 sector0/4。
4. 内核 8 MHz，切换开销占比更高；多任务争用唯一 AT 所有者反而增加风险。
5. 复议条件：PI-01 的 460800 候选在逐事务计时下仍不达标，且计时显示存在可重叠的 CPU 等待。

**时钟说明**：8 MHz 内核是 CAN 时序相关的既有设计；把 C 提到 168 MHz 会牵动 CAN 分频、SysTick、USART BRR、音频，是独立的大改动，**本轮不做**，仅要求 Codex 回答 U-14。
