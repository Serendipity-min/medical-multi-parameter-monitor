# PI 审查 R12：W2 两次完整窗口裁定（F-P230 透传 230400）

**日期** 2026-11-09　**审查人** Claude（PI）　**执行人** Windows 上的 Codex
**被审对象** `codex/field01-preflight@ea510dc`
**承接** [R11](R11-20261109.md)。授权范围、停止条件沿用 R10；本文只裁定数据，不放行新的实板动作。

## 0. 范围（按负责人指示）

只分析**程序运行**得到的两次完整 150 s 窗口。首个 48 s 短窗（SOURCE 停止）和 SNTP 零回复那次属于意外中断，**本文不裁定其原因**，Codex 的相关解释既不背书也不否定。

| 简称 | 镜像 | 结果 |
|---|---|---|
| 窗 A | F-P230 `bb560b89`（R11 冻结） | 150 s 定时停止，`reason=10` |
| 窗 B | F-P230 `5745bb87`（含 SNTP 备用端点） | 150 s 定时停止，`reason=10` |

**窗 B 的镜像不是 R11 冻结的 SHA。** PI 核验：Arm GNU 14.2.1 在 VPS 重编，boot `30b70683`、code `5745bb87`（56,876 B）、hex `1c7aaae8`，与回执**逐位一致**。相对 `6f3e8d1` 的固件差异只有 `gateway_transport.c` 里 `field01_fresh_sntp()`，位于 T0 之前的启动路径；窗口内的发送、服务、入队路径没有改。因此 B 可当作 A 的独立重复，不是新变量。

## 2. 全窗未达的原因：收尾排空策略，不是容量

逐秒表（PI 自行重算）：

| | 0–139 s 到达 | 速率 | 第 141 s | 142–149 s |
|---|---:|---:|---:|---|
| 窗 A | 1,461 | 10.436 | 12 | 全 0 |
| 窗 B | 1,462 | 10.443 | 8 | 全 0 |

- 前 140 s：实收/入队约 **99.86%**，队列高水位 4–5/24，**0 丢弃 0 顶替**。两窗一致。
- 全窗缺口 A 81 批、B 85 批，等于 **约 8.2 s × 10.44 批/s**。
- 代码：`gateway/b5/network_main.c:703` `allow_new = b5_business_remaining() > B5_DRAIN_MS`，`B5_DRAIN_MS = 5000+2000+1000 = 8000 ms`。150 s 窗口在剩余 ≤8 s（T0+142 s）后**停止发布新任务**，CAN 仍在入队，队列在约 2 s 内顶满，随后丢弃/顶替。
- 到达在 T0+141.76 s / 141.90 s 之后归零，与 142 s 切点吻合。

**这是 PI 的错误：** 我写 R11 预测表时没有读 `allow_new`，把 150 s 全窗当成都在稳态发布。这个收尾段是既有设计，不该按稳态容量计分。

这仍是**推断**：代码路径、切点、数量、两次重复四项吻合，但 140–150 s 之间没有队列逐秒记录。

## 3. 机理确认（直接测量）

| | W1 F-N115（普通 115200） | W2 F-P230（透传 230400） |
|---|---:|---:|
| 发送 cyc/字节 | 937（117 µs） | 494（61.8 µs，线速 43.4 µs，有效率约 70%） |
| `svc` CPU | 约 53% | 约 54% |
| 工作段实收/入队 | 8.15 vs 10.44 批/s | **10.44 vs 10.45 批/s** |
| 队列 | 顶满，持续丢弃 | 4–5/24 |

- `svc` 占 CPU 没变，说明发送仍被服务抢占；R11 对“服务没变”的预测成立，有效率 0.70 对预测 0.74 也在范围内。
- 工作段补齐的来源是：去掉普通模式每包约 53 ms 的 AT 往返，加上线速翻倍。DMA 不是必要条件。
- 发送占用：W2 TX 约 658 KB/150 s，约 4.4 KB/s，占 230400 线速的 19%；TX 周期约占 27% CPU。

## 4. 本批没有证明的

1. **容量上限和余量。** 输入固定在约 10.44 批/s，队列没有增长，只能说明出口 ≥ 入口，余量未测。
2. **300 s 完整性。** FIELD01 窗口只有 150 s。
3. **115200 透传是否够用。** 未测（见 §5）。
4. **`svc_max` 21.21 ms**（窗 B）。CAN 无溢出，但原因 UNKNOWN，窗口是否含启动事件未区分。
5. **QoS1 连续槽位高水位**：UNKNOWN（C 没有该指标）。
6. **RESP、RR 的 VALID 为 0**：与传输无关，是此前已列的 ECG+RR 同窗有效性问题，状态不变。

## 5. 下一步

**结论：透传是对症方案，在 150 s 窗口的工作段已实测跟上入队；“容量 PASS”仍不可签。** 下一问题是 115200 透传能否替代 230400（避开 230400 的恢复风险）。

### 5.1 离线（Codex，不需新授权）
- **WP-AG：F-P115 构建。** 当前 `build_arm.py` 对 FIELD01 插桩组合要求 `esp_passthrough == esp_230400`，需放宽为允许“透传 + 115200”。要求：Host 测试覆盖冷启动、透传进入/退出、错误锁存、115200 保持；Windows 与 VPS 位级一致，回执给完整 SHA。**PI 会在 VPS 独立重编后才进入 W3。**
- **WP-AH：工作段口径落到工具。** 逐秒表附 `T0+140 s` 的队列快照（已有）并输出两栏：工作段（T0..T0+142 s）与全窗；收尾段只记录，不计入稳态预测。
- **WP-AD/AF：** 仍按 R11；加问一条：窗 B 的 21 ms `svc_max` 发生在窗口哪一段。

### 5.2 W3 预登记预测（F-P115，工作段口径；不得事后改）

收尾段（T0+142 s 之后）预期仍会出现丢弃，按 §2 说明，**不作失败判据**，但需要出现且与 W2 同形态。
