### 2.2 PI 的推断（**需要验证，见 WP-Q**）

一次 `AT+GMR` 约 190 B（命令 8 B + 回复约 181 B，**PI 按回复结构估算，Codex 请给出实际字节数**）：

| 速率 | 线上时间（估） | 实测 | 实测 − 线上 |
|---:|---:|---:|---:|
| 115200 | 16.4 ms | 18.44 ms | 2.0 ms |
| 230400 | 8.2 ms | 12.18 ms | 4.0 ms |
| 500000 | 3.8 ms | 11.90 ms | 8.1 ms |

线上时间越短，“线上之外”的时间越长，总耗时在 **约 12 ms 处触底**。这符合“**CPU 消费受限**”：C 的内核只有 8 MHz，接收端每字节的软件处理约 60 µs（约 500 个周期），比 230400 的线上字节时间（43 µs）还慢。旁证：RX 环的高水位随速率从 2 → 49 → 143，说明主循环消费不过来。

读源码能解释这个量级（`gateway/mqtt/src/platform.c`）：
- `await_reply()` 每次循环都调用 `platform_poll()`（进入业务回调），再取一个字节；
- `reply_byte()` 对**每个**长度 ≥13 的行字节都做一次 13 字节的 `memcmp(…,"+CIPRECVDATA:",13)`，其余字节还要写 `reply[len]=0`；
- 发送侧 `send_bytes()` 在**每个字节之前**也调用 `platform_poll()`，等待 TXE 时再反复调用。
- 在 PRE 镜像里 `service()` 被 `runtime_ready=false` 提前短路，所以 **PRE 看不到真实业务下的开销**：真实运行时每次 `platform_poll()` 都会进 CAN/采集/入队的完整回调，开销只会更大。

**这一推断对架构决策的含义**：提高波特率只在 CPU 不是瓶颈时才线性有效。230400 已经把 AT 小事务压到接近 CPU 下限；500000 几乎没有额外收益，还增加 CAN 溢出风险。

### 2.3 对容量缺口（需要 +29.3%）的更新估算

PI 之前的估算（230400 ≈ 10.8 批/s，500000 ≈ 13）建立在“二进制写入的耗时完全由线速决定”这个假设上，**现在不再成立**。保守重估（仍是估算，不得入结论表）：

| 做法 | 估算范围 | 依据 |
|---|---|---|
| 仅 230400，且发送字节循环不是 CPU 瓶颈 | 约 9.7–10.8 批/s | 下限用“只缩短线上时间”的算术，上限是 P3 夹具直接缩放 |
| 仅 230400，发送字节循环受 CPU 限制 | 接近 8.1 批/s，几乎无改善 | 与接收侧同一机制 |
| 230400 + 降低每字节 CPU 开销 + 去掉空查询 | 可能越过 10.45 批/s | 取决于 WP-Q 的实测 |

结论：**不能再单靠提速。必须先量出 CPU 花在哪。**

## 3. 架构问题的回答（你最初问的“优化现有架构还是引入 FreeRTOS”）

**结论：保持裸机，不引入 FreeRTOS；下一步是“降低每字节 CPU 开销”，必要时再评估把内核时钟提到 168 MHz。**

理由（均有证据）：
1. 瓶颈是 8 MHz 内核上的**逐字节软件开销**，而不是调度间隙（AT 未占用时间仅 1.5 s/110 s）。RTOS 的任务切换不减少逐字节开销，反而加开销。
2. sector4 余量只有 3,588 B（镜像 2），放不下内核和多任务栈。
3. 真正有效的是：
   - **A. 少做事**：`reply_byte` 里把 `+CIPRECVDATA:` 的判定改为只在 n==13 时判一次并记录状态，其余字节直通；接收时不要每个字节都调业务回调。
   - **B. 不占用 CPU 的发送**：发送缓冲用 DMA（USART3_TX）或中断驱动，不再“每字节一次轮询”。**注意 DMA 流资源可能与麦克风 I2S 的 DMA 冲突，需先出分配表。**
   - **C. 把内核提到 168 MHz**：一次性解决所有逐字节 CPU 瓶颈（约 21 倍余量），也让 500000 以上变得安全。代码里已经有 42 MHz、6×14 TQ 的 CAN 分支（U-14），但这是时钟/CAN/串口/音频一起改，**需要单独评估并完整重做 CAN 验证**，不能仓促。
4. FreeRTOS 在这三条路径里都不是必要条件。
