## 总线与时间

### D-01 用 CANopen（CANopenNode v4.0），不用自定义 CAN 帧
- **背景**：四个采集节点要把波形、数值、有效性、时间锚和在线状态送到网关，网关还要知道节点是否在线、是否重启过。
- **备选**：
  1. 自定义 CAN ID 和帧格式；
  2. CANopen。
- **选择**：CANopen。理由如下：
  - 心跳、NMT、TIME、EMCY、PDO 都有现成的标准语义，不必自己设计“在线”“重启”“时间同步”“故障上报”；
  - 对象字典（OD）把每个字节的含义集中写在一处，网关和节点按同一份 OD 编解码；
  - CANopenNode 是成熟的开源实现，只需移植驱动层（`CO_driver.c`）。
- **代价**：
  - 驱动要自己写，项目里多数 CAN 问题都出在这一层（P-15、P-16、P-17、P-20）；
  - 每个 PDO 最多 8 B，ECG 只能一样本一帧，250 帧/s。
- **何时重新考虑**：需要更高的波形速率或多通道时，可改 CAN FD；F407 不支持 CAN FD，要换芯片。

### D-02 两段总线，用 GT-246-4 拆成四个子段
- **背景**：
  - C 有 CAN1、CAN2 两个控制器。A、E 在段一，B、D 在段二，B 的 ECG 波形单独占段二的大部分流量。
  - 段内终端电阻并联后实测约 40 Ω，偏离标准 60 Ω。
- **选择**：在中间加 GCAN-GT-246-4 网桥，把两段拆成四个约 60 Ω 的子段（R68–R73，杜邦线冒烟 FAIL 后改双绞线验收）。
- **代价**：多一个设备和一跳转发；没有做差分波形测量和故障注入（L-08）。
- **注意**：网桥只是物理隔离，CANopen 语义不变，节点号和 COB-ID 都不改。

### D-03 时间统一：网关 SNTP → CANopen TIME → 节点锚
- **背景**：MQTT 载荷的 `timestamp` 必须是采集时刻的 UTC 毫秒。节点没有网络，屏幕上的软 RTC 不可信。
- **选择**：
  1. C 用 SNTP 粗授时，再取一个**新鲜**的 NTPv4 样本校验（RTT ≤1 s，originate 匹配，stratum 合法）；
  2. C 每 10 s 在两段上各广播一帧 TIME（0x100：当日毫秒 + 自 1984-01-01 起的天数）；
  3. 节点收到后记下“这一刻的 epoch 对应本地哪个 tick”，之后用本地 1 ms 时基外推（`node_policy.h`）；
  4. 节点 30 s 没收到 TIME，就撤销可信时间（epoch=0），只发不带时间的数据或不发。
- **代价**：断网后 SNTP 拿不到新鲜样本，就迟迟不能上线（P-23，最长 551–582 s）。
- **原则**：没有可信时间就不上线。时间错误的数据比晚到的数据更难发现。

## 网关

### D-04 ESP8266 SSL 透传 + STM32 上的 coreMQTT
- **背景**：源端约 10.45 批/s，逐包 AT 发送（每包 `CIPSEND`、等 SEND OK、查接收长度）只有约 8.07 批/s。
- **备选**：
  1. 提高串口波特率；
  2. 用 ESP 自带的 MQTT AT 命令；
  3. 在 STM32 上跑 LwIP + TLS；
  4. **SSL 透传**：ESP 只负责 Wi-Fi 和 TLS socket，MQTT 编解码放在 STM32。
- **选择**：4。
  - 主机模型显示，瓶颈是每包的 AT 交互次数（SEND OK 等待和长度查询合计约 37%），不是线速，所以方案 1 无效。
  - 透传后每包只剩线上传输时间，实测 10.458 批/s，零丢弃。
  - MQTT 用 coreMQTT v2.3.1：不做动态内存分配，只有编解码和会话状态，适合放在受限的 MCU 上。
- **代价**：
  - 透传模式下，ESP 的状态对 STM32 不透明。断链检测只能靠 MQTT 层（PUBACK、PINGRESP），退出透传要靠 `+++` 时序（P-22）。
  - 230400 透传候选收尾有 `RESTORE=DIRTY` 问题，未进入正式镜像，正式用 115200。
- **何时重新考虑**：需要更高吞吐或更可观测的网络栈时，换带原生 TCP/IP 的模组（如 ESP32 跑 AT over SPI），或换带以太网的 MCU。

### D-05 波形 QoS0，标量、状态和补传 QoS1
- **背景**：ECG 波形 250 Hz，丢一批只影响显示；标量（HR、SpO₂ 等）是判断依据，丢一条可能漏报。
- **选择**：
  - 实时波形 QoS0，发完即止；
  - 标量、状态、故障和全部补传 QoS1，在途 4 槽，每个事务 5 s 超时。
- **代价**：QoS1 在途槽满时要限流；PUBACK 停滞会触发超时和重连（P-22）。
- **注意**：QoS1 收到 PUBACK 只证明 Broker 收到，不等于后端和网页收到。端到端要分层计数核对（`AGENTS.md`：PUBACK ≠ 端到端实收）。

### D-06 断网保留只保标量和状态
- **背景**：C 的 SRAM 192 KiB（含 64 KiB CCM），装不下长时间的全波形。
- **选择**：
  - 标量和状态压缩为 28 B 一条，放在 CCM：标量 1,472 条、状态 736 条，约 240 s；
  - 波形尽力保留，补传时为实时数据让路；
  - 时间锚保持 610 s，短时断网期间的采样仍能打上可信时间。
- **验证**：断网约 203 s，标量全部到达，无重复，顺序正确。
- **代价**：断网时长加 SNTP 恢复时间超过 240 s，就会丢数据；大量积压排空约 1.83 条/s，未达目标（已接受）。

### D-07 网关 C 用 HSE 8 MHz
- **事实**：正式 C 构建用外部 8 MHz 晶振，不启用 PLL（`gateway/dual_can/system_hse.c`），四个采集节点是 168 MHz。
- **含义**：C 的所有调度预算（串口服务、CAN 接收、JSON 组包）都按 8 MHz 实测。不能凭 F407 的规格书按 168 MHz 估算 C 的性能。
- **为什么没提主频**：发送循环占 54% 的 CPU 周期，但主要是逐字节轮询等待串口发送，这段时间由线上传输时间决定，主频提高也省不下来。真正的改进是 USART3 改 DMA（项目书 14.2）。*（为什么最初不启用 PLL，现有记录中没有明确说明。）*

## 节点 B

### D-08 ADS 读帧在中断里，算法在主循环
- **背景**：主循环里读 ADS，屏幕刷新等任务会推迟读取，造成丢样（P-01）。
- **选择**：中断只读 9 B、打序号和时间戳、入 128 帧队列；滤波、峰检、R1 和屏幕都在主循环。
- **代价**：主循环停顿超过 512 ms，队列就会溢出；停顿超过 100 ms，等待上传的样本就会过期。所以主循环里不能有大块计算（P-08）。

### D-09 逐通道判有效，输出具体原因位
- **背景**：RESP 削顶曾连带 ECG 失效（P-04）；“无效”本身也不说明为什么。
- **选择**：ECG、RESP 各自维护滤波状态和有效性；输出 8 种原因位（预热、无周期、不稳定、过期、断段、削顶、工频、宽带噪声）。
- **价值**：现场一看屏上的原因码，就能区分是贴片问题、工频问题还是采集断段。R78–R81 专门做了屏上诊断串。

### D-10 呼吸率用 R1 谱峰法
- **背景**：时域谷—峰法 C2 在模拟器上很好；真人自然呼吸不规整，3 个间期 ±20% 很少满足，伪迹又可能凑出周期。
- **选择**：32 s 窗、2 s 步长，0.1–0.7 Hz 谱峰；六道门槛；三窗一致才出值。
- **依据**：R102 离线研究的门槛在跑数据之前写定：阳性覆盖 ≥80%、±1；阴性输出 0%；噪声 ≤1%。通过后才上板（R123）。
- **代价**：出值约 39 s，一次波动后约 37 s 才恢复（D-15）。

### D-11 R1 用 Goertzel 逐频点分摊
- **背景**：R1 首版每 2 s 集中计算，主循环停顿超过 100 ms，上传丢点升到 14–20%（P-08）。
- **选择**：Goertzel 每个频点独立计算，每处理一帧 ADS 数据只算一个频点，246 个频点约 1 s 算完。
- **为什么不用 FFT**：只需要 4096 点谱中的 246 个频点；FFT 必须整块计算，工作区约 32 KB，无法拆到每帧。
- **代价**：结果晚约 1 s 出来，对 32 s 窗来说可以忽略。

### D-12 R1 输入与上传同点、同量化
- **选择**：R1 取 `sequence%5==0` 的样本（50 Hz），按 CAN 上传的量化取整后再计算。
- **价值**：云端 MQTT 录制可以在 Python 里逐窗重放，结果与板上一致（R125：9,883 窗全部一致）。所有 RR 问题都能离线复现和回归，不必反复刷板、找人测试。
- **代价**：多一次乘除和取整，可以忽略。

### D-13 “有效的 0”在节点侧修
- **背景**：数值帧和标志帧分在两个 PDO，网关按到达顺序拼接，节点停顿时会拼出“RR=0、有效”（P-09）。
- **备选**：
  1. 合并成一个 PDO：要改 OD、节点和已冻结的网关；
  2. 网关侧等待配对：要改网关；
  3. **节点侧失效后数值保持 1.1 s**：只改 B 一个文件。
- **选择**：3。保持时间覆盖一个 1 s 定时周期，网关不会再看到“新 0 + 旧有效”。
- **代价**：失效后网页可能多显示约 1 s 的旧值，但标志已经无效，后端会按无效处理。

### D-14 波形有效与数值有效解耦（R125 修订 1）
- **背景**：波形有效位等于 HR/RR 有效性，数值一无效，网页波形就消失。负责人要求“波形一直显示”。
- **选择**：波形有效只看信号完整性：样本新鲜（≤100 ms）、有时间锚、本通道未削顶。
- **原则**：两种“有效”回答的是不同问题。波形有效说的是“这段信号是真实、连续的”，数值有效说的是“这个数可信”。

### D-15 R125 不缩短 RR 窗口
- **背景**：负责人指出，3 分钟测试里一次波动就可能让 RR 很久看不到。
- **研究**（`results/r125_rr_variants.txt`）：比较了 24 s、20 s 窗，3 窗改 2 窗，瞬变削峰，失效保持 16 s，谱质量门槛 0.40、0.35。
- **结果**：
  - 缩窗不提高覆盖，20 s 窗在无呼吸时误报 13.8；
  - 真人失效的主因是谱质量（呼吸不规整），不是单次波动；
  - 只有降门槛有效，但会误报。
- **选择**：R1 参数不变，负责人同意。
- **原则**：误报（无呼吸却显示呼吸率）比不出值更危险。

## 全局

### D-16 裸机协作式主循环；FreeRTOS 留到算法稳定之后
- **现状**：五块板都没有 RTOS。中断只做入队，主循环按节拍轮询各任务。
- **为什么暂不引入**：
  - 主要问题都不是调度器能解决的：出口瓶颈是 AT 交互次数（D-04）；D 丢帧是驱动的发送完成逻辑（P-20）；R1 停顿用分摊就解决了（D-11）。
  - 冻结期内引入 RTOS，等于重做全部时序验证。
- **以后引入的价值**：
  - B：R1 和屏幕刷新放低优先级任务，采集消费放高优先级任务，不再需要手工插 8 个 `FrameFeed` 协作点（`03` §7）；
  - C：网络、CAN 汇聚、语音分任务，配合 USART3 DMA，把逐字节轮询的 54% CPU 周期释放出来。
- **注意**：引入 RTOS 不能解决 D 的丢帧，也不能解决 CAN 速率问题（段二负载只有约 8%）。

### D-17 固件、配置和回退分开存放
- **选择**：
  - 引导、应用和正式配置（sector3）分区存放，升级只写引导和应用；
  - 配置写入先判断预算，最后写提交字（P-25）；
  - 构建逐位可复现：固定工具链和库，源码包用未压缩 tar，逐个成员对 Git blob；
  - 刷写前后整片读回，核对身份、选项字节和非目标扇区；
  - 每次刷写都指定回退点（B：R123 K3 或 C2；C：WP-AY0）。
- **未闭环**：B 的构建脚本有两个开关只在 Codex 本地（`09` 末表）。

### D-18 预注册判读
- **选择**：每张测试卡在采集前提交判读脚本和门槛；采集后只填现场时刻，不改判据。判读结果用 PASS / FAIL / NOT_PASS（已接受）/ NOT_EVALUATED / NOT_RUN / UNKNOWN 六种状态。
- **为什么**：先看数据再定门槛，任何结果都能“通过”。预注册让 FAIL 也有信息量，例如 R126 模拟器 FAIL 是因为网关掉线，不是算法。
- **代价**：偶尔会因门槛写得不合理而 FAIL（例如 R96 的一致率 85% 对 C2 基线也偏高）。处理方法是如实说明，在下一张卡里修正，不回头改旧判据。
- **例外处理**：门槛只在采集前用已有数据标定（例如 R127 G3 中 B 的 90%）。

### D-19 宁可无效，也不出错误的有效值
- 贯穿全项目的取舍：
  - R1 有六道门槛和三窗一致；
  - 失效原因要具体；
  - 没有可信时间不上线；
  - 补传（REPLAY）不覆盖当前值；
  - 合成数据（MOCK）不得冒充实时（LIVE）；
  - 后端严格校验：拒绝未知字段、NaN、时间超前和 seq 倒退。
- **验收指标**：都把“不出错误有效值”列为独立门槛，例如 R128 G5：ECG 段 RR 有效 0 帧，“有效的 0”为 0 帧。
