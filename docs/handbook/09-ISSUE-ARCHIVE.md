# 09 · 问题档案与排障速查

> 本篇收录项目中有代表性的问题。每条写清：现象、怎么发现、原因、处理、验证、教训和出处。
> 状态词：**已修复**、**已缓解**（有恢复机制，根因未关）、**OPEN**（已登记待查）、**UNKNOWN**（原因不明）、**已接受**（负责人接受的限制）、**非问题**（事后证实是操作或记录造成的）。
> 出处中的 Rnn 指 `node-b/docs/PI-REVIEW/` 下的同名记录。

## 0. 排障速查：看到现象先查哪里

| 现象 | 先查 | 常见原因 | 条目 |
|---|---|---|---|
| B 的 HR、RR 同时无效，电极没动 | B 诊断串里的 `discontinuities`、`queue_overflow`、`long_gap` | 主循环停顿 → ADS 队列溢出或中断间隔 >6 ms → 断段重来 | P-08 |
| RR 很久不出，HR 正常 | 原因位：谱质量、贴边、瞬变各占多少 | 呼吸不规整或低频漂移；任何一次波动都要约 37 s 才能恢复 | P-12 |
| 网页 HR/RR 出现“有效的 0” | 数值帧与标志帧的到达顺序 | 节点停顿使两个 PDO 交错（R125 已修） | P-09 |
| 网页 ECG 波形一段段消失 | B 波形标志 bit0/1 的定义 | R125 前波形标志绑定 HR 有效性（已修） | P-11 |
| 网页某路数据隔 2 s 缺一块 | 缺口间隔分布，是否恰为 2.00 s | B 的 R1 集中计算造成周期性停顿 | P-08 |
| 体温每分钟闪一下“过期” | C 串口 `FIVE RX` 里 D 的 PDO3/PDO5 比值 | D 定时帧缺失约 20% | P-20 |
| 真人 ECG 幅度很小、HR 时有时无 | 导联色标；RL 是否贴好；工频残留 | 色标接反；信噪比低；工频拍频 | P-06、P-07 |
| 取下 RL 后工频暴涨约 1000 倍 | — | 正常现象，RL 是共模驱动 | P-07 |
| 网关掉线十几秒后自己恢复 | C 串口里的 `q1_puback`、`TXEXIT`、`PASS_REENTRY` | PUBACK 停滞 → 退出透传 → 重连 | P-22 |
| 断网恢复后好几分钟才有数据 | C 串口 SNTP 零回复次数 | 新鲜 SNTP 样本拿不到 | P-23 |
| 冷启动时 UART 错误计数约 223 | — | 正常现象，ESP 上电输出被当成错误，只看基线之后的新增量 | P-24 |
| CAN 节点偶尔掉心跳 | 自动重传是否开启；终端电阻 | 仲裁失败后不重传；两段并联终端约 40 Ω | P-15、P-19 |
| CPU 停在系统 ROM（VTOR=0x1FFF0000） | **停**：不复位，保存证据 | 原因不明 | P-31 |
| MQTT 录制器异常退出 | 是否收到 `voice/broadcast` 二进制帧 | 录制器假定载荷都是 UTF-8 | P-28 |

## 1. 采集与算法

### P-01 主循环读 ADS 帧造成丢样〔已修复〕
- **现象**：屏幕刷新等任务推迟了 ADS1292R 的读取，帧被覆盖，样本丢失。
- **处理**：在 DRDY 中断里读完整的 9 B 帧，写入 128 帧队列，帧内带中断序号和时间戳；主循环再逐帧处理。之后又加了 R6 补偿，在 8 个 UI 刷新点之后插入 `FrameFeed`，及时排空队列。
- **验证**：限定窗口内 3,406 帧捕获与交付一致，错误计数为 0。
- **教训**：实时采集与耗时任务要分离；队列要带序号，消费端才能发现丢样。
- **出处**：项目书 13.3；`docs/closeout/01` §3.1。

### P-02 START 用 PA1 时出现异常帧间隔〔已修复〕
- **处理**：START 改到 PG15，异常消失。
- **注意**：“PA1 与板载网络共用”这一因果解释是推断。

### P-03 SPI 分频 /64、无回读〔已修复〕
- **处理**：改为 /128（约 656 kHz），每个寄存器写后回读，失败重试一次。8,412 帧完整。

### P-04 RESP 削顶连带 ECG 失效〔已修复〕
- **原因**：旧算法对两路共用一个有效资格。
- **处理**：BIO_V2 逐通道 `accept_input`，独立的原因位。
- **验证**：隔离用例 28/28。
- **教训**：多通道系统里，一路故障不能扩散成全部失效。

### P-05 RESP 增益 12 时削顶成方波〔已修复〕
- **原因**：解调输出含与基础阻抗成正比的直流分量（约 30 mV），×12 后约 360 mV，超过满量程 ±202 mV。
- **处理**：增益降到 4（CH1SET 0x40），这是手册 9.4 推荐的 3–4。

### P-06 导联色标接反〔已修复，R106/R107〕
- **现象**：真人胸前贴法下 QRS 主峰 86% 负向，幅度小，两次贴片相差 7 倍。厂家样例贴法（两踝、一腕）按项目理解应接近 0，实际却有约 250 µV。
- **怎么发现**：对照厂家资料。各例程注释为“红线 RL、黄线 LA、绿线 RA”，模拟器接线照片也是绿夹接 RA、红夹接 RL。而项目一直按“红=RA、绿=RL”贴，并且从未做过通断实测。
- **验证**：R106 模拟器换色，判据预先写定。按厂家色标时 QRS +352 µV、正向 ≥93%；取下红夹仍 60 bpm，取下绿夹输出全 0。另外，R93 自检里的“取下 RL”实际取下的是 RA。
- **处理**：之后所有真人测试一律按**绿=RA、黄=LA、红=RL**。R109 复测胸前 HR 明显改善，但仍未达门槛。
- **教训**：接线约定要实测，不能只凭设计解释。最基础的假设最该先验证。

### P-07 真人 HR 有效率低〔已接受〕
- **现象**：多轮真人 HR 有效率在 0–90% 之间，模拟器一直接近 100%。
- **排查顺序**：
  1. **硬件**（R93）：模拟器 60 bpm，带内 RMS 27.6 µV，50 Hz 残留 0.2 µV，HR 100%。晃线、拉夹后立即恢复。
  2. **信号质量**（R87–R94）：以 A 的 PPG 为时标，对 QRS 做集合平均，量出单拍信噪比只有 0.5–3.3。
  3. **工频**：R94 的工频残留以 40–60 s 周期在 4 到 277 µV 之间起伏，只有残留 ≤30 µV 的几秒里 HR 有效。推断是 250 SPS 下谐波折叠形成的拍频（未证实）。
  4. **算法**（R95 先写门槛，R96 出结果）：梳状滤波无效。Pan–Tompkins 提高了有效率，但与 PPG 脉率的一致率掉到 25–47%。包络自相关并联 C2 提高了覆盖，但导联断开时会报出错误数值。三者都没有过门槛。
- **结论**：瓶颈在信号源（贴片位置、个体差异、两电极、非屏蔽线、工频），不在算法。
- **最好结果**：志愿者丙，R125，HR 98.7%（154/156），与 PR 一致率 97.4%。
- **出处**：R97（原因汇总）、R96、R126；项目书 L-01。

### P-08 R1 首版集中计算使主循环停顿〔已修复，R125〕
- **现象**：R1 上板后上传丢点从 2–6.5% 升到 14–20%，相邻缺口间隔里有 38–42% 恰为 2.00 s（C2 时期只有 0–1.4%）。
- **原因**：每 2 s 一次性算完 246 个频点，主循环停顿超过 100 ms。等待上传的样本超过 100 ms 龄就被丢弃。
- **处理**：每帧只算一个频点。
- **验证**：主机计时，单个频点约占整窗计算的 0.4%。1 小时长测（R128）ECG 丢失 1.4–2.6%，没有 2 s 周期。
- **教训**：在裸机协作调度里，任何周期性大块计算都要拆开。用“缺口间隔分布”找周期性停顿非常有效。

### P-09 “有效的 0”〔已修复，R125〕
- **现象**：真人录制中，RR 由有效转无效的 8 次里有 7 次，网关发出了“RR=0、VALID”。
- **原因**：数值（TPDO3，1 s 定时）和标志（TPDO5，变化即发）分两个 PDO，网关用最近一次收到的标志去配数值。P-08 的停顿使到达顺序交错：失效那一刻，值为 0 的数值帧先到，配上了旧的“有效”标志。
- **处理**：B 失效后 1.1 s 内，数值帧继续发上一个有效值。只改 B，不改已冻结的网关和 OD。
- **验证**：R126、R128 中“有效的 0”为 0 帧（R128 G5）。
- **教训**：数值与有效性拆成两条消息时，必须考虑两条消息的到达顺序。

### P-10 ECG 模式下低频误报 RR〔已修复，R125〕
- **现象**：模拟器 ECG 模式（无呼吸），接夹后基线慢漂在 8.8–8.9 次/分处形成谱峰，输出了一帧 RR=9。
- **处理**：R1 下限 8 → 9.5 次/分。不取 10，因为 10 次/分落在 9.96 那一格。
- **边界**：这个下限是看过误报数据之后才定的，需要以后的数据检验（L-14）。

### P-11 数值无效时网页波形消失〔已修复，R125 修订 1〕
- **原因**：B 的波形有效位 bit0/1 直接等于 HR/RR 有效性；后端会清空非 VALID 批次的样本，网页于是不画波形。
- **处理**：bit0/1 改为只看信号完整性：样本新鲜、有时间锚、本通道未削顶。
- **验证**：主机断言两种语义；R125 模拟器门槛 5“波形 VALID ≥95%”通过；R128 为 99.9%/100%/100%。

### P-12 RR 出值慢、恢复慢〔已接受，设计限制〕
- **现象**：上电约 39 s 才出 RR；中途一次波动，RR 消失约 37 s。
- **原因**：32 s 窗 + 三窗一致 + 约 1 s 计算。详见 `03` §5.6。
- **研究**：R125 试过缩短窗、2 窗、削峰、保持 16 s、降低谱质量门槛，只有降门槛提高了覆盖，但会在无呼吸时误报，所以不改（`results/r125_rr_variants.txt`）。
- **出处**：项目书 L-16。

### P-13 RR 模式下零星 HR 有效〔UNKNOWN〕
- 偶见 0–6 个快照的 HR 有效值（如 43、66、88、146 bpm），来源未查明，不作为真人 HR 的证据（L-15）。

### P-14 SpO₂“没戴指夹就出数”〔非问题〕
- 负责人更正：R100 记录里“戴夹前已报 PR、SpO₂”，是戴上后没有及时口头报告，不是设备误报。之前“SpO₂ 缺少质量门控”的结论撤销。
- **教训**：现场时间线以设备数据为准，口头报告可能晚到。
- 另有一项独立的已知限制：部分 SpO₂ 有效读数超出 94–100% 的预设范围，没有参照仪器，不做精度判断（L-02）。

## 2. CAN 与节点

### P-15 仲裁失败后心跳丢失〔已修复〕
- **处理**：启用 bxCAN 自动重传（NART=DISABLE）；STOP 时有界地取消邮箱中的待发帧。
- **验证**：三窗 180/180。

### P-16 CAN 中断早于协议栈就绪〔已修复〕
- **处理**：推迟中断使能，到协议栈进入正常模式后再开。主机复现了“中断早到”的循环，并加了回归用例。

### P-17 同一 COB-ID 用多个邮箱，发送顺序乱、待发 PPG 被覆盖〔已修复〕
- **处理**：按请求先后顺序发送；待发槽未释放时，保留源端积压，不覆盖。B 的 `produce()` 里“缓冲占着就不发”也是同一原则。

### P-18 新样本年龄被算成约 49 天〔已修复〕
- **原因**：采样 tick 比当前时刻略新时，无符号减法回绕，得到约 2³² ms ≈ 49.7 天。
- **处理**：改用有符号 tick 差，采样时刻统一。
- **教训**：32 位毫秒时间差，凡是可能为负的地方都要用有符号比较。

### P-19 两段总线终端并联约 40 Ω〔已修复〕
- **处理**：用 GCAN-GT-246-4 把总线拆成四个约 60 Ω 的子段（R68–R73：杜邦线冒烟 FAIL → 双绞线正式验收）。
- **边界**：没有差分波形测量和故障注入，物理裕量未验证（L-08）。

### P-20 D 节点定时发送帧缺失约 20%〔OPEN〕
- **现象**（R127 一小时长测，C 串口 `FIVE RX` 计数）：

  | 节点 | PDO3/PDO5 | PDO4/PDO5 |
  |---|---|---|
  | A（段一） | 0.980 | 0.980 |
  | E（段一） | 0.999 | 0.999 |
  | B（段二） | 0.950 | 0.982 |
  | **D（段二）** | **0.807** | **0.874** |

- **影响**：体温按 2 s 分格的覆盖率 87.1%（门槛 99%，负责人接受）。网页上体温 97.3% 的时间显示有效；1 小时内“过期”71 次，61 次只有 1 s。每个 3 分钟窗口都缺 16–22%。
- **已排除**：
  - CAN 速率：段二负载约 8%；
  - B 的波形帧挤占：B 断电的 40 s 里，比值仍为 0.83。
- **头号嫌疑（未证实）**：B、D 共用的驱动 `node-b/canopen/CO_driver.c`。
  - 发送完成中断一次清掉全部 RQCP 标志，但**每次中断最多补发一帧**。
  - D 每秒连发心跳、PDO3、PDO4、PDO5 共 4 帧，硬件只有 3 个邮箱。若一次中断里两个邮箱同时完成，排队的帧就要等下一次中断。下一秒同一个 TPDO 再发时，缓冲还被占着，`CO_CANsend` 返回 `CO_ERROR_TX_OVERFLOW`，这一帧被丢掉。
  - **尚未解释**：D 的 PDO5 一帧不缺。
  - **补记（2026-11-28，手册第二批核对，嫌疑减弱）**：
    - A、E 用 node-a 版驱动，发送完成中断同样每次只补发一帧，与 node-b 版只差三处：TXFP；缓冲占用时 `CO_CANsend` 立即返回；接收过滤扩展帧和远程帧。但 A 的 PDO3/PDO5 = 0.98，E 为 0.999。
    - 按逻辑推算，排队的帧会随每次发送完成逐个补出，几毫秒就能发完，不会拖到 1 s 后同一 PDO 再发的时候。
    - 所以“每次只补发一帧”不足以单独解释约 20% 的缺失。缺得最多的 B（0.95）和 D（0.81）都用 node-b 版驱动，“缓冲占用时立即返回”这一差异值得优先建模。
    - 对照表见 `04` §9。
- **排查计划**：分支 `claude/d-node-tpdo-loss` 的 `docs/issues/D-NODE-TPDO-LOSS.md`：
  1. 先离线建驱动模型；
  2. 再只读读出 `CO_CAN_ERRTX_OVERFLOW`，或挂 CAN 分析仪；
  3. 最后修复：中断里有空闲邮箱就持续补发，或错开定时。
- **教训**：见 P-29。第一个假设（B 挤占）是错的，被时间分辨数据推翻。

## 3. 网关与网络

### P-21 出口吞吐不足〔已修复〕
- **现象**：源端约 10.45 批/s，出口只有约 8.07 批/s。
- **定位**：用 DWT 周期计数器分解每笔发送，并用主机模型复现：二进制写入 49%，SEND OK 等待约 22%，接收长度查询约 14%，AT 空闲只有 1.5 s（约 1.4%）。逐包 AT 交互占满了出口，不是串口线速不够。
- **处理**：改为 ESP8266 SSL 透传，每包只剩串口线上的传输时间。
- **验证**：五板实测 10.458 批/s，队列高水位 6/24，零丢弃。
- **教训**：先量后改。“加波特率”或“上 RTOS”都解决不了交互次数的问题。
- **出处**：R6–R14；项目书 13.1。

### P-22 MQTT 协议错误、畸形载荷与断链〔已缓解，根因 UNKNOWN〕
- **现象**：Broker 多次报告协议错误并断链，R33 时累计 9 次，其中包括无人操作的稳态事件。STM32 的短写、超时、重入计数均无异常。
- **处理**：
  - 显式的退出透传与重入流程：静默 → `+++` → 静默 → `AT`；
  - 退避 2 → 4 → 8 → 16 → 30 s；
  - ACK 停滞时限制波形灌入；
  - 网络类错误持续重试，只有本地不可恢复异常才停止（原来连续失败 3 次就永久停传）。
- **R127 的新证据**：15:14:52 断链 13 s。C 串口显示，最后一个 PUBACK 延迟 1,599 ms，之后不再有 PUBACK；5 s 后 QoS1 事务超时 → `TXEXIT` → 重新入网、授时、TLS、MQTT → `PASS_REENTRY_OK`。期间 UART 错误停在基线 223，CAN 发送失败 0。
- **结论**：触发点是 PUBACK 停滞，恢复流程按设计完成。停滞源自 ESP、无线、公网还是 Broker，仍为 UNKNOWN。
- **教训**：根因查不清时，先把系统做成可恢复的，并且把证据链留好。
- **出处**：R27–R33、R128 §3.1；项目书 13.5、L-07。

### P-23 断网恢复后 SNTP 多次零回复〔已接受，UNKNOWN〕
- **现象**：热点恢复后，Wi-Fi 很快重新关联，但新鲜 SNTP 样本多次零回复，实时遥测 551–582 s 才恢复（目标 ≤90 s）。
- **为什么必须等 SNTP**：网关要用可信 UTC 给数据打时间戳。拿不到新鲜样本就不上线，宁可晚，也不发时间错误的数据。
- **出处**：R36/R37；L-06。

### P-24 冷启动 UART 错误基线约 222–225〔已修复〕
- **现象**：每次冷启动都有约 223 个 UART 错误，误触发锁停。
- **原因**（合理假设，未用示波器确认）：ESP 上电时以 74880 baud 输出 ROM 日志，115200 的接收端把它当成帧错误。
- **处理**：ESP 静默后再建立基线，稳态只看新增量。之后 480 s 观察新增 0。

### P-25 配置分区擦写在提交前中断〔已修复〕
- **原因**：预算判断放在擦写之后，擦完才发现剩余时间不够写提交字。
- **处理**：写前判断预算，提交字放最后。恢复时只补写一个提交字，0 次重擦（R50/R51）。

### P-26 重入次数耗尽后永久停传〔已修复〕

## 4. 云端、网页与测试工具

### P-27 后端 WSS 测试偶发 `CancelledError`〔已修复，测试问题〕
- **原因**：测试夹具读完快照就退出，服务端关闭帧还没到。
- **处理**：读完后显式关闭，并等待服务端关闭帧。修复后两种依赖版本各连跑 30 次全过。
- **教训**：偶发失败先怀疑测试的时序，再怀疑被测代码。

### P-28 MQTT 录制器遇到二进制帧崩溃〔已修复，R127 修订 2〕
- **现象**：通配订阅 `mpm/v1/GW-C-001/#` 收到 `voice/broadcast` 的 MPB1 二进制播报帧，录制器按 UTF-8 解码失败，提前封存（14:21:13）。
- **处理**：改用能保存二进制载荷的录制器；判读脚本跳过语音帧并计数，判据不变。负责人放行补录一次。
- **教训**：通配订阅会收到所有类型的消息，工具不能假定载荷格式统一。

### P-29 R128 的第一个假设是错的〔流程教训〕
- **经过**：先看到 D 的 PDO3 少约 19%，推测“B 的高优先级波形帧挤占了 D”。
- **推翻**：
  - 按 5 分钟分段，比值稳定在 0.79–0.83；
  - B 断电的那一段比值仍为 0.83；
  - 总线负载只有约 8%。
- **处理**：同日在 R128 §3.2、项目书 L-17、验收报告中更正，原文划线保留。
- **教训**：汇总数据只能提出假设，要用时间分辨数据和对照条件（例如 B 断电那一段）检验。写错了要显式更正，不悄悄改掉。

### P-30 G3 覆盖率的第一版指标被混淆〔已修复，采集前〕
- **原因**：按 seq 计算完整性，但 C 先给 seq 加 1，再丢弃“未授时”帧，所以 seq 跨度大于实际发出的帧数。
- **处理**：改为“按 2 s 分格，有数据的格占比”。B 的门槛 90% 用已有数据标定，并在采集前写定。

### P-31 CPU 停在系统 ROM〔UNKNOWN〕
- **现象**：B、C 历史上出现过 CPU 停在系统 ROM（VTOR=0x1FFF0000），部分需要人工复位。
- **原则**：遇到这种情况就停止对目标的写入和复位，保存证据，不强设 PC 或 VTOR 来掩盖（见 `AGENTS.md`）。
- **根因**：调试器副作用、BOOT 引脚状态都未证实。

### P-32 一次“未解释的复电”〔非问题〕
- 后来由负责人确认是本人的手动操作，不是远程控制或安全事件。
