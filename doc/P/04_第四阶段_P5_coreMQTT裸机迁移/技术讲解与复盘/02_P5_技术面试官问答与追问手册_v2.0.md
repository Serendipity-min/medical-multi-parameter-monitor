## 二、裸机架构、调度与外设并发

### Q03: 系统没有使用 RTOS，如何实现多个任务的并发与调度？
- **标准口述回答**：系统采用“中断打标 + 主循环协作轮询 (Cooperative Polling)”的事件驱动架构。SysTick 中断仅累加全局滴答计数器 `g_uptime_ms`；USART3 中断仅将接收字节压入 8192 B（8KB）环形缓冲区；所有协议解析、CAN 状态机推进与 MQTT 报文收发均在 `main()` 主循环的单线程上下文中串行执行。
- **面试官追问**：“如果网络层在等待 AT 指令或服务器响应，发生阻塞时 CAN 采样会不会丢帧？”
- **追问关键答案**：“不会。通过 `platform_set_poll(service)` 注册了协作调度钩子。无论网络层在执行 `delay_ms()` 还是等待串口响应，内部循环都会持续调用 `platform_poll()` 进而触发 `service()`。`service()` 内部包含预算限制（每次最多追赶 8ms），既保证了 CANopen 状态机及时推进，又防止了总线计算过度占用导致网络饥饿。”
- **关联源码/验证证据**：`gateway/mqtt/src/main.c:15-25` (`service()` 函数), `gateway/mqtt/src/gateway_platform.c:platform_poll()`。
- **常见错误说法**：“我在中断服务函数里直接解析 CAN 报文和 MQTT 包，所以不会阻塞。”（严重违反嵌入式高可靠编程准则）。

---

### Q04: 为什么 `service()` 中的时钟追赶要设置 `budget = 8`？
- **标准口述回答**：`serviced` 记录了 CAN 栈上次推进的毫秒时间戳。当网络操作阻塞了若干毫秒后，`serviced` 会落后于 `g_uptime_ms`。如果不设上限一次性追赶全部落后时间，一旦网络阻塞较久，CAN 栈将连续循环数十毫秒，导致看门狗超时或网络包接收超时；设置 `budget = 8` 限制单次最多追赶 8ms，将追赶负荷平摊到后续各轮轮询中。
- **面试官追问**：“如果持续落后，8ms 追赶不够怎么办？”
- **追问关键答案**：“在主循环中，网络处理（`gateway_mqtt_publish`）完成后会立即进入下一次主循环迭代，再次触发 `service()`。只要主循环平均周期小于 1ms，累计的延时会在几个循环内迅速追平；若出现严重持续拥堵，Adapter 内部的采样队列会丢弃超期帧，并通过指标上报。”
- **关联源码/验证证据**：`gateway/mqtt/src/main.c:19-25`。
- **常见错误说法**：“8 是随便写的吉利数字 / 8 代表有 8 个传感器。”

---

### Q05: 串口接收为什么选择无锁环形缓冲区？有并发冲突风险吗？
- **标准口述回答**：因为系统是单生产者、单消费者模型（Single-Producer Single-Consumer, SPSC）：USART3 中断服务函数是唯一的生产者（写入 `head` 并填充缓冲区），主循环是唯一的消费者（读取 `tail` 并提取字节）。只要 `head` 和 `tail` 的读写为原子操作（32位对齐变量），SPSC 环形缓冲在无需互斥锁或关中断的情况下是严格线程安全的。
- **面试官追问**：“如果发生缓冲区满溢出，系统如何处理？”
- **追问关键答案**：“当 `(head + 1) % SIZE == tail` 时，中断例程丢弃最新字节并累加溢出错误计数，不会覆盖未读数据，防止破坏正在解析的帧边界。同时通过控制台输出诊断警报。”
- **关联源码/验证证据**：`gateway/mqtt/src/gateway_platform.c` 中环形缓冲区读写实现。
- **常见错误说法**：“通过加互斥锁 Mutex 解决的中断冲突。”（裸机无 RTOS 根本没有 Mutex）。

## 三、CANopen 协议、对象字典与生理数据建模

### Q06: CANopen 的对象字典 (OD) 是如何设计的？
- **标准口述回答**：对象字典是一个由 16 位索引和 8 位子索引构成的规范化参数表。在本项目中，按照 CiA 301 与自定义设备规范划分：
  - `0x1000 - 0x1FFF`：通信子协议区（设备类型、心跳周期、TPDO/RPDO 通信与映射参数）；
  - `0x2000 - 0x2FFF`（以及网关镜像区 `0x3000 - 0x3FFF`）：制造商特定生理参数区。Node-A 分配波形 `0x2110:01`（PPG）及标量 `0x2120:01..04`（SpO2, PR, NIBP 收缩/舒张）；Node-B 分配波形 `0x2110:01`（ECG）、`0x2111:01`（RESP）及标量 `0x2120:01..03`（HR, RR, TEMP）。体温属于 Node-B 采集上报。
- **面试官追问**：“为什么高频波形不用 SDO 传输？”
- **追问关键答案**：“SDO 是应答式确认传输，包含发起、上传、确认握手开销，通信效率低；PDO 是面向实时过程数据的广播式传输，直接将生理采样映射到 CAN 帧载荷中，无需应用层握手，能满足 ECG 250Hz 和 PPG 50Hz 的实时吞吐要求。”
- **关联源码/验证证据**：`gateway/canopen/src/mp_od.c`, `gateway/canopen/src/mp_adapter.c`。
- **常见错误说法**：“波形数据通过 SDO 读写，体征参数通过 PDO 传输。”

---

### Q07: 生理波形为什么要进行 1 秒批次汇聚？
- **标准口述回答**：ECG 采样率为 250Hz，PPG 和 RESP 采样率为 50Hz。如果每采集到一个采样点就封装一次 JSON 并通过 MQTT 发送，每秒将产生 350 个 MQTT 报文。不仅串口 AT 指令吞吐率无法承受，而且网络 TCP/IP 报文头开销巨大，甚至会拖垮云端 Broker。因此网关在 Adapter 层实施 1 秒批次汇聚，每秒将 250 点 ECG（500 字节）打包成一个数组单包发布。
- **面试官追问**：“1 秒批次打包会导致波形在客户端呈现延时 1 秒，医疗监护上能接受吗？”
- **追问关键答案**：“符合医疗监护通用工程规范。中央监护大屏通常具有 1–2 秒的显示平滑缓冲区用于抗网络抖动。此外，床旁机本地显示屏是零延时硬刷新的，网关负责的是远端远程监护上云，1 秒批次在网络带宽、系统功耗与临床实时性之间取得了最佳平衡。”
- **关联源码/验证证据**：`gateway/canopen/src/mp_adapter.c:mp_adapter_poll()`。
- **常见错误说法**：“为了让数据更准确所以必须凑满 1 秒做滤波。”

---

### Q08: 什么是 `RR INVALID (0xFF)`？网关如何处理？
- **标准口述回答**：`RR` 代表呼吸率（Respiration Rate）。当患者发生体动或呼吸阻抗探头接触不良时，算法无法从阻抗波形中提取出置信的呼吸率数值，Node-B 上报特殊状态码 `0xFF`。网关严格保留该标志，并在转换 JSON 时输出为 `null` 或携带非零质量位，绝不将其转换为 0。
- **面试官追问**：“为什么不能转为 0？”
- **追问关键答案**：“在临床医学中，呼吸率 0 rpm 代表窒息（Apnea）或呼吸停止，会触发最高级别紧急生命体征声光报警！如果把‘信号无效’误报为‘0’，会导致极其严重的误报警（Alarm Fatigue）；反之如果把‘0’误报为无效，会造成漏报。必须严格区分‘数值为零’与‘测量无效’。”
- **关联源码/验证证据**：`gateway/canopen/src/mp_adapter.c`, `gateway/data_model/model.c`。
- **常见错误说法**：“0xFF 是负数补码，说明呼吸算法溢出了。”

---

### Q09: 规范数据帧 `MpFrame` 为什么包含 `seq`、`epoch` 和 `boot` 字段？
- **标准口述回答**：
  1. `seq`：单流内严格单调递增的序号，用于下游识别丢包率与剔除重复报文；
  2. `epoch`：网关通过 SNTP 获取的基准时间戳，用于锚定绝对时钟；
  3. `boot`：系统重启代际计数器。高 16 位为 Gateway 重启代号，低 16 位为采集节点重启代号。当节点意外复位后，`seq` 会从 0 重新开始计数，后端必须结合 `boot` 代际才能正确识别序列连续性，防止误将新会话的报文判为旧报文丢弃。
- **面试官追问**：“如果网关断电重启，`boot` 计数器保存在哪里？”
- **追问关键答案**：“在未来物理板上应存储于外部 EEPROM 或内部 Flash 非易失性配置区；当前合成系统中，网关重启会自增内存启动计数，并在初次连接时通过 LWT 和首帧告知云端会话重置。”
- **关联源码/验证证据**：`gateway/data_model/model.h` 中 `MpFrame` 结构体定义。
- **常见错误说法**：“`boot` 是指 MCU 的启动时间（毫秒）。”

## 四、coreMQTT 协议深度与网络适配

### Q10: 为什么从 Paho 迁移到 coreMQTT？
- **标准口述回答**：Paho Embedded C 虽然使用广泛，但在裸机上存在三个设计短板：一是内部缓冲区与网络层耦合较深，状态复位逻辑不透明；二是报文拼装易出现隐式动态内存或不可控边界；三是缺乏面向严苛安全认证的静态证明。coreMQTT v2.3.1 是 AWS 面向安全关键领域设计的轻量级 C 库，具有零动态内存分配、报文解析完全有界、通过形式化 CBMC 验证的特点，完美契合医疗设备的静态资源审计要求。
- **面试官追问**：“coreMQTT 相比 Paho 带来额外的开发成本是什么？”
- **追问关键答案**：“coreMQTT 仅包含纯协议编解码状态机，不提供任何底层套接字读写、重试线程、定时器或队列管理。所有网络抽象（`TransportInterface_t`）、超时计算、PUBACK 匹配、重发与断网离线缓存都必须由我们自己在应用层编写适配代码，开发与测试工作量显著增加。”
- **关联源码/验证证据**：`gateway/mqtt/src/mqtt_transport_adapter.c`, `gateway/third_party/coreMQTT/`。
- **常见错误说法**：“coreMQTT 性能比 Paho 快 10 倍 / coreMQTT 支持多线程所以选它。”

---

### Q11: 为什么说 coreMQTT 是“零动态内存分配”？
- **标准口述回答**：coreMQTT 的所有协议 API（如 `MQTT_Init`, `MQTT_Connect`, `MQTT_Publish`）均不调用 `malloc`、`calloc` 或 `free`。协议上下文 `MQTTContext_t`、底层传输上下文 `NetworkContext_t` 以及用于存储拼装报文的静态数组完全由调用方在编译期静态分配（位于 BSS 段）。但需要严谨说明：网关整体中 CANopenNode 实例初始化（`CO_new`）依然依赖 `calloc`（由 `gateway/mqtt/src/heap.c` 的有界动态堆 `_sbrk` 托管，分配失败即返回错误并安全隔离），不可夸大为整网关完全不调用 `calloc`。
- **面试官追问**：“没有动态内存，如果服务器发来的报文超过了你的静态缓冲区大小怎么办？”
- **追问关键答案**：“coreMQTT 会在解析报文固定报文头中的 Remaining Length 时与缓冲区上限比对，如果长度超出预分配缓冲区，直接返回 `MQTTNoMemory` 或 `MQTTBadResponse` 错误码，立即有界终止解析，绝不会发生缓冲区溢出或野指针越界写入。”
- **关联源码/验证证据**：`gateway/mqtt/src/gateway_transport.c`, `gateway/mqtt/src/heap.c`。
- **常见错误说法**：“它在内部用了一个隐藏的虚拟堆分配内存 / 整个工程连 CANopen 都没有一行 calloc。”

---

### Q12: 解释 `mqtt_transport_adapter.c` 中 `writev` 的实现与优化原理。
- **标准口述回答**：标准 `send` 只能发送一块连续内存。在发布 MQTT 报文时，报文头与数据载荷往往位于不同的内存块。如果调用两次 `send`，在 AT 指令架构下会产生两次独立的 `AT+CIPSEND` 命令握手交互，引起严重的串口往返延迟。`writev`（向量写）在适配层内部开辟了一个 2048 字节的临时静态缓冲区，将多个散片向量在内存中一次性聚合拷贝，随后触发单次 `AT+CIPSEND` 将整包一次性写入 ESP8266，极大提升了网络吞吐效率。
- **面试官追问**：“聚合拷贝完成后对缓冲区有安全清理措施吗？”
- **追问关键答案**：“有。在数据通过串口送出后，代码对敏感暂存缓冲区立即调用擦除，防止敏感报文或鉴权信息在 RAM 中残留。”
- **关联源码/验证证据**：`gateway/mqtt/src/mqtt_transport_adapter.c:transport_writev()`。
- **常见错误说法**：“`writev` 是 Linux 的系统调用，单片机裸机上根本不能用。”

### Q13: QoS 0 与 QoS 1 的本质区别是什么？
- **标准口述回答**：
  - **QoS 0（最多交付一次）**：网关将报文送入底层传输驱动后即视为发布成功，Router 立即将帧出队确认。Broker 不会回复确认报文，网关无法得知 Broker 是否实际收到；
  - **QoS 1（至少交付一次）**：网关从 Router 取出独立帧副本发送，只有等待 Broker 回复对应的 `PUBACK` 报文，且校验报文内的 `Packet ID` 与发送的 ID 一致，Router 才会出队确认。若超时未收到或收到错误 ID，本轮发布失败，Router 将副本回存到有界缓存，重连后才可能补传；缓存满时仍会丢弃旧帧。
- **面试官追问**：“QoS 1 能保证数据‘不重不漏’吗？收到 PUBACK 是否代表后端已完成消费？”
- **追问关键答案**：“**不能保证不重，且 PUBACK 不等于后端消费确认！**
  1. **不重不漏问题**：QoS 1 提供单次 MQTT 发布链路的至少一次交付语义，但**不保证本工程端到端不丢帧**：32 帧缓存可能溢出淘汰，Broker 已确认也不代表 Backend 已消费。当网络抖动导致 PUBACK 丢失时网关会重发，Broker 端可能收到重复报文。要实现严格的无重复业务呈现，必须依靠后端应用层的唯一序号 (`seq`) 进行去重；
  2. **PUBACK 的语义边界**：MQTT 属于 Hop-by-Hop 单跳协议，Broker 返回的 PUBACK 仅证明第一跳 Broker 节点成功接收了该报文并接管了路由职责，**绝不等于下游 Python Backend、Hub 或时序数据库已成功消费、解析和持久化存储**。若后端服务离线或崩溃，Broker 依然会向网关返回 PUBACK。端到端业务闭环需在应用层另行规划。”
- **关联源码/验证证据**：`gateway/mqtt/src/gateway_transport.c`, `gateway/storage/router.c`。
- **常见错误说法**：“QoS 1 就是恰好收到一次，既不丢也不重 / 收到 PUBACK 就代表云端数据库已经存好了。”

### Q14: 迟到或错号的 PUBACK 是如何处理的？
- **标准口述回答**：在 `gateway/mqtt/src/gateway_transport.c` 的发布等待循环中，网关维护当前待确认的 `pending_id`。`mqtt_event()` 仅在 PUBACK 的 Packet ID 匹配时设置 `acknowledged=1`；收到错号或不期望的报文时调用 `mqtt_failed()`，立即将本轮发布判为失败、关闭适配连接，并由外层重连，**不是忽略错号后继续等待**。如果一直没有匹配 PUBACK，则按 5 秒预算超时失败，由 Router 缓存该帧（容量满时仍可能淘汰）。
- **面试官追问**：“如果不校验 Packet ID 会引发什么严重后果？”
- **追问关键答案**：“会导致**确认错位**。假设帧 1 超时未确认，网关重发了帧 1 并随后发送了帧 2；此时若收到了针对旧帧 1 的迟到 PUBACK，若不校验 ID 就误将其当成帧 2 的确认，会导致实际已经丢失的帧 2 从队列中被错误删除，造成静默永久丢数据！”
- **关联源码/验证证据**：`gateway/mqtt/tests/test_p5_qos_ack.c` 中的专项测试用例。
- **常见错误说法**：“只要收到 PUBACK 就代表成功，不管 ID 是多少。”

### Q15: 系统 KeepAlive 机制是如何运作的？
- **标准口述回答**：MQTT CONNECT 报文协商了 15 秒的保活周期（`keepAliveSeconds = 15`）。在数据循环中，若超过保活间隔未发送任何业务数据，主循环调用 `gateway_mqtt_yield()`，内部触发 `MQTT_ProcessLoop()` 自动生成并向 Broker 发送一个 `PINGREQ`（心跳请求）报文，并等待 Broker 回复 `PINGRESP`（心跳响应）。
- **面试官追问**：“如果 Broker 持续不回复 PINGRESP 怎么办？”
- **追问关键答案**：“coreMQTT 内部维护心跳超时计时器。如果连续未收到 PINGRESP 响应，`MQTT_ProcessLoop` 返回 `MQTTKeepAliveTimeout` 错误，网关判断链路已成‘半开死连接’（TCP 假活），立即主动关闭底层连接，进入网络重连流程。”
- **关联源码/验证证据**：`gateway/mqtt/src/gateway_transport.c:gateway_mqtt_yield()`。
- **常见错误说法**：“ESP8266 硬件会自动发 PINGREQ，MCU 不需要管。”

## 五、ESP8266 AT 指令与安全传输边界

### Q16: ESP8266 与 MCU 的通信架构与物理波特率是多少？
- **标准口述回答**：STM32F407 的 USART3 通过串口线与 ESP8266-01S 模块的 RX/TX 引脚交叉连接，通信波特率配置为 115200 bps，8 位数据位，1 位停止位，无硬件流控（标准 AT 固件默认配置）。
- **面试官追问**：“为什么不用 921600 等更高波特率？”
- **追问关键答案**：“在裸机无硬件 RTS/CTS 流控的简易接线环境下，超高波特率在 ESP 处理内部 Flash 写入或 TLS 密集计算时容易发生接收 FIFO 溢出导致丢字节。115200 bps 传输 1 秒批次数据（约 1KB）仅需约 80ms，带宽余量充足且信号稳定性最好。”
- **关联源码/验证证据**：`gateway/esp_at_probe/src/main.c`, `gateway/mqtt/src/gateway_platform.c`。
- **常见错误说法**：“波特率越高越好，我们跑在 2Mbps 上。”

### Q17: TLS 握手是由谁执行的？证书校验是如何配置的？
- **标准口述回答**：TLS 1.2 握手与加解密由 ESP8266 内部固件的 mbedTLS 协议栈执行。网关通过 AT 指令序列开启单向证书校验：
  1. 通过 `AT+CWSSLCCONF` 启用 CA 证书链校验；
  2. 配置 Common Name (CCN) 校验与 Server Name Indication (SNI) 扩展，防止中间人通过替换合法证书实施攻击；
  3. CA 证书在生产烧录时预置于 ESP8266 的专有 Flash 分区。
- **面试官追问**：“如果 CA 证书校验失败，系统会降级为明文连接吗？”
- **追问关键答案**：“**绝对不会！** 我们的 Host 测试（`tls_ca_failure_no_plaintext_fallback`）严格验证了这一红线：若 TLS 握手或证书校验失败，系统直接报错断开，严禁任何降级为明文 1883 端口的行为，确保医疗数据在公共网络上的机密性与防篡改。”

### Q18: 网关如何实现绝对时间对齐？SNTP 失败过吗？
- **标准口述回答**：网关依赖 ESP8266 的 SNTP 客户端服务。在连上 Wi-Fi 后，发送 `AT+CIPSNTPCFG=1,0` 配置启用 SNTP 且时区为 UTC 0，随后通过 `AT+SYSTIMESTAMP?` 查询真实绝对时间戳，并据此锚定 `stack.epoch`。

## 六、数据路由、缓存与断网淘汰

### Q19: 详细解释 Router 的双级缓存结构与容量限制。
- **标准口述回答**：`gateway/storage/router.c` 实现了完全静态分配的双级环形队列：
  - **Live Queue (实时队列)**：容量固定为 16 帧，专用于存放最新产生的波形与状态帧；
  - **Cache Queue (离线缓存队列)**：容量固定为 32 帧，当网络处于断开状态时，由实时队列溢出或未发布的数据转入离线队列缓存。
  总计静态容量为 48 帧。
- **面试官追问**：“为什么离线缓存只设 32 帧（约 30 多秒数据）？为什么不做几千帧？”
- **追问关键答案**：“受限于 STM32F407ZGT6 的物理 RAM。每帧 `MpFrame` 约占用 1KB 内存，48 帧静态分配已占用近 50KB RAM，占芯片总 RAM 的四分之一以上。如果做数百帧会导致 RAM 耗尽崩溃。在医疗监护仪设计中，数小时长周期的全量离线存储应当依托外部 SD 卡或 SPI Flash，MCU 内部 RAM 仅负责秒级网络抖动的弹性平滑。”
- **关联源码/验证证据**：`gateway/storage/router.h`, `gateway/storage/router.c`。
- **常见错误说法**：“我们用链表动态分配，可以存无限多帧。”

---

### Q20: 离线缓存队列满后采用什么淘汰策略？实测证据是什么？
- **标准口述回答**：采用 **FIFO 有界淘汰（丢弃最旧数据）**。当 32 帧离线缓存满时，新采样帧强行推入，队列头部最旧的一帧被丢弃，同时累加计数器 `router.dropped`。
- **面试官追问**：“你们测试中发生过丢包吗？”
- **追问关键答案**：“**发生过，并且我们在技术文档和指标中如实记录了 `lost=203`**。在长时间断网恢复测试中，控制台明确输出了 `GW METRICS ... lost=203`。这充分证明了我们的设计是诚实坦率的‘有界有损缓存’，从不在架构陈述中虚假宣传‘断网数据绝对无损零丢失’。”
- **关联源码/验证证据**：`gateway/mqtt/src/main.c:157-160` (METRICS 输出日志), `gateway/storage/router.c`。
- **常见错误说法**：“我们的缓存算法特别先进，断网几天一个点都不会丢。”

### Q21: 网络恢复后，历史数据是如何“补传 (Replay)”的？
- **标准口述回答**：当 `gateway_network_open()` 成功重连后，网关首先标记 `mp_router_online(&router, true)`，并立即优先发布一帧当前最新的 `MP_GATEWAY_STATUS` 网关状态。随后，主循环在提取帧时，若实时队列为空，优先从 Cache 队列中提取历史帧，将其打上 `replay = true` 标志，通过 QoS 1 逐帧补传并等待 ACK。
- **面试官追问**：“补传的历史数据会不会把前端实时大屏正在跳动的心电图‘冲乱’？”
- **追问关键答案**：“不会。因为每帧数据都明确携带 `replay=true` 标志以及当时的精确采样时间戳 `timestamp`。后端 Python 服务解析到 `replay=true` 后，直接将其分流存储入时序历史数据库，前端大屏的 Canvas 实时渲染引擎（基于 Vite + TypeScript 原生 DOM/Canvas 构建）忽略带有 `replay` 标志的帧，仅用实时帧驱动波形滚动，完全不影响床旁监视。”
- **关联源码/验证证据**：`gateway/mqtt/src/main.c:122-124`, `gateway/storage/router.c`。
- **常见错误说法**：“补传的数据会插队到实时波形中间显示出来。”

## 七、缺陷复盘与 `GEMINI-P5-001` 最小修复

### Q22: 请详细介绍你们在 P5 审查中修复的 `GEMINI-P5-001` 缺陷。
- **标准口述回答**：在审查 `gateway/mqtt/src/main.c` 时，我们发现本地调试命令 `'E'`（用于手动触发/清除 Node-A 的 CANopen EMCY 紧急报文）存在空指针解引用隐患。原代码直接访问 `stack.nodes[0].co->em`，如果 Node-A 因初次初始化失败或重启脱挂导致 `co` 为 NULL，键入 `'E'` 会直接导致 MCU HardFault 死机；并且原代码在解引用前就执行了 `fault = !fault`，会导致故障状态机被非法翻转。
- **面试官追问**：“你是怎么修复这个缺陷的？为什么不用 `break`？”

- **关联源码/验证证据**：`gateway/mqtt/src/main.c:55-65`, 提交 `2e13ff3`。
- **常见错误说法**：“我重构了整个控制台模块，加了多线程指令队列。”

### Q24: 历史上的 CANopen 重启崩溃 Bug 是什么原因？如何解决的？
- **标准口述回答**：历史 Bug 发生在通过控制台命令 `'R'` 重启 Node-B 时。原先的重启逻辑如果 `CO_new()` 动态分配失败或 `CO_CANinit()` 失败，仅打印错误，但没有清空节点结构体，且 `enabled` 仍为 `true`。后续主循环轮询 `mp_stack_tick(&stack)` 时，继续解引用无效的 `co` 指针，导致系统崩溃；此外，旧实例的 OD 扩展回调未注销，新实例重新注册时引发冲突。

- **面试官追问**：“你们是如何回归验证这个重启修复的？”
- **追问关键答案**：“在 `gateway/canopen/build_host.py` 中，通过 GCC 链接器包装选项（`-Wl,--wrap=calloc`, `--wrap=CO_CANinit` 等）注入模拟的分配失败与总线失败故障，执行了 17 项重启可靠性测试，验证了在各种失败路径下均无内存泄漏且各节点正常解挂。”
- **关联源码/验证证据**：`gateway/canopen/src/mp_stack.c`, `gateway/canopen/tests/restart_reliability.c` (17 项用例全部 PASS)。

## 九、12 道进阶逼问与高难度追问专项

### Q29: 如果 Broker 突然宕机，主循环卡在 TLS 发送上怎么办？ESP8266 挂死如何自愈？
- **标准口述回答**：底层 `mqtt_transport_adapter.c` 中的发送接口并非无界死等，而是注入了严格的单次有界超时（例如 5000ms），并且依赖底层 ESP8266 硬件 TCP 的重传超时机制。若超时未收到 `SEND OK`，`esp_mqtt_send()` 返回 `-1`，传输适配层返回错误并关闭连接，本轮发布失败进入外层重试。不要凭空指定 `MQTTServerDataBufferOverflow` 作为该 AT 超时路径的返回码。
- **追问**：“如果 ESP8266 模块死机，串口彻底无响应怎么办？你们有硬件 GPIO 复位引脚吗？”
- **追问核心**：“**当前硬件并未连接或配置 ESP8266 的 GPIO RST 硬复位引脚**！系统完全依靠**纯软件有界超时判定与状态机自愈**：
  1. `gateway/mqtt/src/platform.c` 中的 `await_reply` 使用调用者提供的有界超时（例如常规 AT 2000ms、入网/TLS 可达 30000ms）。若串口无回应或返回错误，本步骤失败并由外层重试；这不是独立的硬件看门狗，模块完全挂死时软件重试也未必能恢复；
  2. 网关调用 `gateway_network_close()` 向模块下发 `AT+CIPCLOSE` 拆除可能残留的套接字；
  3. 下一次主循环重连入口调用 `esp_mqtt_reset()`（`gateway/mqtt/src/platform.c:257`），在关中断保护下清空 UART 环形队列指针（`head = tail`）、重置错误标志（`errors = 0`）与数据包长度；
  4. 重新按序执行 `AT`、`ATE0`、`AT+SYSSTORE=0`、`AT+CWMODE=1`、`AT+CWJAP`、`AT+CIPSNTPCFG=1,0`，实现纯软件冷重连与状态同步。在此重连期间，主循环通过 `platform_poll()` 继续推进 CAN 采样，确保床旁生理监护不停滞。”

### Q30: 为什么不把心电图波形做压缩（如差分编码或 Huffman）再发 MQTT？
- **标准口述回答**：在 P5 裸机阶段，系统主频运行于 **16 MHz HSI** 内部时钟（样机当前未配置外部 HSE 晶振与 PLL 倍频至 168 MHz），RAM 资源也极为受限，核心目标是确保数据管道的确定性与极简性。当前 `MpFrame.values` 使用 `int32_t[250]`，250 点原始数值约占 **1000 B**；JSON 序列化后的长度还受实际数值、符号及字段影响，不能未经实际抓包统计就断言总量小于 1.5 KB 或小于 12 kbps。是否压缩应依据持续带宽、CPU 和端到端负载实测决定。过早引入复杂压缩算法会显著增加 MCU CPU 负荷与内存消耗，甚至带来压缩解压失真的算法风险。

---

### Q31: 如果出现网络抖动，PUBACK 刚好在超时时间点到达，如何避免死锁？
- **标准口述回答**：代码中严格按照单调递增的 `g_uptime_ms` 计算时间差 `(g_uptime_ms - start_time) >= timeout`。如果 PUBACK 在刚好超时前一刻到达并被正确匹配，视为成功出队；若已超时被判定为失败，该帧被留在队列中，即使下一刻有迟到的 PUBACK 进入，在下次重连重传时会重新生成新的 Packet ID，旧 PUBACK 会因 ID 不匹配被丢弃，不会产生状态死锁。同时牢记：PUBACK 仅证明第一跳 Broker 接收，不等于后端服务已经完成入库消费。

### Q32: 为什么实现有界动态堆 (`heap.c`)？内存布局是怎样的？
- **标准口述回答**：CANopenNode 官方库在初始化分配各模块（如 SDO、PDO、EMCY）时默认调用了 `calloc`。如果在嵌入式中直接使用 newlib 默认不受控的堆，极易产生内存碎片或无界侵占栈区。我们在 `gateway/mqtt/src/heap.c` 中实现了严格有界的 `_sbrk`，配合链接脚本 `STM32F407ZGT6_FLASH.ld` 为其划定了硬边界：在 `._user_heap_stack` 段中预留了 **24 KiB**（`0x6000` = 24,576 B）的动态堆（`_heap_start` 至 `_heap_end`），`_sbrk` 严格检查若累积分配超出 `_heap_end` 立即返回 `ENOMEM`，绝不越界；在 `_heap_end` 向上静态规划了 **8 KiB**（`0x2000` = 8,192 B）主栈预留区（并非有 MPU 的栈保护机制）。
- **面试官追问**：“那当前网关的静态 RAM 占用率到底是多少？剩余 10,864 B 空间是什么含义？”
- **追问关键答案**：“
  1. **配置 RAM 容量**：链接脚本配置使用常规 SRAM 前 128 KiB（131,072 B，栈顶 `_estack = 0x20020000`）；
  2. **已分配静态段**：Data 段（88 B）+ BSS 段（全局变量 87,348 B + 24 KiB Heap 预留 + 8 KiB Stack 预留 + 对齐 4 B，共计 120,120 B）合计占用 **120,208 字节**，占配置 RAM 的 **91.7%**；
  3. **10,864 B 剩余 RAM 的本质**：从预留段末尾（`0x2001D590`）到 `_estack`（`0x20020000`）之间留有 `0x2A70` = **10,864 字节**未分配空间。这是已链接预留区之上的未分配裕量，并非整个栈的精确上限；向下另有 8,192 B 已预留的栈区域，因此 `_estack` 到 `_heap_end` 共约 19,056 B 地址距离。链接预留不是栈溢出硬保护，实际安全栈深仍须测量；
  4. **工程台账**：运行时栈高水位尚未进行真机打桩实测，已作为残余风险 RSK-P5-001 列入管控。”
- **关联源码/验证证据**：`gateway/mqtt/src/heap.c`, `gateway/mqtt/STM32F407ZGT6_FLASH.ld`, `gateway/mqtt/build/gateway_mqtt.map`。

### Q33: 当前系统测试中，最大的“未测风险”是什么？
- **标准口述回答**：最大的未测风险是**极端负载下的运行时动态栈高水位（Stack High-Water Mark）未经过硬件打标测量**。虽然静态 BSS 段我们精确统计到了 120,120 字节，但当高频中断与复杂 JSON 序列化嵌套发生时，系统栈实际深度的极值尚未在真机上通过内存打桩（Watermarking）进行 24 小时长时间极限压测。这是后续进入 P6 或 RTOS 任务化改造时必须优先补齐的测试。

---

### Q34: 如果两块实体板 CAN 晶振频偏达到 1%，通信会发生什么？
- **标准口述回答**：标准 CAN 协议（如 500kbps）对振荡器容差有严格要求（通常要求陶瓷谐振器或晶振频偏在 0.5% 以内，推荐石英晶体在 0.1% 以内）。若频偏达到 1%，位时序的重同步跳转宽度（SJW）将无法补偿累积的采样点相位偏差，导致位填充错误（Stuff Error）或 CRC 校验错误，节点将频繁发送主动错误标志并最终进入 Bus-Off 挂起状态。这正是为什么单板环回通过后，物理板必须严格测试物理晶振与位时序配置的原因。

---

### Q35: 你们的固件如何防止看门狗超时？
- **标准口述回答**：STM32F407 启用了独立看门狗 (IWDG)。主循环的每一次迭代、以及底层阻塞等待过程中的 `platform_poll()` 回调中均设置了喂狗点。如果主循环或网络等待单次停留超过安全阈值（如 2 秒），看门狗将强制硬件复位，防止固件死锁。

---

### Q36: 为什么重连后要先发布带有 `retain = true` 的网关状态帧？
- **标准口述回答**：状态流（`MP_GATEWAY_STATUS`）包含了网关当前的 Wi-Fi 信号强度、已连接节点列表以及丢包统计。设置 `retain = true` 可以让 MQTT Broker 永久保留最新的一份网关健康状态，确保在任何时刻新打开网页的医生大屏能够瞬间获知监护仪是在线还是离线，而无需等待下一个 5 秒周期。

---

### Q37: 什么是 MQTT 的遗嘱报文 (LWT)？你们是如何配置的？
- **标准口述回答**：LWT (Last Will and Testament) 是在 MQTT CONNECT 报文握手时向 Broker 预存的一份“遗嘱”。网关在 `gateway_mqtt_open` 中将 LWT 的 Topic 设为 `v1/monitor/status`，载荷中显式标记 `status: "OFFLINE"`。一旦网关发生物理断电、硬件死机或网络被拔出，Broker 在心跳超时（1.5 倍 KeepAlive 即约 22.5 秒）后会自动将此遗嘱向所有订阅端广播，确保前端大屏能及时显示“设备意外离线”报警。

---

### Q38: 为什么不采用 MQTT 5.0 的 Shared Subscription 或 Topic Alias 特性？
- **标准口述回答**：本项目以高可靠、精简化为首要原则。MQTT 3.1.1 协议经过了十余年全球工业界的大规模检验，库体积小（coreMQTT 仅数千行代码）、资源开销极低。MQTT 5.0 增加了大量属性键值对、复杂理由码与共享订阅特性，会显著增加嵌入式端的解析器复杂度和 RAM 开销。在固定拓扑的医疗监护仪上，3.1.1 的功能完全满足需求，无需承担不必要的复杂度溢出风险。

---

### Q39: 在物理板上做短 Smoke 测试后，为什么必须恢复原始 Flash？
- **标准口述回答**：因为在严谨的工程变更准则中，任何临时诊断固件或未最终签发的测试版本都严禁长期残留在物理原型机上。我们在硬件调试窗口结束后，通过 SWD/J-Link 将**本次测试窗口开始时板上已有的无关模块程序**作为恢复基线完整回写至 1MiB Flash，并用 VerifyBin 与独立回读核对（恢复 SHA-256 为 `15102707af11cfb7f57bac250bd30e583274d9f992292f5db6576a4b69c37354` ；该恢复基线与更早的旧历史镜像不同），确认本次测试固件不残留，但不能称其为‘出厂固件’。

---

### Q40: 如果后端 Python 消费能力不足，发生反压怎么办？
- **标准口述回答**：网关的 QoS 1 PUBACK 只确认 Broker 收到发布，**不等待 Python Backend 消费完成**。后端宕机时 Broker 仍可能照常发送 PUBACK；本项目 Backend MQTT 客户端使用 `clean_session=True`，不能假定它离线期间的遥测都由 Broker 持久化。Backend 入口为有界队列，拥塞时可丢弃并计数；网关的 16 实时帧和 32 缓存帧主要缓冲 Broker 发布链路异常，并非端到端持久化队列。需通过应用层确认、去重和对账完善完整性。
