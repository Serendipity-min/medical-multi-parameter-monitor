# 问题一：畸形 MQTT 报文可能越界读取

这是**优先级更高的一个**。

当前代码里：

```c
int MQTTDeserialize_publish(..., unsigned char* buf, int buflen)
```

虽然传入了：

```text
buflen
```

但其核心逻辑并没有真正拿它约束 Remaining Length 的解析。

例如现在是：

```c
header.byte = readChar(&curdata);

MQTTPacket_decodeBuf(curdata, &mylen);

curdata += lenlen;

enddata = curdata + mylen;
```

问题在于：

```text
MQTTPacket_decodeBuf()
```

本身没有“buffer end”参数。

它内部通过：

```c
bufptr = buf;
MQTTPacket_decode(bufchar, value);
```

不断读取 Remaining Length。

也就是说：

> **它知道 MQTT 报文声称有多长，却不真正知道调用方实际给了多少有效字节。**

随后：

```c
enddata = curdata + mylen;
```

也是根据**报文自己声明的长度**构造结束地址。

这就是畸形输入触发 OOB Read 的典型根源。

### A. Remaining Length 必须带长度

不要继续使用：


增加类似：


每读取一个字节都确保：


并继续遵守 MQTT：


### B. `MQTTDeserialize_publish()` 真正使用 `buflen`

至少验证：

```text
buflen >= 2

1 + remaining_length_field_length <= buflen

remaining_length <=
buflen - header - remaining_length_field

topic length <= remaining packet

QoS > 0 时至少还有 Packet ID 2 Bytes

QoS != 3
```

最后：

```text

```

而不是：

```text

```

### C. `MQTTClient.c` 传“实际收到长度”

现在很多反序列化调用用了：

```c
c->readbuf_size
```

也就是：

> Buffer 容量。

正确应该传：

> **本次 Packet 实际有效长度。**

例如：

```text

实际收到 = 4 bytes
```

不能告诉 Parser：

```text
你有 2048 bytes 可以读
```

这是非常重要的边界。

可以给 `readPacket()` 增加：

```c
actual_packet_len
```

或者保存在 Client：

```c
c->read_packet_length
```

然后：

```c
MQTTDeserialize_ack(
   ...,
   c->readbuf,
   actual_packet_len
);
```

# 问题二：小字符串 Buffer 可能越界写

这个问题也确实能从当前源码解释出来。

例如：

```c
strindex = snprintf(strbuf, strbuflen, ...);
```

之后：

```c
strindex += snprintf(
    &strbuf[strindex],
    strbuflen - strindex,
    ...
);
```

这里隐藏了一个经典 C 坑。

`snprintf()` 返回的是：

> **“如果空间足够，本来应该写多少字符”**

不是：

> “实际上写进去了多少”。

假设：

```text
buffer = 16 bytes
完整文本需要 80 bytes
```

那么：

```c
snprintf(...)
```

可能返回：

```text
80
```

随后代码会：

```c
&strbuf[80]
```

这已经越过 16 byte buffer。

然后：

```c
strbuflen - strindex
```

变成负数。

传进 `snprintf(size_t)` 后可能变成一个巨大的无符号数。

于是：

> **OOB Write。**

Codex 的 ASan 报告和这段代码逻辑是对得上的。
