# 1. 项目目标与范围

## 1.1 总体目标

开发一套可运行、可联调、可扩展的多参数生理监护工程系统，实现：

- 血氧饱和度 SpO2 / PPG / PR；
- 无创血压 NIBP；
- 体温 TEMP；
- 心电 ECG / 心率 HR；
- 呼吸阻抗波形 RESP；
- 呼吸率 RR；
- 四个模块分别具有本地显示；
- 两个采集节点通过统一板间协议汇聚；
- Gateway-C 独立完成网络上云，不依赖个人电脑常开；
- 腾讯云完成数据接收、转发、存储与网页大屏展示；
- 网络异常时具备基本离线缓存与恢复能力；
- 测试通过后再决定是否进入最终单板样机集成。

## 1.2 本阶段不强制完成的内容

以下内容不作为当前合同的必交项：

- 医疗器械注册与临床认证；
- HIS/EMR 正式医院系统接入；
- 最终产品化 PCB；
- 所有模块集成到单块 STM32F407；
- 公网远程控制血压充气、泄压等动作；
- 最终量产、试产和医疗认证。

## 3.2 呼吸率责任边界

呼吸率不是独立新增传感器。

数据来源为：

```text
ADS1292R 心率/ECG 模块
        ↓
呼吸阻抗原始通道 RESP_RAW
        ↓
成员 B 保证原始数据可靠采集
        ↓
P 负责 RR 算法设计、验证与版本管理
        ↓
验证后的算法集成至 Node-B
        ↓
输出 RESP 波形 + RR
```

责任冻结为：

| 工作 | 负责人 |
|---|---|
| ADS1292R 硬件和驱动 | B |
| RESP_RAW 采集 | B |
| RESP_RAW 数据接口 | B |
| RR 算法设计 | P |
| RR 算法参考实现 | P |
| RR 算法验证 | P |
| RR 算法集成到 Node-B | B 配合，P 验收 |
| RR 本地显示 | B |
| RR 云端展示 | P |

# 4. 功能设计

## 4.1 Node-A

Node-A 负责成员 A 的两个模块：

```text
Node-A / STM32F407-A
├── AFE4490 Arduino 血氧模块
│   ├── Red / IR 原始采样
│   ├── PPG
│   ├── SpO2
│   └── PR
│
├── 血压模块
│   ├── 测量状态
│   ├── 实时压力
│   ├── SYS
│   ├── DIA
│   └── PR / Error
│
├── 血氧独立显示屏
├── 血压独立显示屏
├── CAN → Gateway-C
└── ESP8266-A（调试 / 冷备用预留）
```

## 4.2 Node-B

Node-B 负责成员 B 的两个实体模块，同时运行 P 提供的 RR 算法：

```text
Node-B / STM32F407-B
├── 体温模块
│   └── TEMP
│
├── ADS1292R 心率/ECG模块
│   ├── ECG
│   ├── HR
│   └── RESP_RAW
│
├── P 负责的 RR 算法
│   └── RESP_RAW → RR
│
├── 体温独立显示屏
├── ECG / HR / RESP / RR 显示屏
├── CAN → Gateway-C
└── ESP8266-B（调试 / 冷备用预留）
```

## 4.3 Gateway-C

Gateway-C 负责：

- 接收 Node-A、Node-B 数据；
- 统一设备状态；
- 统一数据格式；
- 识别节点离线；
- 数据上传；
- 断网缓存；
- 网络恢复后的历史数据补传；
- 与腾讯云建立安全连接。

Gateway-C **不重新执行血氧、血压、ECG、体温等传感器底层解析**。

## 4.4 云端与网页

云端负责：

- Gateway 身份识别；
- 数据接收；
- 实时转发；
- 状态管理；
- 必要的数据记录；
- 浏览器实时监护；
- 历史记录与后续扩展。

## 5.2 阶段 1 并行开发方式

> **术语说明**：本文中的“节点功能联调”仅指每块采集开发板内部完成自身两个模块与两块显示屏的联合运行，不表示 Node-A 与 Node-B 合并到同一块开发板。Node-A、Node-B 在当前阶段始终保持为两块独立 STM32F407 采集节点；两者只通过 CANopen 与 Gateway-C 通信。最终是否进行整机/单板集成，留到后续样机阶段单独评审。


传感器开发和云端开发互不等待，可同步推进：

```mermaid
flowchart TB
    START["G0 方案冻结"]
    START --> HW["A / B：传感器单模块开发"]
    START --> CLOUD["P：云端先行开发"]

    HW --> A1["A：AFE4490 血氧 + NIBP"]
    HW --> B1["B：TEMP + ECG/HR/RESP_RAW"]

    CLOUD --> C1["Nginx / Backend / Web"]
    C1 --> C2["Mock MQTT Gateway / Publisher 模拟数据链路"]

    A1 --> NODE["Node-A、Node-B 独立节点功能联调"]
    B1 --> NODE
    C2 --> READY["云端接口待真实 Gateway 接入"]

    NODE --> GW["CANopen 双节点通信 + Gateway-C 汇聚联调"]
    READY --> GW
    GW --> REAL["ESP8266-C → MQTT/TLS → 腾讯云真实联调"]
```

因此 P **无需等待 A/B 完成传感器**。在真实 Gateway-C 尚未完成前，由 Mock MQTT Publisher 产生模拟 ECG、PPG、SpO2、NIBP、TEMP、RR 和节点状态数据，先把 MQTT Broker、Backend、Nginx、WebSocket 和 Web 大屏打通。后续只需要将模拟发布端替换为真实 Gateway-C。

## 5.3 开发原则

项目采用：

> **方案先冻结；硬件模块与云端可并行；单模块先打通；再分别完成 Node-A、Node-B 节点内功能联调；随后进行 CANopen 双节点通信与 Gateway-C 汇聚联调；最后完成真实设备上云和整体测试。**

禁止在没有单模块测试依据的情况下，同时调试四个传感器、CAN、ESP8266 和云端真实链路。

# 6. 系统方案设计

## 6.1 正常工作主链路

系统按四个逻辑区域排列：**采集节点 → 中央网关 → 云端 → 浏览器终端**。

```mermaid
flowchart TB

    subgraph ACQ["① 采集节点"]
        direction TB

        subgraph NA["成员 A / Node-A · STM32F407-A"]
            direction TB
            AFE["AFE4490 Arduino 血氧模块<br/>SPI + DRDY/控制信号<br/>PPG / SpO2 / PR"]
            NIBP["HKB-08 血压模块<br/>UART<br/>NIBP"]
            SA["血氧显示屏"]
            SB["血压显示屏"]
            AFE --> SA
            NIBP --> SB
        end

        subgraph NB["成员 B / Node-B · STM32F407-B"]
            direction TB
            TEMP["GY-641V3 体温模块<br/>I2C<br/>TEMP"]
            ECG["ADS1292R<br/>SPI + DRDY/控制信号<br/>ECG / HR / RESP_RAW"]
            RR["P 负责 RR 算法<br/>输入：RESP_RAW"]
            SC["体温显示屏"]
            SD["ECG / HR / RESP / RR 显示屏"]
            TEMP --> SC
            ECG --> SD
            ECG -->|"RESP_RAW"| RR
            RR --> SD
        end
    end

    subgraph GWZONE["② 中央网关"]
        direction TB
        GWC["Gateway-C 主控<br/>STM32F407-C<br/>CANopen 汇聚 / MQTT Client / 离线缓存"]
        ES["ESP8266-C<br/>Wi-Fi / TCP / TLS 网络接口"]
        GWC -->|"UART / AT"| ES
    end

    subgraph CLOUD["③ 腾讯云"]
        direction TB
        MQ["MQTT Broker<br/>Mosquitto / 兼容 Broker<br/>MQTT over TLS"]
        BE["Backend<br/>订阅 / 状态 / 记录 / WebSocket 推送"]
        NG["Nginx :443<br/>HTTPS / WebSocket / Reverse Proxy"]
        MQ --> BE
        BE <--> NG
    end

    subgraph VIEW["④ 用户终端"]
        WEB["PC / 浏览器 Web 大屏"]
    end

    NA -->|"CANopen / CAN"| GWC
    NB -->|"CANopen / CAN"| GWC
    ES -->|"Wi-Fi → 路由器/AP → Internet → MQTT/TLS"| MQ
    NG <-->|"HTTPS / WebSocket"| WEB
```

主数据路径按顺序理解为：

```text
Node-A / Node-B
        ↓  CANopen over CAN
STM32F407-C（Gateway-C 主控）
        ↓  UART / AT
ESP8266-C（Gateway-C 网络接口）
        ↓  Wi-Fi / Internet
MQTT over TLS
        ↓
腾讯云 MQTT Broker
        ↓
Backend
        ↓
Nginx / WebSocket
        ↓
PC / Browser Web 大屏
```

其中 **Gateway-C 是一个完整网关节点，STM32F407-C 是网关主控，ESP8266-C 只提供网络连接能力**。设备侧数据汇聚由 CANopen 完成，云端遥测采用标准 MQTT，不再另行设计自定义的板间或云端通用通信协议。

> **当前硬件关系保持不变**：Node-A、Node-B、Gateway-C 分别为三块独立 STM32F407 开发板。CANopen 的作用是让 Node-A、Node-B 同时与 Gateway-C 通信和汇聚数据，不代表把 A/B 两个节点合并到同一块开发板。

## 6.2 系统层次

系统分为五层：

```text
传感器层
    ↓
Node-A / Node-B 采集与本地显示层
    ↓
CANopen 板间通信层
    ↓
Gateway-C 网络网关层
    ↓
腾讯云 + Web 应用层
```

这样可以保证：

- 本地显示不依赖云端；
- PC 不是系统网关；
- Gateway-C 是正常网络出口；
- Node-A/B 与云端实现解耦；
- 后续最终样机集成时，CANopen 对象字典、MQTT 数据模型和 Web 架构可以继续复用。

# 7. 软硬件接口设计

本阶段只冻结接口类型，不冻结具体任务调度方式。

## 7.1 Node-A 接口

| 模块 | 主要接口 |
|---|---|
| AFE4490 Arduino 血氧模块 | **SPI + DRDY/控制信号** |
| 血压 HKB-08 | UART |
| 两块本地显示屏 | UART |
| Gateway-C | CAN |
| ESP8266-A | UART |

AFE4490 已正式替代此前考虑过的 HKS UART 成品模组路径。当前只冻结接口关系：

```text
指夹血氧探头
    ↓
AFE4490 模拟前端
    ↓ SPI + 数据就绪/控制信号
STM32F407-A
    ↓
PPG / SpO2 / PR
```

AFE4490 是血氧模拟前端，Node-A 需要读取红光/红外采样并形成 PPG、SpO2 和 PR。具体寄存器、采样时序和算法参数进入成员 A 的《AFE4490 血氧模块详细设计与测试记录》，不在总合同中提前冻结。


## 7.2 Node-B 接口

| 模块 | 主要接口 |
|---|---|
| ADS1292R | SPI + DRDY/控制信号 |
| 体温 GY-641V3 | I2C |
| 两块本地显示屏 | UART |
| Gateway-C | CAN |
| ESP8266-B | UART |

其中：

- ADS1292R 提供 ECG/HR 所需数据；
- ADS1292R 同时提供 RESP_RAW；
- RESP_RAW 是 P 的 RR 算法输入。

## 7.3 Gateway-C 接口

| 对象 | 主要接口 |
|---|---|
| Node-A | CAN |
| Node-B | CAN |
| ESP8266-C | UART |
| 腾讯云 | 通过 ESP8266-C 建立 MQTT/TLS 网络连接 |
| 离线缓存 | 优先使用现有板载存储资源，具体容量在详细设计阶段确认 |

## 7.4 软件框架原则

本系统方案阶段 **不强制指定 FreeRTOS 或裸机**。

只要求软件最终满足：

- 多模块并行采集；
- 显示不阻塞传感器采集；
- CAN 通信不影响采集；
- 网络故障不影响本地监护；
- 错误状态可以恢复；
- 可完成规定的稳定性测试。

具体软件框架由成员在详细设计阶段根据模块代码、开发板资源和实测结果确定，并提交模块设计说明。

# 8. 通信协议总体规划

调整通信原则：

> **优先复用公开、成熟、具备工业生态和现成协议栈的标准协议，不再自行设计通用通信协议。**

项目仍需自行定义的内容，仅限于本系统特有的 **生理参数数据字典、对象映射、MQTT Topic 与 Payload 语义**，而不再重新实现网络管理、心跳、可靠传输、发布订阅等通用机制。

## 8.1 协议选型

| 通信链路 | 采用协议 | 主要原因 |
|---|---|---|
| Node-A / Node-B → Gateway-C | **CANopen CC（CiA 301） over Classic CAN** | 工业成熟、对象字典完善，已有 PDO/SDO/NMT/Heartbeat/EMCY 等机制，适合 STM32 节点网络 |
| Gateway-C → 腾讯云 | **MQTT 3.1.1 over TLS** | OASIS 标准，发布/订阅生态成熟，支持 QoS、Will、Retain，适合遥测和设备状态 |
| Backend → Browser | **HTTPS + WebSocket** | 浏览器原生支持，Nginx 生态成熟，适合实时波形和状态推送 |
| 历史查询 / 配置类接口 | **HTTPS / REST** | 通用、易调试，适合低频查询和管理接口 |

CANopen 已广泛用于工业嵌入式网络，CiA 官方也列出医疗设备等应用领域；MQTT 3.1.1 是 OASIS 标准协议，具有成熟 Broker、客户端库和调试工具生态。

本项目选择标准协议的核心考虑为：

- **CANopen**：复用成熟的网络管理、心跳、故障和对象访问机制，减少自定义 CAN 应用层协议带来的兼容与维护风险；
- **MQTT**：复用成熟 Broker、QoS、Last Will、Retain 和客户端生态，降低设备上云与断线恢复的开发风险；
- **HTTPS / WebSocket**：直接使用浏览器和 Nginx 现成生态，不再维护专用浏览器协议。


## 8.2 传感器内部接口

传感器厂家接口仍只存在于对应 Node 内部：

- AFE4490 Arduino 血氧模块：SPI + 数据就绪/控制信号；
- ADS1292R：SPI + DRDY/控制信号；
- HKB-08：UART；
- GY-641V3：I2C。

Node 内部完成厂家协议解析与算法处理后，再转换为统一的项目数据对象。Gateway-C 和云端不直接解析传感器寄存器或厂家私有帧。

## 8.3 Node 到 Gateway：CANopen

Node-A、Node-B 与 Gateway-C 之间采用 **CANopen CC / CiA 301**。

角色初步划分：

- Gateway-C：CANopen 网络管理与数据汇聚节点；
- Node-A、Node-B：CANopen 设备节点。

优先复用 CANopen 标准机制：

- **PDO**：ECG、PPG、SpO2、NIBP、TEMP、HR、RR 等实时过程数据；
- **SDO**：参数配置、诊断与非实时数据访问；
- **NMT**：节点启动、停止和运行状态管理；
- **Heartbeat**：节点在线状态检测；
- **EMCY**：关键节点故障或异常事件；
- **Object Dictionary**：统一组织设备通信参数和项目生理参数。

本项目仍需要建立一份简化的 **CANopen 应用对象字典**，定义 ECG、HR、RESP、RR、PPG、SpO2、PR、NIBP、TEMP、数据有效性等业务对象。具体 Index、Sub-index 和 PDO 映射在《CANopen 对象字典与 PDO 映射设计》中确定，本总方案不提前写死。

## 8.4 Gateway 到云端：MQTT over TLS

Gateway-C 到腾讯云采用 **MQTT 3.1.1 over TLS**。

云端部署标准 MQTT Broker，例如 Eclipse Mosquitto 或兼容实现。Gateway-C 作为 MQTT Client：

```text
STM32F407-C
    ↓ MQTT Client
ESP8266-C
    ↓ SSL/TLS Socket
Internet
    ↓
MQTT Broker
```

ESP8266-C 继续承担 Wi-Fi、TCP 和 TLS 网络连接；MQTT 协议逻辑由 Gateway-C 软件统一管理。这样可以继续复用 ESP8266 的 SSL Client 能力，而不依赖其特定厂商 MQTT AT 命令。

初步通信规则：

- 高频波形数据：优先使用较低开销的发布策略；
- 关键数值、状态、测量结果：优先采用 **QoS 1**；
- Gateway 在线状态：使用 MQTT **Last Will**；
- 最新设备状态：可使用 **Retain**；
- 离线缓存补传与实时数据需要在 Topic 或 Payload 中明确区分。

具体 Topic、QoS 分配和 Payload 格式在 Gateway 详细设计阶段冻结。

## 8.5 云端到浏览器：HTTPS + WebSocket

浏览器侧不再定义自有 MVIEW 协议。

采用：

- HTTPS：页面、REST API、历史查询；
- WebSocket：实时波形、参数和设备状态推送；
- JSON：低频参数和状态；
- Binary WebSocket：高频波形可按实际性能需要采用。

Nginx 继续负责 Web HTTPS、WebSocket 反向代理和静态页面发布。

## 8.6 项目数据字典

采用标准协议后，项目仍然需要定义自己的业务数据字典，因为 CANopen 和 MQTT 负责“如何通信”，不会自动定义“SpO2、RR、NIBP 在本项目中是什么意思”。

数据字典只需统一以下信息：

- 参数名称；
- 数据来源；
- 单位；
- 数据类型；
- 有效 / 无效 / 离线等状态；
- 时间信息；
- 算法版本或必要来源信息。

主要对象包括：

```text
ECG / HR
RESP / RR
PPG / SpO2 / PR
NIBP
TEMP
Node / Gateway Status
Fault / Alarm
```

同一份数据字典同时映射到：

```text
CANopen Object Dictionary
        ↓
Gateway 内部数据模型
        ↓
MQTT Topic / Payload
        ↓
Backend / Web
```

这样即使未来更换物理链路或云端实现，生理数据语义仍保持一致。

## 8.7 标准协议实施原则

1. 优先采用成熟开源协议栈或官方兼容实现，避免自行重写 CANopen、MQTT、WebSocket 核心协议；
2. P 统一维护 CANopen 对象字典和云端数据字典；
3. A/B 只按照冻结的数据对象和 CANopen 映射实现节点；
4. 云端优先使用标准 MQTT Broker 和现成客户端生态；
5. 不在总合同阶段提前冻结 CANopen Index、PDO 字节布局、MQTT Topic 全量结构和二进制 Payload。

协议栈实现优先评估成熟开源项目，例如 CANopenNode、Eclipse Paho Embedded C、Eclipse Mosquitto 等；具体库版本在详细设计和许可证审查后确定，不在本合同中锁定。

# 9. 呼吸率 RR 设计

## 9.1 数据来源

RR 原始数据明确来源于成员 B 所负责的 **ADS1292R 心率/ECG 模块中的呼吸阻抗原始通道**。

```text
ADS1292R
   ↓
RESP_RAW
   ↓
P 的 RR 算法
   ↓
RESP / RR
```

因此：

- B 不需要额外采购独立呼吸传感器；
- B 负责保证 RESP_RAW 可用；
- P 负责将 RESP_RAW 转换为 RR。

## 9.2 P 的 RR 工作内容

P 负责：

1. 对 RESP_RAW 进行数据分析；
2. 设计必要的预处理；
3. 设计呼吸周期检测方法；
4. 输出 RR；
5. 对无效信号、导联脱落和明显异常数据进行质量判断；
6. 先建立 PC/Python 参考算法；
7. 再形成可在 STM32 上运行的算法版本；
8. 与 B 共同完成 Node-B 集成；
9. 负责最终算法验收。

本阶段不在总合同中提前冻结：

- 滤波器具体阶数；
- FFT 窗口长度；
- 峰值阈值；
- RR 最终算法参数。

这些内容由 P 在取得真实 RESP_RAW 数据后形成《RR 算法设计与验证报告》。

# 10. Gateway-C 与云端设计

## 10.1 Gateway-C

Gateway-C 是正常运行时唯一的公网出口。

```text
Node-A ─┐
        ├── CANopen → Gateway-C → ESP8266-C → MQTT/TLS → Cloud
Node-B ─┘
```

职责：

- 作为 CANopen 汇聚节点接收 Node-A / Node-B 数据；
- 管理节点状态和必要的 SDO/NMT 操作；
- 将 CANopen 对象转换为统一云端数据模型；
- 运行 MQTT Client；
- 管理 ESP8266-C 网络连接；
- 断网缓存；
- 网络恢复后的补传。

## 10.2 腾讯云

使用现有腾讯云服务器与域名资源。

推荐云端结构：

```text
Gateway-C
    ↓
ESP8266-C
    ↓
MQTT over TLS
    ↓
MQTT Broker
    ↓
Backend
    ↓
WebSocket
    ↓
Nginx
    ↓
Web Browser
```

MQTT Broker 负责设备消息接入；Backend 订阅相关 Topic 后完成状态管理、记录和网页推送。

## 10.3 MQTT Broker

优先采用成熟 Broker，例如：

- Eclipse Mosquitto；
- 或后续根据规模更换为其他兼容 MQTT 3.1.1/5.0 的 Broker。

一期优先满足：

- TLS；
- 客户端认证；
- Topic ACL；
- Last Will；
- QoS；
- 日志和基本运行监控。

## 10.4 Nginx

Nginx 继续作为 **Web 入口**，负责：

- HTTPS；
- WebSocket 反向代理；
- 前端静态页面；
- Backend REST API；
- 基本访问控制与日志。

MQTT 标准 TLS 入口优先由 MQTT Broker 提供（常用端口 8883）。如后续运维需要统一入口，再评估 Nginx Stream 代理，不作为当前必需条件。

# 11. Gateway-C 离线缓存

## 11.1 目标

应对：

- WAN 临时中断；
- 路由器重启；
- 腾讯云短时不可达；
- Nginx / Backend 临时维护。

## 11.2 工作逻辑

```text
网络正常
  ↓
实时上传

网络中断
  ↓
Gateway-C 本地缓存

网络恢复
  ↓
实时数据继续优先上传
  +
历史缓存低优先级补传
```

MQTT Topic 或 Payload 必须能够区分：

```text
LIVE
REPLAY
```

具体缓存容量、Flash 布局和记录格式在 Gateway-C 详细设计阶段确定。

# 12. 备用方案

## 12.1 A/B ESP8266 MQTT/TLS 冷备用

正常模式：

```text
Node-A ─┐
        ├── CANopen → Gateway-C → ESP-C → MQTT/TLS → Cloud
Node-B ─┘
```

若 Gateway-C 故障，后续可启用：

```text
Node-A → ESP-A ─┐
                ├── MQTT/TLS → Cloud
Node-B → ESP-B ─┘
```

冷备用仍复用同一 MQTT Broker、Topic 体系和项目数据字典，不再维护第二套自定义公网协议。

该方案本期：

> **保留接口与软件扩展位置，不作为一期强制完成项。**

## 12.2 备用链路原则

备用链路的目的主要是绕过 Gateway-C 单点故障，而不是再引入一套不同通信协议。

因此当前原则为：

- 主链路和冷备用均使用 MQTT/TLS；
- 通过 Gateway/Node 身份和数据来源字段避免重复记录；
- 是否自动切换、切换等待时间和恢复策略在可靠性阶段再确定；
- 若未来需要真正的网络介质冗余，再考虑 4G/5G 等第二网络链路。
