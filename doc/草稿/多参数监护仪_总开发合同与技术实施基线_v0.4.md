## 0. 合同定位、执行优先级与角色定义

### 0.1 合同定位

本文件同时作为：

1. 项目总开发合同；
2. 三人团队研发任务书；
3. 软硬件接口控制基线；
4. 阶段验收与交付基线；
5. Git 仓库中的配置项与变更控制依据。

- 四个生理监护模块如何由两名嵌入式成员分工开发；
- 四块本地显示屏如何分配；
- 两块采集 STM32F407 如何汇聚到第三块 Gateway-C STM32F407；
- Node-A / Node-B 与 Gateway-C 之间采用何种总线；
- Gateway-C 如何通过 ESP8266 安全上传腾讯云；
- Nginx、后端、WebSocket 与网页大屏如何分层；
- `MMP-BUS/1`、`MMP/2`、`MVIEW/1` 三层协议如何定义；
- 如何处理断网缓存、重连、重复帧、离线节点与备用链路；
- 如何以可复现测试结果判断是否进入最终单板样机集成阶段。

## 1.3 市场调研结论

本项目首版定位冻结为：

> **“多参数生理信号采集 + 本地模块化显示 + 中央网关汇聚 + 云端实时监护大屏”的工程验证平台。**

当前不以“医疗器械注册、临床诊断准确率、医院 HIS/EMR 正式接入、除颤防护等级、医用 BF/CF 分类认证”为验收目标。

本项目的核心工程价值不是单个传感器本身，而是：

1. 多模块并行采集；
2. MCU 间标准化通信；
3. 网络协议统一；
4. 断网与节点失效可识别；
5. 云端与本地解耦；
6. 可逐步扩展为最终整机样机。

# 2. 需求分析

## 2.1 当前已确认硬件与团队约束

### 2.1.1 团队与模块

- 成员 A 负责两个实体模块：**血氧 SpO2/PPG/PR**、**无创血压 NIBP**；
- 成员 B 负责两个实体模块：**体温 TEMP**、**心率模块 ADS1292R（ECG/HR）**；
- ADS1292R 同时提供呼吸阻抗原始通道 `RESP_RAW`，其硬件采集由 B 负责；
- 项目负责人 P 负责 **呼吸率 RR 算法**：RESP 预处理、`RESP_FILTERED`、RR 时域/频域估计、RR 信号质量、Python Reference、C 算法版本和算法验收；
- 项目负责人 P 同时继续负责 **Gateway-C、统一协议、云端、网页大屏、系统集成项目管理**。

### 2.1.2 开发板

当前规划使用三块 STM32F407：

```text
STM32F407-A：成员 A 采集节点
STM32F407-B：成员 B 采集节点
STM32F407-C：项目负责人中央网关 Gateway-C
```

### 2.1.3 显示屏

当前共有四块显示屏，冻结为 **四个实体模块各一块屏幕**：

```text
Node-A / 成员 A
├── SpO2/PPG/PR → Screen-A1
└── NIBP        → Screen-A2

Node-B / 成员 B
├── TEMP        → Screen-B1
└── ECG/HR/RESP/RR → Screen-B2
```

其中 `RR` 算法产权与实现责任属于 P，但运行时算法库集成在 Node-B，使 Gateway-C 或云端故障时 Screen-B2 仍能显示本地 RR。

因此每块采集 STM32F407 必须同时驱动两块显示屏。

### 2.1.4 Wi-Fi 模块

- Node-A：ESP8266-A，开发和独立调试使用；后续预留冷备用直连云端能力；
- Node-B：ESP8266-B，开发和独立调试使用；后续预留冷备用直连云端能力；
- Gateway-C：ESP8266-C，作为正常运行时唯一公网出口。

## 2.3 非功能需求

### 2.3.1 稳定性

- 任一浏览器关闭，不影响采集与上云；
- 项目负责人的个人电脑关闭，不影响采集与上云；
- Node-A 或 Node-B 离线时，另一节点继续工作；
- 云端不可用时，本地四块显示屏仍能工作；
- Gateway-C 与云端断开时进入缓存状态而不是伪造数据；
- 网络恢复后实时数据优先，历史数据低优先级补传。

### 2.3.2 数据真实性

禁止以下行为：

- 无效值填充为正常值；
- 探头脱落仍显示最近一次值且不标记陈旧；
- 丢帧后通过插值制造“看起来连续”的原始医疗波形；
- 把回放数据作为实时数据触发当前告警；
- 将不同来源的 HR / PR 混成一个字段而不标来源。

### 2.3.3 性能

纠偏报告给出了原始遥测与 FIR 滤波支路的理论预算。由于目前没有提交完整端到端实测数据，本合同将其定义为 **验收目标**，而非“当前已达成指标”：

| 指标 | 验收目标 |
|---|---:|
| 原始遥测链路发送 → 云端前端入队 P95 | **≤ 200 ms** |
| 129-tap FIR 滤波显示综合端到端 P95 | **≤ 500 ms** |
| 本地屏关键数值刷新 | ≤ 500 ms |
| Node 心跳周期 | 500 ms |
| Node Stale 判定 | > 1.5 s 未收到有效心跳 |
| Node Offline 判定 | > 3 s 未收到有效心跳 |
| 云端 WebSocket 心跳 | 20 s 建议周期 |
| 系统稳定性连续测试 | ≥ 24 h |

### 2.3.4 安全

- 公网仅开放 80/443；
- 80 仅用于 ACME/HTTPS 跳转；
- 后端业务端口不得直接暴露公网；
- 所有公网实时数据走 TLS/WSS；
- 公网不提供远程启动 NIBP 加压等危险控制；
- 密钥不得硬编码提交到 Git；
- 不以本工程样机替代医疗诊断设备。

# 3. 功能设计

## 3.1 Node-A 功能

```text
Node-A / STM32F407-A / 成员 A
│
├── HKS 血氧模块（当前暂定）
│   ├── PPG
│   ├── SpO2
│   └── PR
│
├── HKB-08 系列 NIBP
│   ├── 实时袖带压力
│   ├── SYS
│   ├── DIA
│   ├── PR
│   ├── Arrhythmia Flag
│   └── Error Code
│
├── Screen-A1：SpO2/PPG/PR
├── Screen-A2：NIBP
├── CAN：MMP-BUS/1 → Gateway-C
├── ESP8266-A：独立联调 / 冷备用预留
└── Debug UART
```

### 3.1.1 血氧模块当前状态

血氧实物当前暂按 **HKS 智能模组路径**开发，但型号仍需通过 PCB 丝印、购买链接或芯片近照最终冻结。

若最终确认 HKS-12C：

```text
HKS → UART 115200 8N1 → STM32F407-A
```

若实际为 AFE4490 类方案，则必须触发变更单，改为 SPI + PPG / SpO2 算法工作包，重新评估成员 A 工期。

## 3.2 Node-B 功能

```text
Node-B / STM32F407-B / 成员 B
│
├── ADS1292R 心率/心电模块
│   ├── ECG_RAW
│   ├── ECG_FILTERED
│   ├── HR
│   └── RESP_RAW          ← B 负责可靠采集
│
├── P 提供 RR Algorithm Library
│   ├── RESP_FILTERED
│   ├── RR
│   ├── RR_QUALITY
│   └── RESP_ALGO_VERSION
│
├── GY-641V3 TEMP
│   ├── To
│   ├── Ta
│   └── Bo
│
├── Screen-B1：TEMP
├── Screen-B2：ECG/HR/RESP/RR
├── CAN：MMP-BUS/1 → Gateway-C
├── ESP8266-B：独立联调 / 冷备用预留
└── Debug UART
```

### 3.2.1 RR 算法责任边界

```text
B：ADS1292R CH1 → RESP_RAW
                     │
                     ▼
P：Preprocess → RESP_FILTERED → Peak/FFT/SQI → RR
                     │
                     ▼
B：将 P 冻结的 C 算法库集成到 Node-B
                     │
            ┌────────┴────────┐
            ▼                 ▼
        Screen-B2         MMP-BUS/1
```

P 对 RR 算法结果负责，B 对算法运行环境、输入数据完整性和固件集成负责。B 不得未经 P 评审自行修改 RR 算法阈值、滤波频带、窗口长度或算法版本。

## 3.3 Gateway-C 功能

Gateway-C 不参与生理算法计算，职责冻结为：

```text
Gateway-C / STM32F407-C
│
├── 接收 Node-A CAN 数据
├── 接收 Node-B CAN 数据
├── 节点心跳与在线状态判定
├── 数据序号 / 丢帧 / 重复检查
├── CAN → MMP/2 网络封装
├── 时间同步与统一时间戳
├── Gateway 离线缓存
├── 实时优先 + REPLAY 低优先级补传
├── ESP8266-C AT 状态机
├── WSS/WebSocket Client
└── Gateway 状态日志
```

Gateway-C **不得**重新解释 HKS、HKB、ADS1292R、GY-641V3 的供应商原始私有协议。

## 3.4 云端功能

```text
Nginx
├── HTTPS 静态网页
├── WSS Gateway Ingest
├── WSS Browser Monitor
└── REST API Reverse Proxy
        ↓
Backend
├── Gateway 鉴权
├── MMP/2 解析
├── 去重 / 状态管理
├── 实时 WebSocket Hub
├── Recording
├── REPLAY 入库
└── Device / Node / Stream Health
```

## 3.5 Web 大屏功能

网页至少展示：

- ECG 波形；
- HR；
- RESP / RR（在该模块验证通过后）；
- PPG；
- SpO2；
- PR；
- NIBP SYS/DIA/最近测量时间/测量状态；
- TEMP；
- Gateway-C Online/Offline；
- Node-A Online/Stale/Offline；
- Node-B Online/Stale/Offline；
- 数据质量 / 探头脱落 / 测量中；
- LIVE / REPLAY 明确标签；
- 网络与数据最后更新时间。

## 4.2 架构原则

### 4.2.1 PC 不作为网关

PC 仅作为浏览器查看终端。PC 关闭、更新、休眠或崩溃，不得影响生理数据采集与上云。

### 4.2.2 Gateway-C 是正常上云唯一出口

正常运行时：

```text
Node-A ─┐
        ├── CAN → Gateway-C → ESP8266-C → WSS → Cloud
Node-B ─┘
```

Node-A / Node-B 的 ESP8266-A/B 不同时向云端上传，避免重复数据、三套网络状态机和多源冲突。

### 4.2.3 云端故障不影响本地屏

本地屏显示的数据直接来自各 Node，不依赖 Gateway-C、路由器、腾讯云或 PC。

### 4.2.4 协议分层

```text
传感器私有协议
    ↓
Sensor Driver
    ↓
统一物理量 / 状态模型
    ↓
MMP-BUS/1（CAN）
    ↓
Gateway-C
    ↓
MMP/2（WSS/TLS）
    ↓
Backend
    ↓
MVIEW/1（WSS）
    ↓
Browser
```

### 5.2.1 ADS1292R 强制约束

根据纠偏报告：

- `PD0` / `PD1` 分别作为 ADS1292R `CS` / `START`；
- STM32 工程中必须关闭 FSMC；
- 禁止初始化外部 SRAM/FSMC；
- `RCC->AHB3ENR` 的 `FSMCEN` 保持关闭；
- 若未来必须启用 FSMC，必须重新分配 ADS1292R 控制引脚并触发变更评审。

## 5.4 CAN 物理层

### 5.4.1 参数

- CAN：Classic CAN 2.0A；
- 标准 11-bit Identifier；
- 初始速率：**500 kbit/s**；
- 拓扑：线型总线，禁止星型长支路；
- 总线两端各 120 Ω 终端电阻；

- 示波器/逻辑分析仪实测 CANH/CANL 后方可进入长时间测试。

## 5.5 本地显示屏

四块显示屏必须先确认物理电平：

- TTL 屏：可在确认 I/O 电压兼容后直连 STM32 UART；

### 5.6.2 P-RR 呼吸率算法工作包

P 为 RR 算法唯一主责人，工作包至少包括：

```text

P-RR-02  呼吸信号预处理
P-RR-03  RESP_FILTERED 生成
P-RR-04  时域峰谷/周期检测
P-RR-05  频域 RR 估计
P-RR-06  Signal Quality / Lead-Off / Motion Artifact 判定
P-RR-07  Python Reference Algorithm
P-RR-08  STM32 C Algorithm Library
P-RR-09  与参考算法一致性测试
P-RR-10  算法版本号与协议字段维护
```

第一版工程候选参数：

- ADS1292R `RESP_RAW`：250 SPS；
- 预处理目标频带：约 0.10~1.20 Hz（工程候选，需实测冻结）；
- 算法内部可降采样至约 25 SPS；
- 默认滑动窗口：30 s；
- 更新步长：1 s；
- 时域估计为主、频域估计为辅；
- `RR_TIME` 与 `RR_FREQ` 一致性用于质量判定；
- 参数均属于工程候选，不作为临床阈值。

算法开发顺序：

```text
真实 RESP_RAW
→ Python Reference
→ 可视化/参数冻结
→ C Library
→ Node-B 集成
→ Python vs STM32 对照
→ Screen-B2 / CAN / Cloud
```

P 发布算法时必须提供：

```text
resp_algo.h
resp_algo.c
算法版本号
参数配置
Python reference
固定输入样例
期望输出
单元测试
变更记录
```

B 负责集成，不负责擅自改变算法定义。

# 6. 通信协议总规范

# 6.1 协议分层总览

| 层级 | 协议 | 作用 |
|---|---|---|
| 传感器层 | ADS1292R SPI / HKS UART / HKB UART / GY I2C | 只存在于各 Node 驱动内部 |
| 板间总线 | **MMP-BUS/1 over CAN** | Node-A / Node-B → Gateway-C |
| 公网设备协议 | **MMP/2 over WSS/TLS** | Gateway-C → 云端；备用时 Node-A/B 可复用 |
| 浏览器协议 | **MVIEW/1 over WSS** | Backend → Web Browser |

> `MMP/1` 为历史版本。本合同自 v0.4 起继续冻结为 `MMP-BUS/1 + MMP/2`。纠偏报告中关于端序、校验和、算法延迟等技术结论继续生效，但网络协议名称与封包格式统一迁移至 MMP/2。

## 6.2 传感器层关键冻结项

### 6.2.1 ADS1292R

- SPI1；
- 250 SPS 基准采样；
- 每个 DRDY 读取 9 字节；
- Byte 0~2 状态；Byte 3~5 RESP；Byte 6~8 ECG；
- 24 位有符号补码解析；
- 129-tap FIR 为当前基准滤波方案，但其 256 ms 群延迟单独计入显示链路。

### 6.2.2 HKS 血氧（暂定）

历史 `FF C7 03 CD A0` 中的 `0xCD` 不作为合法固定校验和。

标准动态校验：

```c
CKSUM = (Length + Command + Sum(Parameters)) & 0xFF;
```

当前标准启动候选帧：

```text
FF C7 03 A3 A0
```

G1 必须执行：

```text
Test-1: FF C7 03 A3 A0
Test-2: FF C7 03 CD A0
```

并对模块返回的周期帧反算校验和。**实物抓包结果是最终驱动冻结依据。**

### 6.2.3 GY-641V3

I2C：

```text
7-bit address = 0x52
8-bit write   = 0xA4
8-bit read    = 0xA5
```

原始传感器字节采用 **Big-Endian / MSB First**，必须按 `int16_t` 解析负温补码：

```c
int16_t to_raw = (int16_t)(((uint16_t)raw[1] << 8) | raw[2]);
int16_t ta_raw = (int16_t)(((uint16_t)raw[3] << 8) | raw[4]);
int16_t bo_raw = (int16_t)(((uint16_t)raw[5] << 8) | raw[6]);
```

进入 MMP-BUS/1 与 MMP/2 后统一转换为 **Little-Endian**。

### 6.2.4 HKB-08 NIBP

已冻结候选基础参数：

```text
UART 115200 8N1
Start:     FF C0 03 A3 A0
Stop:      FF C0 03 A4 A1
Emergency: FF 00
```

公网云端禁止直接触发 Start / Emergency；这些控制保持本地优先。

# 7. MMP-BUS/1 —— Node 到 Gateway 的 CAN 协议

## 7.1 设计原则

MMP-BUS/1 不复制 MMP/2 的大帧头，而利用 CAN ID 表达流类型，以降低板间开销。

所有多字节字段统一 **Little-Endian**。

### 7.1.1 CAN ID 规划

| CAN ID | 来源 | 数据流 | 优先级说明 |
|---:|---|---|---|
| `0x060` | Node-A | Heartbeat / Health | 高 |
| `0x061` | Node-B | Heartbeat / Health | 高 |
| `0x070` | Node-A | Alarm / Fault | 高 |
| `0x071` | Node-B | Alarm / Fault | 高 |
| `0x100` | Node-B | ECG + RESP Raw | 实时高频 |
| `0x110` | Node-B | HR + RR + RR Quality | 中 |
| `0x120` | Node-A | PPG + SpO2 + PR | 实时 |
| `0x200` | Node-A | NIBP Pressure | 实时 |
| `0x210` | Node-A | NIBP Result | 事件 |
| `0x220` | Node-B | TEMP | 低频 |
| `0x300` | Gateway-C | Broadcast Time Sync | 管理 |
| `0x310` | Gateway-C | Node-A Management | 管理 |
| `0x320` | Gateway-C | Node-B Management | 管理 |
| `0x3F0`~`0x3FF` | 任意 | Debug / Reserved | 开发期 |

> ID 冻结后不得由成员自行修改。新增数据流必须提交协议变更单。

## 7.2 数据帧定义

### 7.2.1 `0x100` ECG + RESP Raw

```text
Byte 0      sample_seq_u8
Byte 1..3   ecg_s24_le
Byte 4..6   resp_s24_le
Byte 7      flags
```

`flags` 建议：

```text
bit0 LEAD_OFF
bit1 ECG_VALID
bit2 RESP_VALID
bit3 FILTER_ACTIVE
bit4..7 reserved
```

基准频率：250 frame/s。

### 7.2.2 `0x110` HR + RR

该帧由 **Node-B** 发出；`HR` 由 B 的 ECG/HR 模块产生，`RR` 由 P 的算法库产生。

```text
Byte 0      seq_u8
Byte 1      hr_bpm_u8
Byte 2      rr_bpm_u8
Byte 3      hr_quality_u8
Byte 4      rr_quality_u8
Byte 5      status_u8
Byte 6      resp_algo_version_u8
Byte 7      reserved
```

`resp_algo_version_u8` 由 P 维护。算法参数或实现发生影响结果的变更时必须升级版本号。

### 7.2.3 `0x120` PPG + SpO2 + PR

```text
Byte 0      seq_u8
Byte 1      ppg_u8
Byte 2      spo2_u8
Byte 3      pr_u8
Byte 4      quality_u8
Byte 5      sensor_status_u8
Byte 6..7   reserved
```

当 HKS `XY == 0xFF` 或 `PR == 0` 等无效状态出现时，必须通过 `sensor_status` 显式表示，云端不得按正常值显示。

### 7.2.4 `0x200` NIBP Pressure

```text
Byte 0      seq_u8
Byte 1..2   pressure_mmhg_u16_le
Byte 3      beat_flag_u8
Byte 4      measure_state_u8
Byte 5      error_code_u8
Byte 6..7   reserved
```

### 7.2.5 `0x210` NIBP Result

```text
Byte 0      seq_u8
Byte 1..2   sys_u16_le
Byte 3..4   dia_u16_le
Byte 5      pr_u8
Byte 6      flags_u8
Byte 7      error_code_u8
```

`MAP` 若模块未原生返回，可在 Gateway/Cloud 作为“派生值”计算，但必须标明 `derived=true`，不得伪装成传感器原生输出。

### 7.2.6 `0x220` TEMP

```text
Byte 0      seq_u8
Byte 1..2   To_x100_s16_le
Byte 3..4   Ta_x100_s16_le
Byte 5..6   Bo_x100_s16_le
Byte 7      status_u8
```

### 7.2.7 Heartbeat

```text
Byte 0..3   uptime_s_u32_le
Byte 4..5   health_flags_u16_le
Byte 6      fw_version_u8
Byte 7      heartbeat_seq_u8
```

周期：500 ms。

## 7.3 Gateway 节点状态判定

```text
最近心跳 <= 1.5 s        ONLINE
1.5 s < 最近心跳 <= 3 s STALE
最近心跳 > 3 s          OFFLINE
```

状态变化必须作为 Gateway Status / Event 上传云端。

## 7.4 CAN 错误与验收

验收必须覆盖：

- 单节点断开；
- 两节点同时恢复；
- CANH/CANL 反接；
- 终端电阻缺失；
- 高频 ECG 250 fps 下总线负载；
- Bus-Off 恢复；
- 重复帧与序号跳变；
- Gateway 重启后 Node 状态重新建立。

# 8. MMP/2 —— Gateway 到腾讯云的统一设备协议

## 8.1 传输层

正常主链路：

```text
STM32F407-C
    ↓ USART3 / AT
ESP8266-C
    ↓ SSL Socket
WSS / TLS 1.2+
    ↓
Nginx :443
    ↓
Backend /device/v1/ingest
```

ESP8266 仅承担：

- Wi-Fi；
- DNS；
- TCP；
- TLS/SSL Socket。

Gateway-C STM32 负责：

- HTTP Upgrade；
- WebSocket Client frame；
- MMP/2；
- 心跳；
- 重连；
- 断网缓存与 REPLAY。

> ESP8266 正常运行仅维持一个公网 TLS/WSS 连接，避免其受限内存下维护多 SSL 会话。

## 8.2 WebSocket 入口

```text
wss://<domain>/device/v1/ingest
```

握手至少包含：

```text
Host
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Version: 13
Sec-WebSocket-Key
Authorization: Device <gateway_id>:<device_token>
X-Gateway-ID: <gateway_id>
```

`device_token`：

- 至少 256-bit 随机值；
- 不提交 Git；
- 后端仅保存安全哈希或受控 Secret；
- 泄露后可单独轮换；
- 一台 Gateway 一个独立 Token。

## 8.3 MMP/2 二进制帧

MMP/2 统一采用 **Little-Endian**。

### 8.3.1 固定 40 字节 Header

| Offset | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 4 | `magic` | ASCII `MMP2` |
| 4 | 1 | `version` | `0x02` |
| 5 | 1 | `msg_type` | 消息类型 |
| 6 | 2 | `flags` | LIVE / REPLAY / FILTERED / UTC_SYNCED 等 |
| 8 | 4 | `gateway_id` | Gateway 逻辑 ID |
| 12 | 1 | `node_id` | A=1，B=2，Gateway=0 |
| 13 | 1 | `stream_id` | 数据流 |
| 14 | 2 | `quality` | 质量/状态位 |
| 16 | 4 | `boot_id` | 每次设备启动唯一标识 |
| 20 | 4 | `seq` | 每个 stream 单独递增 |
| 24 | 8 | `timestamp_ms` | UTC ms；未同步时配合 flag |
| 32 | 2 | `payload_len` | Payload 长度 |
| 34 | 2 | `sample_rate_hz` | 采样率 |
| 36 | 2 | `sample_count` | 本帧样本数 |
| 38 | 2 | `reserved` | 置 0 |

紧随其后：

```text
Payload[payload_len]
CRC32[4]
```

CRC32 覆盖：

```text
Header + Payload
```

TLS 负责公网传输机密性与强完整性；CRC32 用于应用层帧边界、错误数据和实现缺陷检测，不替代 TLS。

## 8.4 `msg_type`

| 值 | 类型 | 作用 |
|---:|---|---|
| `0x01` | HELLO | Gateway 上线与能力声明 |
| `0x02` | TELEMETRY | 实时遥测 |
| `0x03` | STATUS | Gateway / Node 状态 |
| `0x04` | EVENT | 告警、节点上下线、错误事件 |
| `0x05` | REPLAY | 离线缓存补传 |
| `0x06` | ACK | 服务端确认 |
| `0x07` | PING | 应用层心跳 |
| `0x08` | PONG | 心跳响应 |

## 8.5 `flags`

建议冻结：

```text
bit0 LIVE
bit1 REPLAY
bit2 FILTERED
bit3 UTC_SYNCED
bit4 DERIVED
bit5 INVALID
bit6 STALE
bit7 ALARM
bit8..15 reserved
```

### 8.5.1 LIVE 与 REPLAY

实时数据：

```text
flags.LIVE = 1
flags.REPLAY = 0
```

补传数据：

```text
flags.LIVE = 0
flags.REPLAY = 1
```

服务端和浏览器禁止将 REPLAY 当成当前实时状态触发实时告警。

## 8.6 Stream ID

| ID | Stream |
|---:|---|
| `0x01` | ECG_RAW |
| `0x02` | ECG_FILTERED |
| `0x03` | RESP_RAW |
| `0x04` | PPG |
| `0x05` | RESP_FILTERED |
| `0x10` | HR |
| `0x11` | RR |
| `0x12` | SPO2 |
| `0x13` | PR |
| `0x20` | NIBP_PRESSURE |
| `0x21` | NIBP_RESULT |
| `0x30` | TEMP |
| `0x40` | NODE_STATUS |
| `0x41` | GATEWAY_STATUS |
| `0x50` | ALARM_EVENT |

### 8.6.1 RR Stream 责任与 Payload

`RR` (`stream_id=0x11`) 来源逻辑为：

```text
Node-B RESP_RAW
→ P RR Algorithm
→ Node-B 实时运行
→ Gateway-C
→ Cloud
```

建议 Payload：

```text
Byte 0..1   rr_bpm_u16_le
Byte 2      rr_quality_u8
Byte 3      rr_status_u8
Byte 4      resp_algo_version_u8
Byte 5      method_u8          # 1=time, 2=freq, 3=fused
Byte 6..7   reserved
```

若 Lead-Off、波形幅值不足、运动伪迹严重、时域/频域估计不一致，则必须设置 `INVALID`/低质量状态，不得保持上一正常 RR 冒充实时值。

## 8.7 序号、去重与重启

服务端唯一数据键建议为：

```text
(gateway_id, node_id, boot_id, stream_id, seq)
```

同键重复到达：

```text
只保留一次
```

`boot_id` 变化：

```text
表示 Gateway 或备用 Node 新启动会话
```

不得因为 `seq` 重新从 0 开始而误判为旧包。

## 8.8 时间

优先级：

```text
UTC_SYNCED timestamp
    > Gateway monotonic + server mapping
    > server_receive_time fallback
```

Gateway 可通过 ESP8266 SNTP 或云端握手获取 UTC，并使用 RTC/单调计时维持时基。

## 8.9 重连策略

Gateway 与云端连接失败时：

```text
1 s → 2 s → 4 s → 8 s → 16 s → 30 s
```

最大退避保持 30 s，并加入少量抖动，避免服务器恢复时同时重连。

WSS 正常时每约 20 s 发送 Ping/Pong 或应用层心跳。

# 11. 安全设计

## 11.1 数据安全

- Gateway → Cloud 强制 WSS/TLS；
- ESP8266 必须验证服务器证书，禁止长期使用“忽略证书验证”的调试配置；
- Token/密钥不写入公开日志；
- 云端 Session 与 Gateway Token 分离；
- 浏览器不可直接连接设备；
- 浏览器只允许读取授权监护会话。

## 11.2 操作安全

本期云端为 **只读监护链路**。

以下操作不得从公网开放：

- NIBP 启动充气；
- NIBP 强制停泵/泄压；
- 传感器写寄存器；
- 修改医疗阈值；
- 固件烧录。

## 11.3 人体测试边界

在未完成电气安全审查、供电隔离、漏电风险确认之前，不以人体连接替代台架验证。

首轮验证顺序：

```text
内部测试源 / 串口模拟器
→ 模块台架
→ CAN 联调
→ 云端仿真
→ 受控人体测试（如确需且条件满足）
```

# 15. Gateway-C 离线缓存（建议）

## 15.1 目的

解决：

- 路由器重启；
- WAN 临时中断；
- 腾讯云维护；
- Nginx/Backend 短时不可用。

## 15.2 工作模式

```text
Cloud Online
    ↓
LIVE → 直接上传

Cloud Offline
    ↓
LIVE → Gateway Ring Buffer

Cloud Recover
    ↓
LIVE → 最高优先级实时上传
REPLAY → 低优先级后台补传
```

## 15.3 缓存介质

优先使用 Gateway-C 板载 SPI Flash；若实物核实为 W25Q128 16 MB，可作为一期介质。

合同目标：

- 最低保存 **30 分钟核心数据**；
- 目标 **60 分钟**；
- 实际可保存时长由最终记录格式、Flash 容量和磨损策略实测确定。

若板载 Flash 不满足，再增加 microSD 或外部 Flash，不在前期强行增加硬件。

## 15.4 缓存安全

必须具有：

- Ring Buffer；
- Block Header；
- CRC；
- 写入指针；
- 已确认上传指针；
- 掉电后恢复扫描；
- LIVE 与 REPLAY 分离；
- Flash 擦写寿命统计。

# 16. 备用方案：Node-A / Node-B ESP8266 WSS 冷备用

本方案作为 **预留能力**，不作为当前 P0 必做验收项。

## 16.1 目的

解决 Gateway-C 本身失效，而 Node-A / Node-B 仍正常工作的场景。

正常：

```text
Node-A ─┐
        ├── CAN → Gateway-C → ESP-C → WSS → Cloud
Node-B ─┘
```

Gateway 故障：

```text
Node-A → ESP-A ─┐
                ├── WSS/TLS → Cloud
Node-B → ESP-B ─┘
```

## 16.2 设计原则

- ESP-A/B 正常情况下不上云；
- Node 连续检测 Gateway 心跳失效并达到确认时间后才允许切换；
- 冷备用仍使用 MMP/2，不新建第二套数据模型；
- 服务器通过 `source_path` 区分：

```text
PRIMARY_GATEWAY
EMERGENCY_DIRECT
```

- 去重键仍包含 node/boot/stream/seq；
- Gateway 恢复稳定一段时间后，关闭 Emergency Direct；
- 避免主/备长期同时上传。

## 16.3 MQTT 决策

当前 **不增加 MQTT 作为公网备用协议**。

原因：

1. 如果 MQTT 与 WSS 共用同一 ESP8266、同一 Wi-Fi、同一路由器、同一公网，则没有形成故障域冗余；
2. ESP8266 ESP-AT 的 MQTT over TLS 受内存/固件能力限制，不适合作为本期安全公网备用基线；
3. 同时维护 WSS 与 MQTT 会增加两套协议、Topic、ACL、Broker 和重复数据处理。

MQTT 保留为二期可选：

- ESP32 / Linux Gateway 升级后的设备侧方案；或
- 云端内部消息总线，用于后端服务解耦。

# 20. 风险登记与处理

| 风险 | 影响 | 当前措施 |
|---|---|---|
| 血氧实物不是 HKS-12C | A 工期与接口变化 | 暂定 HKS，W1 完成型号确认 |
| 四块屏为 RS232 而非 TTL | MCU 电气风险 | 上电前核验，必要时加电平转换 |
| CAN 收发器不兼容 | A/B/C 无法组网 | 在 M3 前做单独 CAN 回环和双节点验证 |
| Gateway-C 单点故障 | 全局上云中断 | 一期离线缓存；二期 A/B ESP 冷备用 |
| 路由器/WAN 故障 | 上云中断 | Gateway Ring Buffer + REPLAY |
| ESP8266 TLS 内存不足 | 重启/连接不稳 | 仅一个公网 TLS 会话，不并行 MQTT |
| FIR 延迟 | Web 波形滞后 | Raw 与 Filtered 双链路分开验收 |
| RR 算法在真实 RESP 上质量不足 | RR 不稳定或误检 | P 先做 Python Reference + SQI，再发布 C 库；B 只集成冻结版本 |
| NIBP 大电流干扰 | MCU 复位 | 独立 5V 支路、储能、电源完整性测试 |
| 密钥泄露 | 云端未授权接入 | Secret 不入 Git、可轮换 Token |
| 浏览器被当成关键网关 | PC 关机导致数据断 | PC 从架构关键链路移除 |

# 附录 B：关键技术冻结结论

1. HKS 血氧历史 `0xCD` 校验和解释废止，采用动态累加，实物抓包最终确认；
2. GY-641V3 I2C 温度为 Big-Endian 原始字节，按 `int16_t` 补码解析，进入统一协议后转 Little-Endian；
3. ADS1292R `PD0/PD1` 使用时必须关闭 FSMC；
4. 129-tap / 250 Hz FIR 理论群延迟 256 ms，Raw 与 Filtered 指标分离；
5. 四模块四屏；Node-A/Node-B 各两模块两屏；
6. 第三块 STM32F407 作为 Gateway-C；
7. Node-A/B → Gateway-C 使用 CAN + MMP-BUS/1；
8. Gateway-C → Cloud 使用 ESP8266-C + WSS/TLS + MMP/2；
9. PC 仅为浏览器终端，不是 Gateway；
10. Gateway-C 离线缓存建议一期实现；
11. A/B ESP WSS 直连作为冷备用预留；
12. MQTT 当前不作为备用公网协议；
13. 最终单板样机开发暂定，测试通过后另立合同；
14. v0.4 人员模块归属冻结：A = SpO2 + NIBP；B = TEMP + ADS1292R ECG/HR/RESP_RAW；P = RR Algorithm；
15. RR 正式运行于 Node-B，但算法所有权、Python Reference、C Library、质量判定和版本维护归 P；
16. MMP-BUS/1 原有数据流 ID 尽量不变，仅更新来源 Node：ECG/RESP/HR/RR/TEMP 属于 Node-B；SpO2/PPG/PR/NIBP 属于 Node-A。
